# MCP

> 도구와 환경

외부 도구 서버를 하니스에 꽂는 프로토콜. 에이전트가 하니스에 기본 제공되는 것 이상의 도구를 얻는 방법.

**Model Context Protocol.** 외부 도구 서버를 [하니스](./harness.md)에 꽂는 프로토콜로, [에이전트](./agent.md)가 하니스에 기본 제공되는 것 이상의 [도구](./tool.md)를 얻는 방법입니다. 에이전트는 "MCP를 호출"하지 않습니다. 도구를 호출하고, 하니스가 그 도구를 MCP 서버에서 가져왔을 뿐입니다. 리소스(읽기 전용 데이터)와 프롬프트(재사용 가능한 템플릿)도 노출하지만 도구 제공이 주된 용도입니다.

이 프로토콜은 통합 문제를 풉니다. 표준이 없다면 모든 하니스가 자기만의 Linear 통합, Slack 통합, 데이터베이스 통합을 필요로 하고, 각각 따로 작성하고 유지해야 합니다. MCP가 있으면 통합을 서버로 한 번 작성하고, MCP를 지원하는 어떤 하니스든 쓸 수 있습니다. 하니스가 서버에 연결하고, 서버가 자신이 제공하는 도구를 알리면, 그 도구들이 내장 도구와 함께 에이전트에게 쓸 수 있게 됩니다.

비용은 [컨텍스트](./context.md)로 치릅니다. 서버가 알리는 모든 도구는 이름, 설명, 파라미터 스키마로 된 정의로 도착하고, [모델](./model.md)은 아는 도구만 호출할 수 있습니다. 순진한 접근은 모든 정의를 미리 [컨텍스트 창](./context-window.md)에 로드하는 것입니다. 넉넉한 서버 몇 개를 설치하면 [세션](./session.md)이 아무것도 입력하기 전부터 수천 [토큰](./token.md)의 도구 스키마로 시작하고, 작업이 쓰지 않을 도구에 [주의 예산](./attention-budget.md)을 씁니다.

많은 하니스는 이제 도구 검색으로 이를 완화합니다. 전체 정의 대신 컨텍스트에 쓸 수 있는 도구를 가리키는 [컨텍스트 포인터](./context-pointer.md)를 두고, 에이전트가 이름이나 목적으로 도구를 검색해 필요할 때만 정의를 로드합니다. 하니스가 이렇게 하지 않으면 선행 비용이 그대로 적용되므로, 프로젝트가 실제로 필요로 하는 서버만 활성화하는 것이 좋습니다.

_사용 예:_

"에이전트가 Linear에서 티켓을 읽어야 해요."

"하니스가 Linear MCP 서버를 쓰도록 설정하세요. Linear API를 에이전트가 호출할 수 있는 도구로 노출합니다. 맞춤 도구 래퍼를 직접 쓰는 수고를 덜 수 있어요."
