# 자동 검사 (Automated check)

> 작업 패턴

환경에서 실행되는 결정적 검증. 테스트, 타입 검사, 린트, 빌드, 프리커밋 훅. 통과/실패만 있고 판단은 없습니다.

[환경](./environment.md)에서 실행되는 결정적 검증입니다. 테스트, 타입 검사, 린트, 빌드, 프리커밋 훅이 여기에 속합니다. 통과/실패만 있고 판단은 없습니다. [에이전트](./agent.md)가 다른 누구도 개입시키지 않고 스스로 교정할 수 있는 신호입니다. 불안정한(flaky) 테스트는 검사가 아닌 것이 아니라 고장 난 검사입니다. 자동 검사는 _설계상_ 결정적입니다.

자가 교정은 루프로 동작합니다. 에이전트가 변경을 하고, [도구 호출](./tool-call.md)로 검사를 실행하면, 실패 출력이 [컨텍스트 창](./context-window.md)에 들어옵니다. 파일과 줄이 적힌 타입 오류, 기대값과 실제값이 적힌 실패한 단언입니다. 에이전트가 문제를 고치고 다시 검사를 돌리기에 충분하며, 통과할 때까지 사람이 개입하지 않고 반복합니다. 이 루프를 믿을 수 있게 하는 것은 결정성입니다. 같은 코드는 항상 같은 판정을 내므로 통과가 의미를 갖습니다. 불안정한 검사는 이를 오염시킵니다. 에이전트가 멀쩡한 코드를 "고치거나" 실제 실패를 재시도로 넘겨 버립니다.

그래서 좋은 검사는 코드베이스의 [AX](./ax.md)에서 큰 부분을 차지합니다. 엄격한 타입, 빠른 테스트 스위트, 린터가 있는 저장소의 에이전트는 자기 실수 대부분을 당신이 보기 전에 잡습니다. 그런 것이 없는 저장소의 에이전트는 만든 것을 그대로 내놓습니다. 이 차이는 실행 중 유일한 검증이 검사뿐인 [AFK](./afk.md) 실행에서 가장 큽니다. 다만 검사는 단언한 것만 잡습니다. 초록불은 단언한 속성이 성립한다는 뜻이지 코드가 옳다는 뜻이 아닙니다. 판단이 필요한 빈틈은 [자동 리뷰](./automated-review.md)와 [사람의 검토](./human-review.md)의 몫입니다.

_피할 표현:_ "피드백 루프" / "백프레셔": 둘 다 검사와 리뷰를 뭉뚱그립니다. _피할 표현:_ "테스트": 테스트는 자동 검사지만 모든 자동 검사가 테스트는 아닙니다.

_사용 예:_

"에이전트가 AFK 실행에서 계속 망가진 코드를 내놓아요."

"[샌드박스](./sandbox.md)에 어떤 자동 검사가 연결되어 있죠?"

"단위 테스트만요."

"타입 검사와 린트를 추가하세요. PR이 올라오기 전에 그것들로 스스로 교정할 겁니다."
