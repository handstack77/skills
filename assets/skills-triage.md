# 분류

## 기능

`triage`는 프로젝트 추적기의 문제들을 처리합니다. 각 문제를 **분류 역할**(카테고리 역할과 상태 역할)의 작은 상태 기계를 통해 이동시킵니다. 각 문제는 에이전트 준비 완료 요약, 보고자에게의 특정 질문, 또는 기록된 이유가 있는 종료된 문제로 끝납니다.

이것은 **직접 생성하지 않은** 문제에만 해당됩니다. 즉, 원시 버그 보고서, 들어오는 기능 요청, 또는 사전 알림 없이 도착한 외부 풀 리퀘스트를 의미합니다: 추적 시스템에 외부에서 들어온 작업으로, 보고자가 남긴 형태 그대로입니다. [to-tickets](./skills-to-tickets.md)의 [티켓](./ticket.md)은 이미 에이전트가 처리할 준비가 되어 있으므로, 그 위에 `triage`을 실행하면 작업이 낭비됩니다. 규칙은 간단합니다: `/triage`은 들어오는 문제에만 적용되며, 직접 생성한 문제에는 적용되지 않습니다.

손으로 라벨링하는 것과도 다릅니다. 왜냐하면 추천을 한 후 기다리기 때문입니다. 그것은 이유와 함께 카테고리와 상태 호출을 제공하고, 코드베이스에서 찾은 것을 알려주며, 사용자가 지시하기 전까지는 아무것도 적용하지 않습니다.

## 언제를 사용해야 하는가

당신은 `/triage`를 입력한 다음 원하는 것을 일반적인 언어로 설명하여 이것을 호출합니다. [에이전트](./agent.md)는 스스로 그것을 실행하지 않습니다. 예시: "내 주의가 필요한 것을 보여줘", "#42를 보자", "#42를 에이전트 준비 상태로 이동"

| 현재 상태 | 이동할 위치 |

| --- | --- |
| 다른 사람들의 원시 보고서로 가득한 트래커 | `/triage` |

| 직접 생각한 대충의 아이디어, 기록된 것은 없음 | [문서와 함께 그릴](./skills-grill-with-docs.md) |

| [스펙](./spec.md)으로 변환할 확정된 대화 | [to-spec](./skills-to-spec.md) |

| 에이전트 준비용 티켓으로 나눌 스펙 | [to-tickets](./skills-to-tickets.md) |
| 레이블이 아닌 근본 원인이 필요한 확인된 버그 | [버그 진단](./skills-diagnosing-bugs.md) |

## 전제 조건

`triage`는 귀하의 이슈 트래커를 읽고 쓰므로, [setup-me-skills](../docs/engineering/setup-me-skills.md)가 먼저 해당 트래커와 레이블 어휘를 구성해야 합니다. 아래의 역할 이름은 **표준적**입니다. 트래커의 레이블 문자열은 다를 수 있으며, setup에서 매핑을 제공합니다. 트래커가 이미 표준 이름을 정확히 사용하고 있다면, 매핑이나 설정할 것은 없습니다.

트래커 구성은 외부 풀 리퀘스트가 요청 범위에 포함되는지와 누가 외부로 간주되는지를 결정합니다. 해당 플래그는 기본적으로 꺼져 있으며, 설정 시 더 이상 이에 대해 묻지 않습니다. PR을 범위에 포함하려면 `docs/agents/issue-tracker.md`에서 켜면 됩니다.

## 상태 기계

모든 분류된 항목은 정확히 하나의 카테고리 역할과 하나의 상태 역할로 끝납니다. 카테고리는 두 가지가 있습니다: `bug` (무언가가 고장남) 및 `enhancement` (새로운 기능 또는 개선). 상태는 다섯 가지가 있습니다:

| 상태 | 의미 |

| --- | --- |
| `needs-triage` | 평가해야 합니다. 라벨이 없는 문제는 보통 먼저 여기에 도착합니다. |

| `needs-info` | 보고자의 응답을 기다리고 있습니다. 그들이 회신하면 `needs-triage`로 돌아갑니다. |

| `ready-for-agent` | 완전히 명시되어 있으며, 에이전트 브리핑이 첨부되어 있습니다. [AFK](./afk.md) 상태의 에이전트가 처리할 수 있습니다. |
| `ready-for-human` | 동일한 요약, 추가로 에이전트가 수행할 수 없는 이유: 판단, 외부 접근, 수동 테스트. |

| `wontfix` | 종료됨, 이유가 기록됨. |

그것이 전체 어휘입니다. 항목당 정확히 하나의 상태 역할이라는 규칙은 쿼리를 단순하게 유지합니다. 상태는 또한 [기술](./skill.md)에서 가장 많이 요청되는 부분입니다. 사용자는 다른 문제로 인해 차단된 지정된 작업을 위한 상태, 미래 트리거를 기다리는 작업을 위한 `deferred` 상태, 그리고 종료 `implemented` 상태를 요청했습니다. 그 중 어느 것도 출시되지 않았습니다. 아래 질문을 참조하세요.

`wontfix`에는 세 가지 사례가 있습니다. 차이가 중요한 이유는 그 중 하나만 지식 베이스에 기록되기 때문입니다:

| 왜 종료하는지 | 어떤 일이 발생하는지 |

| --- | --- |
| 이미 구현됨 | 기능이 이미 존재하는 위치를 가리키는 코멘트. 이미 구현된 기능이므로 `.out-of-scope/`에는 아무것도 들어가지 않으며, 파일을 넣으면 중복 확인이 깨집니다. |

| 거부된 버그 | 정중한 설명 후 종료. |

| 거부된 개선사항 | `.out-of-scope/`에 파일을 넣고 종료 코멘트에서 링크한 후 종료. |

`.out-of-scope/`는 각 거부된 **개념**마다 하나의 마크다운 파일을 보관하며, 이슈마다 보관하지는 않습니다. 각 파일은 짧은 디자인 문서로, 데이터베이스 행이 아닙니다. 파일에는 무엇이 거부되었는지, 그 이유, 그리고 그것을 요청한 모든 이슈가 나와 있습니다. `triage`는 어떤 평가를 시작하기 전에 전체 디렉터리를 읽습니다. 파일은 키워드가 아니라 개념으로 매칭되므로 '야간 테마'는 `dark-mode.md`와 매칭됩니다. 매칭을 찾으면 이전 결정을 보여주고, 요청을 처음부터 다시 논쟁하지 않고 여전히 동의하는지 묻습니다.

## 브리핑 전에 확인

어떤 [심문](./grilling.md) 전에, `triage`는 해당 주장(claim)이 옳은지 확인합니다. 버그의 경우, 리포터가 제시한 단계에서 재현합니다. PR의 경우, 브랜치를 확인하고 관련 테스트를 실행합니다. 그런 다음 세 가지 결과 중 하나를 보고합니다:

- 코드 경로와 함께 확인됨.

- 재현 실패.

- 시도할 자세한 정보가 부족함. 이것이 가장 강력한 `needs-info` 신호입니다.

같은 과정에서, 코드베이스에 대해 두 가지 검사를 더 수행합니다. **중복성** 검사는 해당 기능이 이미 구현되어 있는지 묻고, 리포터의 표현이 아닌 도메인 개념으로 검색합니다. **이전 거절** 검사는 `.out-of-scope/`가 이미 아니라고 말했는지 묻습니다. 두 검사 모두 비용이 적으며, 어느 하나라도 해당되면 `wontfix`가 생성됩니다.

이 모든 작업은 하나의 아티팩트를 좋게 만든다: **에이전트 브리프(agent brief)**. 이것은 문제가 `ready-for-agent`로 이동할 때 `triage`가 게시하는 구조화된 코멘트다. `triage`가 게시한 후에는, 브리프가 계약이 되고 원래 보고서는 단지 컨텍스트에 불과하다. 브리프는 정확하기보다는 **내구성(durable)**을 갖는다. 왜냐하면 코드가 변경되는 동안 문제가 `ready-for-agent`에 몇 주 동안 머물 수 있기 때문이다. 따라서 브리프는 타입, 시그니처, 행동 계약을 명시하며, 파일 경로나 라인 번호는 절대 명시하지 않는다. 확인된 재현이 추측보다 훨씬 더 강력한 브리프를 만든다.

## PR은 코드가 첨부된 이슈입니다

트래커가 외부 풀 리퀘스트를 요청 표면으로 취급하면, 이들은 동일한 범주, 상태 및 전환을 가진 동일한 머신을 거칩니다. 상태는 diff에 적용됩니다. `ready-for-agent`는 브리프가 첨부되어 있고 에이전트가 코드에서 다음 단계를 진행해야 함을 의미합니다. `ready-for-human`는 사람이 이를 병합할 수 있음을 의미합니다. PR에 대한 브리프는 기존 diff에서 해야 할 일을 설명하며, 처음부터 무언가를 만드는 방법을 설명하는 것은 아닙니다.

Discovery는 오직 *외부* PR만 보여줍니다. 이는 협력자의 진행 중인 브랜치가 선별(triage) 작업이 아니기 때문입니다. 이 필터는 discovery에만 적용됩니다. PR을 명시적으로 지정하면, `triage`가 작성자와 상관없이 처리합니다.

## 자주 묻는 질문

**저는 `/to-spec`와 `/to-tickets`를 실행했으며, 이제 그 티켓들이 분류되지 않은 상태로 남아 있습니다. 그 위에 `/triage`를 실행해야 하나요?**
아니요. 그들은 이미 에이전트 준비가 되어 있습니다. `to-tickets`는 문서를 게시할 때 `ready-for-agent` 라벨을 적용하므로 AFK 러너가 다른 과정 없이 이를 가져갑니다. 이 문제를 겪은 사용자는 스펙 플로우를 실행하고 출력에서 `needs-triage`를 확인했으며, 그들의 AFK 러너는 모든 것을 무시했습니다. `triage`는 외부에서 들어오는 작업을 위한 진입로입니다. 스펙 플로우는 사용자가 직접 시작하는 작업의 차선입니다. 이 둘은 `ready-for-agent`에서 만나며, 그 전에는 만날 수 없습니다.

**`to-spec` → `to-tickets` → `implement` 흐름이 있는 지금, `triage`가 여전히 관련이 있나요?**
인바운드 작업이 있는 경우에만 해당됩니다. `triage`는 그 흐름보다 오래되었으며 다른 일을 처리합니다: 다른 사람이 제출한 보고서를 처리합니다. 트래커에 있는 모든 항목이 자신의 계획에서 나온 것이라면 거의 사용하지 않게 될 것입니다. 공개적으로 유지 관리하는 것이 있거나 팀이 버그를 당신에게 제출한다면, 그 작업이 시작되는 곳입니다. 주요 용도는 외부 기여자로부터 문제를 받는 오픈 소스 저장소입니다.

**에이전트가 `ready-for-agent`와 `gh`를 적용하려고 시도했으나, 라벨이 존재하지 않는다고 표시되었습니다.**
이것은 알려진 오픈 버그입니다 (#616). `setup-me-skills`는 라벨 어휘를 `docs/agents/triage-labels.md`에 작성하지만, 사용자의 트래커에는 라벨을 생성하지 않습니다. 다섯 개의 상태 라벨과 두 개의 카테고리 라벨을 `gh label create` 또는 트래커의 UI를 사용하여 한 번만 직접 생성하면 오류가 멈춥니다. 이 문제는 아직 병합되지 않은 커뮤니티 수정 브랜치와 연결되어 있습니다.

**다섯 상태로는 충분하지 않습니다. 차단, 연기, 구현은 어떨까요?**

이 기술은 가장 많이 접수된 공백입니다. 세 가지 형태로 나뉩니다:

- 완전히 명시된 이슈이지만 다른 이슈가 종료될 때까지 기다리는 이슈(#139). 기자는 `ready-for-agent` '기술적으로는 사실'이지만 오해의 소지가 있어 에이전트가 이를 집어 들고 막히게 된다고 말했습니다.

- 의도되었지만 트리거를 기다리는 미래 작업으로, 아직 실행할 수 없음 (#297).

- "구현됨, 검증 대기" 상태에 대한 종료 상태. 없으면, AFK 실행기가 완료된 티켓을 다시 큐에 넣을 수 있음.

차단된 케이스는 실제로 받아들여지지만, 이름은 결정되지 않았습니다 (`blocked` 대 `paused`). 어느 것도 출하되지 않았습니다. 임시 해결책으로, 사람들은 카테고리 옆에 리포지토리 로컬 추가 라벨을 추가합니다. 그러면 상태 슬롯은 정확한 값을 가지지만, 스킬은 추가 라벨에 대해 알지 못합니다. 한 커뮤니티 포크는 더 나아가 `needs-slicing`, `tracking` 및 노력 라벨을 추가합니다. 그것은 작동하지만, 그 포크에 속할 뿐 스킬에는 속하지 않습니다.

**이것이 `/diagnosing-bugs`와 어떻게 다른가요?**
여기서 검증 단계는 의도적으로 얕습니다. 이것은 "이것이 실제인가, 그리고 대략 어디에 있는가"를 답하며, 근본 원인을 찾지 않습니다. 보고자의 단계에서 몇 분 안에 버그가 재현되지 않으면 `needs-info`를 사용하거나, 지금 조사하고 싶다면 [diagnosing-bugs](./skills-diagnosing-bugs.md)를 사용하세요. 두 스킬의 텍스트는 아직 서로를 언급하지 않습니다. 한 사용자가 그 간극을 보고했으며, 여전히 열려 있습니다.

**내 전체 백로그를 향해 그것을 가리키고 실행할 수 있나요?**
물어볼 수는 있지만, 그것이 읽는 내용을 주의해서 보세요. '주의가 필요한 항목 표시' 패스는 *선택*을 위한 저렴한 목록입니다. 하나의 문제를 선택하면 `triage`가 해당 문제에 대한 전체 [맥락](./context.md)을 수집합니다. 만약 한 번에 스무 개의 문제에 걸쳐 실행하면, 에이전트는 그 저렴한 목록만을 유일한 증거로 사용하면서 당신에게 알리지 않을 수 있습니다. 목록은 문제 본문을 반환하지만 댓글은 반환하지 않습니다. 한 사용자가 정확히 이 상황을 겪었습니다. 이미 '이미 수정됨, 닫는 것을 권장함'이라는 댓글이 달린 세 개의 문제가 있었고, 세 문제 모두 새 에이전트 요약을 받았습니다. 대량 패스를 실행할 경우, 각 문제의 댓글을 반드시 읽도록 명시적으로 말하세요.

**Linear이나 GitHub Issues 외 다른 것과도 작동하나요?**
네. 트래커는 하드코딩된 가정이 아니라 설정(config)입니다. 사람들은 이를 Linear(`linear` CLI를 통해), GitLab, 그리고 `.scratch/` 아래의 일반 마크다운 파일에 대해 실행합니다. 일반적인 분할은 이슈와 계획은 Linear, 코드와 PR은 GitHub를 사용하는 것입니다. "이슈 트래커"라고 표시된 스킬은 Linear에 매핑되고, "PR"이라고 표시된 스킬은 GitHub에 매핑됩니다. 로컬 마크다운 트래커에는 오픈 템플릿 버그가 있습니다: 생성된 파일에는 수용 기준이 두 번 포함될 수 있는데, 한 번은 최상위 수준에서, 한 번은 에이전트 브리프 안에서(#200) 포함됩니다.

## 작동 중이면

- 접하는 모든 항목은 정확히 하나의 카테고리 역할과 하나의 상태 역할로 끝나며, 0이거나 서로 충돌하는 두 상태가 절대 나오지 않습니다.

- 논리적 근거와 함께 추천을 제공하고 멈춥니다. 문제의 라벨을 다시 지정하고 진행하지 않습니다.

- 버그를 재현했거나, PR을 확인하고 실행했으며, 그 전에 `ready-for-agent`에 도달한 것은 없습니다.

- 그것이 작성하는 브리핑은 타입과 동작을 명시하며, 파일 경로나 라인 번호를 포함하지 않습니다.

- 6개월 전에 거부한 요청이 다시 오면, 다시 선별하지 않고 예전 이유를 인용하면서 알려줍니다.

- 게시하는 모든 댓글은 `> *This was generated by AI during triage.*`

## 적합한 위치

`triage`는 **온램프(on-ramp)**이며, 메인 체인의 단계가 아닙니다. 메인 흐름은 당신이 가진 아이디어(그릴, 사양, 티켓, 구현, 리뷰)에서 시작됩니다. `triage`는 다른 사람으로부터 온 작업을 위한 병렬 레인입니다. 두 레인은 같은 곳에서 끝납니다: 간단한 설명이 있는 `ready-for-agent` 라벨이 붙은 이슈입니다. [implement](./skills-implement.md)은 [to-tickets](./skills-to-tickets.md)에서 티켓을 가져오는 것과 같은 방식으로 이를 처리합니다. 요청이 `triage`가 간단히 설명하기 전에 더 많은 세부 사항이 필요할 때, `triage`는 [grilling](./skills-grilling.md)과 [domain-modeling](./skills-domain-modeling.md)을 한 번에 한 라운드씩 실행하여 `GLOSSARY.md`와 ADR에 결정을 기록합니다. 자신이 어떤 레인에 있는지 확실하지 않을 때, [ask-me](./skills-ask-me.md)가 경로를 안내합니다.
