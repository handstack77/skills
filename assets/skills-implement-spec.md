# 구현 사양

## 기능

`implement-spec`는 [spec](./spec.md)과 그 [tickets](./ticket.md)을 가져와 한 번에 모두 처리합니다. 조정하는 [agent](./agent.md)는 각 티켓을 자체 git 작업 트리에서 작업하는 구현자 [subagent](./subagent.md)에게 전달하고, 완료된 각 브랜치를 하나의 **integration branch**로 병합하며, 결과에 대해 [code-review](./skills-code-review.md)를 실행하고 티켓을 해결합니다.

티켓을 목록이 아닌 **작업 그래프**로 읽습니다. 차단 엣지는 무엇이 시작될 수 있는지를 결정하므로, 언제든지 차단자가 모두 완료된 티켓들의 **전선(frontier)**이 있으며, 전선 위의 모든 티켓이 동시에 실행됩니다. 이것이 티켓을 하나씩 처리하는 것과의 차이입니다. 그래프의 형태가 속도를 결정하며, 트래커에서 티켓의 순서가 속도를 결정하지 않습니다.

## 언제 사용할까

이것은 `/implement-spec`를 입력하여 호출하며, 에이전트가 스스로 사용하지는 않습니다.

| 상황 | 사용할 때 |

| --- | --- |
| 한 번에 적용하고 싶은, 블로킹 엣지가 있는 티켓으로 나뉜 스펙 | `/implement-spec` |

| 자신의 [컨텍스트 창](./context-window.md)에서 한 번에 하나의 티켓씩, 티켓 간 [정리](./clearing.md) | [구현](./skills-implement.md) |

| 아직 티켓으로 나뉘지 않은 스펙 | 먼저 [티켓으로 변환](./skills-to-tickets.md) |
| 실제 그래프가 없는 작은 작업 조각 | [바로 구현](./skills-implement.md) |

## 사전 요구 사항

- **이슈 추적기.** 이 스킬은 설정된 추적기 [setup-me-skills](../docs/engineering/setup-me-skills.md)에서 티켓을 읽고 해결합니다. 설정이 되어 있지 않으면, 추측하는 대신 먼저 해당 설정을 실행하라고 알려주며 중단됩니다.

- **블로킹 엣지가 있는 티켓**: [to-tickets](./skills-to-tickets.md)이 쓰듯이. 엣지가 없으면 그래프는 평평해지고 모든 티켓이 동시에 시작됩니다.

- **서브 에이전트를 백그라운드에서 실행하고 각 에이전트에 git 작업 트리를 제공하는 [하네스](./harness.md).** 이 기능은 티켓을 동시에 실행하기 위해 존재하므로, 서브 에이전트를 하나씩 실행하는 하네스에서는 단지 `implement`보다 느립니다.

## 통합 브랜치

모든 것은 하나의 브랜치에 합쳐집니다. 각 구현자는:

- 시작하기 전에 자신의 워크트리가 통합 브랜치를 기반으로 하고 있는지 확인합니다,

- 자신의 티켓을 [tdd](./skills-tdd.md)로 빌드하며, 한 번에 하나의 슬라이스씩 빨간색-녹색으로 진행합니다.

- 완료를 보고하기 전에 통합 브랜치의 최신 커밋을 자신의 브랜치에 병합하므로, 배포 시에 패스트 포워드가 가능합니다.

트래커는 풀 리퀘스트가 존재하는지 여부를 결정합니다. 트래커가 PR을 통해 작업을 닫거나 PR을 요청하면, 스킬은 첫 번째 병합 후에 임시 PR을 열고 마지막에 준비 완료로 표시합니다. 그렇지 않으면 실행은 통합 브랜치에서 중단되며, 모든 티켓이 트래커가 작업을 닫는 방식대로 해결됩니다. 이는 로컬 마크다운 트래커를 대상으로 완전히 오프라인에서 작동합니다.

구현자는 붙여넣은 요약본 대신 [컨텍스트 포인터](./context-pointer.md) (명세서, 티켓, 공유 탐색 노트, 이전 커밋)을 통해 오케스트레이터와 대화합니다. 이렇게 하면 각 서브에이전트의 프롬프트가 작게 유지되고 오케스트레이터 창에 그래프를 표시할 공간이 남습니다.

## 자주 묻는 질문

**이것은 내가 각 티켓에서 직접 `/implement`를 실행하는 것과 어떻게 다른가요?**

이것이 바로 해당 기능이 답변하기 위해 존재하는 질문입니다. 기능이 출시되기 전에는 사람들은 계속해서 자신만의 버전을 만들었고, 한 사용자는 필요성을 이렇게 설명했습니다: '스펙에 5개 이상의 티켓이 포함될 수 있는 경우, 새로운 세션을 하나씩 만들고 각 티켓을 하나씩 수행하도록 지시하는 대신, 하위 에이전트가 티켓을 구현하도록 하고 싶다'고요. `implement`에서는 여러분이 디스패처가 됩니다: 티켓마다 하나의 [세션](./session.md)을 만들고, 그 사이를 비우며, 어떤 티켓이 차단 해제되었는지 스스로 추적하는 방식입니다. `implement-spec`는 그 작업을 하나의 조정 세션에 맡깁니다. 대가로 각 티켓의 작업이 진행될 때마다 읽는 것이 아니라, 마지막에 통합 브랜치를 검토하게 됩니다. 실행을 시작하려면, 컨텍스트를 지우고 `/implement-spec`와 함께 스펙을 가리키는 포인터(이슈 번호 또는 파일 경로)를 입력하면 됩니다. 실제 그래프가 없는 작은 변경의 경우, 이를 건너뛰고 바로 `implement`를 사용하십시오.

**GitHub이 필요합니까? 브랜치에서 멈추기를 원합니다.**

아니요, 더 이상은 아닙니다. 진행 중인 버전을 좋아했던 한 사용자가 정확히 이런 불만을 제기했습니다: "마지막에 PR을 생성하는데, 이는 GitHub과 같은 온라인 저장소가 필요합니다. 오프라인에서도 같은 작업을 수행하고 모든 작업이 병합된 브랜치에서 멈출 수 있으면 좋겠습니다." 현재 실행은 통합 브랜치에서 종료됩니다. PR은 구성된 트래커가 PR을 통해 작업을 종료하거나 사용자가 요청할 때만 열리므로, 로컬 마크다운 트래커에서는 모든 티켓이 해결되고 브랜치에 작업이 병합되면서 실행이 종료됩니다.
**검토 및 수정 루프가 몇 시간 동안 실행되었거나, 아직 빌드되지 않은 티켓을 계속 '수정'했습니다.**
두 가지 경우는 `code-review`가 스킬이 지정한 한 지점을 제외한 다른 곳에서 실행될 때 발생합니다. 이 코드는 전체 사양과 비교하므로, 모든 티켓이 도착한 후에만 의미가 있습니다. 실행 도중에 실행되면, 미작성 티켓마다 실패로 간주됩니다. 그런 다음 에이전트가 해당 티켓을 작성하고, 이는 또 다른 검토를 촉발합니다. 마지막에는 스킬이 `code-review`를 한 번 실행하고 모든 발견 사항을 하나의 수정 하위 에이전트로 보냅니다. 하지만 그 수정 이후 언제 중지할지는 아직 알려주지 않습니다. 한 사용자는 다섯 개 티켓 기능에서 "검토 및 수정 루프가 약 4시간 걸렸다"고 보고했습니다. 두 번째 광범위 검토가 시작되면, 고정된 발견 사항에 대해 집중 체크를 실행하고 중지하라고 지시하세요. 첫 번째 검토가 실제 문제를 찾을 것으로 예상하세요. 실행 결과물은 검토가 완성하는 초안이며, 자체적으로 바로 사용할 수 있는 것은 아닙니다.
**그것은 implement가 하는 것처럼 TDD를 구동합니까?**
지금은 그렇지만 처음에는 그렇지 않았습니다. 진행 중인 버전을 실행하는 사용자들은 '구현 하위 에이전트들이 /tdd 지시어를 상속하지 않는다'는 사실을 발견했기 때문에, 빨강-초록 과정은 티켓 하나에서 전체 사양으로 확장되자마자 중단되었습니다. 이제 각 구현자는 `tdd`로 자신의 티켓을 빌드합니다. `implement` 세션에서처럼 시접을 상호작용적으로 동의하는 단계는 여전히 없으므로, 시접을 고정하고 싶다면 사양이나 티켓에 이름을 지정하세요.

**병렬로 실행 중인 두 구현자가 동일한 파일에서 충돌했거나, 동일한 것에 대해 서로 다른 이름을 선택했습니다.**

워크트리는 충돌을 제거하지 않고 병합 시점으로 미룹니다. 티켓 텍스트에서 작성된 차단 엣지는 각 티켓이 어떤 파일에 영향을 줄지에 대한 추측이며, '코드베이스의 다른 부분'에 있는 두 티켓도 메시지 카탈로그, 설정 레지스트리, 또는 타입을 공유합니다. 각 구현자는 자신의 티켓과 공유된 노트만 볼 수 있으며, 다른 사람의 진행 중인 작업은 볼 수 없습니다. 그래서 한 사용자의 웹과 모바일 티켓이 `blockedSince`와 `blockedOn`로 동일한 문자열을 추가했습니다. 두 개의 프론티어 티켓이 하나의 공유 파일에 접근할 때는, 둘 사이에 차단 엣지를 추가하여 순서대로 실행되게 하거나, 탐색 노트가 각 티켓이 추가하는 정확한 이름을 수정하도록 해야 합니다.

**차단된 티켓은 차단 요소가 병합된 후에도 시작되지 않습니다.**

이것은 GitHub에서 알려진 문제입니다. 트래커의 blocked-by 수는 차단자가 *닫힐 때만* 감소하며, 티켓은 일반적으로 PR이 병합될 때 닫히는데, 이는 실행이 끝나는 시점입니다. 트래커는 시작 그래프를 얻기 위한 올바른 소스이지만 실행 중간에는 오래된 정보입니다. 오케스트레이터에게 어떤 티켓이 통합 브랜치에 병합되었는지 추적하고, 그로부터 프론티어를 계산하도록 지시하세요.

**티켓의 핵심 테스트가 해당 워크트리 내에서 건너뛰어졌고, 성공(green)으로 보고되었습니다.**

워크트리는 git이 추적하는 것만 보유합니다. gitignore에 포함된 피처, 로컬 데이터베이스, 자격증명을 읽는 테스트는 그곳에서 조용히 건너뛸 수 있습니다. 검증이 추적되지 않은 자료에 의존하는 티켓의 경우, 오케스트레이터에 메인 체크아웃에서 실행하도록 알려주세요.

## 작동 중입니다

- 그래프가 허용하는 경우 여러 구현자가 한 번에 실행되며, 하나씩 순차적으로 실행되지 않습니다.

- 티켓은 전체 실행이 끝날 때가 아니라 마지막 블로커가 통합 브랜치에 들어오는 즉시 시작됩니다.

- 모든 티켓의 추적은 `tdd`가 실행 중이며, 코드 이전에 실패한 테스트가 표시됩니다.

- 통합 브랜치로의 병합은 충돌 해결이 아닌 빨리 감기(패스트 포워드) 방식입니다.

- 실행은 모든 티켓이 해결된 한 브랜치에서 끝나며, 트래커에서 원할 경우에만 PR이 생성됩니다.

## 어디에 적합한가

`implement-spec`는 메인 체인의 빌드 단계로, 각 티켓마다 [implement](./skills-implement.md)를 한 번 실행하는 것의 병렬 대안입니다:

```text
grill-with-docs → to-spec → to-tickets → implement-spec → retro
```

그 이웃들은 [to-tickets](./skills-to-tickets.md)로, 읽은 블로킹 엣지를 작업 그래프(task graph)로 선언하며, [code-review](./skills-code-review.md)는 통합 브랜치에서 종료하기 전에 수행합니다. [ask-me](./skills-ask-me.md)는 어떤 흐름에 있는지 확실하지 않을 때 전체 집합을 대상으로 라우터 역할을 합니다.
