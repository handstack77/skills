# 캐시 토큰 (Cache tokens)

> 모델

제공자가 프리픽스 캐시로 이전 요청에서 캐싱해 둔 입력 토큰. 훨씬 낮은 요율로 과금됩니다.

[제공자](./model-provider.md)가 이전 [모델 제공자 요청](./model-provider-request.md)에서 캐싱해 두어 다시 처리할 필요가 없는 [입력 토큰](./input-tokens.md)입니다. 연속된 요청이 프리픽스를 공유하면 제공자는 [프리픽스 캐시](./prefix-cache.md)로 그 작업을 재사용하고 캐시된 부분을 훨씬 낮은 요율로 과금합니다. 긴 [세션](./session.md)을 감당할 만하게 만드는 지렛대입니다. 이것이 없으면 모든 [턴](./turn.md)이 전체 이력의 값을 다시 치릅니다.

이것이 중요한 이유는 세션의 과금 방식 때문입니다. [모델](./model.md)은 [상태가 없으므로](./stateless.md) 모든 요청이 [시스템 프롬프트](./system-prompt.md), 모든 메시지, 모든 [도구 결과](./tool-result.md)를 포함한 대화 전체를 입력 토큰으로 다시 보냅니다. 50번째 턴이 되면 요청마다 50턴 분량의 이력을 싣고, 매번 전부를 정가로 치르게 됩니다. 캐시가 셈을 바꿉니다. 제공자가 이미 같은 프리픽스에서 처리한 토큰은 캐시 토큰으로 과금되며, 흔히 입력 요율의 10분의 1 이하입니다. 긴 세션에서는 보내는 것의 대부분이 캐시 토큰이어서 청구서가 제정신을 유지합니다.

예시가 토큰이 언제 캐시되고 언제 안 되는지 보여 줍니다. 각 글자는 대화 내용의 한 블록이고, 각 요청은 지금까지의 대화를 보냅니다.

| 요청이 보내는 것 | 캐시됨 | 정가로 과금 | 이유 |
| --- | --- | --- | --- |
| `AB` | 없음 | `AB` | 첫 요청이라 맞춰 볼 것이 없음 |
| `ABC` | `AB` | `C` | `AB`가 이전 요청의 정확한 프리픽스 |
| `ABCD` | `ABC` | `D` | 프리픽스가 여전히 온전함 |
| `AXCD` | `A` | `XCD` | 편집으로 `B`가 `X`가 되어 거기서 일치가 깨짐 |

캐시는 특정한 방식으로 취약합니다. 정확한 프리픽스만 일치시킵니다. 대화의 앞쪽에서 무엇이든 바뀌면(예: [하니스](./harness.md)가 내용을 재배열하거나, 타임스탬프가 갱신되거나, 파일의 표현이 달라지면) 그 지점부터 캐시가 빗나가고 이후의 모든 것이 입력 정가로 과금됩니다. 캐시는 몇 분의 비활동 뒤에 만료되기도 하므로, 오래 쉬었다 재개한 세션은 이력 값을 한 번 다시 냅니다. 뚜렷한 이유 없이 세션 비용이 뛰면 사용량 보고서에서 캐시 토큰과 입력 토큰을 비교해 보세요. 깨진 캐시는 거기서 먼저 드러납니다.

_사용 예:_

"긴 세션 비용이 끔찍해요. 리팩터링 하나에 8달러예요."

"캐시 토큰을 확인하세요. 하니스가 턴 사이에 시스템 프롬프트나 파일을 재배열하고 있으면 프리픽스가 깨져서 요청마다 입력 정가를 다시 냅니다."
