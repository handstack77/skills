# 자동 리뷰 (Automated review)

> 작업 패턴

한 에이전트가 다른 에이전트의 작업을 검토하는 것. 흔히 다른 모델이나 시스템 프롬프트를 씁니다. 비결정적이며 판단을 내립니다.

한 [에이전트](./agent.md)가 다른 에이전트의 작업을 검토하는 것으로, 흔히 다른 [모델](./model.md)이나 [시스템 프롬프트](./system-prompt.md)를 씁니다. 비결정적이며 판단을 내립니다. 어디서든 돌 수 있습니다. PR의 병합 전, 커밋 이력에 대한 사후, [서브에이전트](./subagent.md)로서의 세션 도중. CI의 LLM-as-judge는 [자동 검사](./automated-check.md)가 아니라 자동 리뷰입니다. 범주를 정하는 것은 어디서 도느냐가 아니라 단언이 _무엇을 하느냐_입니다.

작업하는 에이전트와 분리되어 있다는 점이 이것을 작동하게 합니다. 코드를 쓴 에이전트에게 자기 작업을 검토하게 하면 얻는 것이 거의 없습니다. 버그를 만든 [세션](./session.md)에는 그것을 만든 추론도 들어 있고, 에이전트는 자신의 결론을 확인으로 다시 읽습니다. 새 [컨텍스트 창](./context-window.md)을 가진 검토자는 그런 애착이 없어서 낯선 사람처럼 diff를 봅니다. 검토가 의존하는 것이 바로 그것입니다. 다른 모델이나 검토 전용 시스템 프롬프트는 이를 더 날카롭게 합니다. 사각지대가 다르고, 시스템 프롬프트를 막연한 "문제를 찾아라"가 아니라 실제로 신경 쓰는 것(보안, API 계약, 성능)으로 좁힐 수 있습니다.

다른 검토 계층 사이에 놓입니다. 자동 검사는 결정적이며 기계적으로 단언할 수 있는 것을 잡고, [사람의 검토](./human-review.md)는 비싸고 확장성이 가장 나쁩니다. 자동 리뷰는 중간에 있습니다. 오해를 부르는 함수 이름이나 놓친 엣지 케이스처럼 판단이 필요한 문제를 기계 비용으로 잡습니다. 비결정적이므로 놓치거나 문제가 아닌 것을 지적할 수 있습니다. 사람을 대체하는 관문이 아니라 사람이 보기 전에 바닥을 끌어올리는 필터로 다루세요.

_피할 표현:_ "AI 리뷰" / "에이전트 리뷰": 작업하는 에이전트 자신과 구분하기에는 너무 모호합니다.

_사용 예:_

"[AFK](./afk.md) 실행에서 나쁜 PR이 너무 많이 나와요."

"병합 전에 자동 리뷰 단계를 추가하세요. 다른 모델에 별도의 시스템 프롬프트로, 보안과 계약 변경으로 범위를 좁혀서요."
