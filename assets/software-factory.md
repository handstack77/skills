# 소프트웨어 팩토리 (Software factory)

> 작업 패턴

사람이 아니라 트리거가 에이전트 세션을 시작하는 작업 체계. 더 많은 작업이 AFK로 돌고 HITL 시간은 필요한 곳에 남겨 둡니다.

[에이전트](./agent.md) [세션](./session.md)을 사람이 아니라 트리거가 시작하는 작업 체계입니다. 이슈 생성, 일정, CI 실패, 다른 세션의 종료 같은 것이 트리거입니다. 그래서 더 많은 작업이 [AFK](./afk.md)로 돌고, 사람의 주의는 남아 있는 [사람이 개입하는](./human-in-the-loop.md) 결정에 쓰입니다.

팩토리가 없으면 모든 세션은 누군가 시작했기 때문에 시작됩니다. 완전히 AFK인 작업도 사람이 세션을 열고, [티켓](./ticket.md)을 가리키고, 출발시키기를 기다립니다. 팀은 그것이 허용하는 것보다 더 많이 출시하고 싶어 합니다. 팩토리는 세션을 시작하는 일에서 사람을 빼는 것이지, 반드시 다른 모든 것에서 빼는 것은 아닙니다.

흔한 트리거와 그것이 시작하는 세션:

| 트리거 | 시작하는 세션 | 예 |
| --- | --- | --- |
| 이슈 생성 또는 라벨 부여 | 탐색, 버그 수정, 구현 | `ready-for-agent` 라벨이 붙은 이슈가 PR을 여는 세션을 얻음 |
| 일정(cron) | 반복적인 유지보수 | 밤마다 린트 규칙 하나 수정 |
| CI 실패 또는 모니터링 경보 | 진단, 수정 시도 | main의 빌드 실패가 깨뜨린 커밋을 찾아 수정을 제안하는 세션을 얻음 |
| 다른 세션의 종료 | 후속 작업 | 한 에이전트가 연 PR이 [자동 리뷰](./automated-review.md)를 촉발하고, 그 코멘트가 수정 세션을 촉발 |

팩토리가 소프트웨어 프로세스 전체를 덮을 필요는 없습니다. 한 종류의 세션을 돌려 검토 가능한 PR 하나를 여는 cron 작업 하나도 팩토리입니다. 그렇게 작게 시작하는 것이 유용합니다. 좁은 루프는 작고 비슷한 PR을 만들고, 그것을 검토하면 루프를 넓히기 전에 얼마나 믿을 수 있는지 알 수 있습니다.

사람은 팩토리의 어디에나 있을 수 있습니다. 세션을 촉발하는 이슈를 쓰고 라벨을 붙이고, 구현이 시작되기 전에 계획을 승인하고, 병합 전에 [사람의 검토](./human-review.md)를 합니다. 이 결정 중 무엇을 사람에게 남길지가 주된 설계 질문입니다. 팩토리의 출력을 사람이 검토하지 않는 코드베이스, 또는 그 일부는 [다크 팩토리](./dark-factory.md)입니다.

_사용 예:_

"`no-floating-promises` 위반을 누가 다 고쳤죠?"

"팩토리요. cron 작업이 밤마다 린트 규칙 하나를 골라 PR을 열어요. 저는 아침에 검토만 합니다."
