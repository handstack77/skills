# 티켓으로

## 기능 설명

`to-tickets`는 계획, [사양](./spec.md), 또는 당신이 참여 중인 대화를 받아서, 이를 이슈 트래커 상의 **[티켓들](./ticket.md)** 집합으로 나눕니다. 각 티켓은 자신이 시작되기 전에 완료되어야 하는 다른 티켓들을 나타내는 **차단 엣지(blocking edges)**를 선언합니다.

모든 티켓은 **추적 탄환(tracer bullet)** 입니다: 변경의 모든 계층(스키마, API, UI, 테스트)을 통과하는 좁지만 완전한 경로로, 티켓이 배포되자마자 단독으로 시연할 수 있습니다. 이것이 작업을 나누는 명백한 방식과 다른 점인데, 명백한 방식은 한 번에 한 계층씩 잘라 마무리 시 통합하는 것입니다. 또한 각 티켓의 크기를 단일 새로운 [컨텍스트 창](./context-window.md)에 맞추어 조정합니다. 이는 당신의 명세를 한 번도 본 적 없는 [세션](./session.md)이 티켓을 바로 이해할 수 있도록 합니다.

## 언제 사용하는지

이것은 `/to-tickets`를 입력하여 호출합니다. [에이전트](./agent.md)가 스스로 사용하지는 않습니다.

| 위치 | 실행할 항목 |

| --- | --- |
| 당신은 사양 문제가 있으며 빌드는 여러 세션에 걸쳐 있습니다 | `/to-tickets`, 또는 `/to-tickets #` |

| 계획은 대화에서만 있으며, 문서화되지 않았습니다 | `/to-tickets`는 스레드를 직접 읽으며, 사양이 필요 없습니다 |

| 전체 변경 사항이 하나의 컨텍스트 창에 들어맞습니다 | [구현](./skills-implement.md), 티켓은 건너뜁니다 |
| 아직 아무것도 결정되지 않음 | [문서와 함께 그릴](./skills-grill-with-docs.md), 그다음 [사양으로](./skills-to-spec.md) |

| [웨이파인더](./skills-wayfinder.md) 지도가 정리됨 | 먼저 [사양으로](./skills-to-spec.md), 지도를 축소하고, 그다음 `/to-tickets` |

`to-tickets`가 생성한 티켓은 구조상 에이전트 준비가 되어 있습니다. 그 위에 [트라이애지](./skills-triage.md)를 실행하지 마세요. 트라이애지는 다른 사람에게서 온 작업에 사용됩니다.

## 사전 조건

`to-tickets`는 트래커에 게시하므로, [setup-me-skills](../docs/engineering/setup-me-skills.md)에서 이 저장소를 위한 트래커와 함께 분류 라벨 어휘를 설정해야 합니다. 실제 트래커(GitHub 또는 Linear)든, 추가 설정이 필요 없는 `.scratch/` 하위의 로컬 마크다운 파일이든 어느 쪽이든 작동합니다.

## Tracer bullets, not layers

**수평** 슬라이스는 변화의 한 층을 배포합니다. 모든 층이 도착할 때까지 아무 것도 작동하지 않으며, 각 티켓의 수용 기준은 다른 티켓이 담당하는 작업까지 포함해야 합니다. **수직** 슬라이스(추적 총알)는 모든 층을 한 번에 통과하는 얇은 경로를 배포하므로, 단독으로 검증 가능하며 그것이 평가하는 모든 것을 소유합니다.

이것은 사람들이 가장 자주 깨는 규칙입니다. 한 팀은 26티켓 스택을 계층별(코퍼스, 프로듀서, 애그리게이터, 셀렉터)로 나눠 실행했고, 닫힌 티켓당 대략 20회의 에이전트 실행을 얻었으며, 그중 약 3분의 2는 재작업이었습니다. 그들의 자체 사후 분석은 모든 실패 유형을 구현이 아닌 수평적 분할 때문이라고 추적했습니다.

무엇이든 발행되기 전에 두 가지 일이 일어난다. `to-tickets`는 사전 리팩토링(원칙: '변경을 쉽게 만든 다음, 쉬운 변경을 한다')을 찾고 먼저 그 작업을 지시한다. 그런 다음 분해 내용을 번호 매겨진 목록으로 제시하고 당신에게 질문한다: 세분화가 적절한가, 차단 요소가 실제로 있는가, 합치거나 분리할 것이 있는가. 당신이 승인할 때까지 아무것도 추적기로 넘어가지 않으며, 그 퀴즈가 반박할 기회를 제공하는 장소다.

## 블로킹 엣지

엣지는 유물의 핵심 지점입니다. 이는 추적기에 따라 두 가지 방식으로 작동합니다:

| 추적기 | 엣지가 위치한 곳 | 작동 방식 |

| --- | --- | --- |
| 로컬 마크다운 | `.scratch//issues/-.md` 아래 티켓별 한 파일에 텍스트, 블로커 순 번호 매기기 | 위에서 아래로, 수작업 |

| 실제 트래커 (GitHub, Linear) | 원래 블로킹 링크 또는 트래커에 서브 이슈가 있는 경우 | 블로커가 완료된 모든 티켓은 **전선(frontier)** 에 있으며 가져갈 수 있음 |

모서리는 어쨌든 티켓 안에 존재합니다. 트래커는 오직 어떤 것이 병렬로 작동할 수 있는지만 결정합니다. `to-tickets`는 아티팩트를 생성합니다; 이를 실행하는 것(한 번에 한 세션이든, 여러 대든)은 스킬의 일이 아니라 당신의 일입니다.

## 광범위 리팩터 예외

한 가지 형태가 추적-총알 규칙을 깨뜨린다. **광범위 리팩터**는 단일 기계적 변경(열 이름 변경, 공유 심볼 재타입)으로, 그 **파급 범위**가 전체 코드베이스를 덮는다. 하나의 편집으로 수천 개의 호출 지점이 깨져서, 수직 슬라이스는 녹색으로 표시될 수 없다.

`to-tickets` 시퀀스는 대신 **확장–축소**처럼 동작한다:

- **확장**: 아무 것도 깨지지 않도록 기존 옆에 새 폼을 추가합니다.

- **이전**: 호출 지점을 블래스트 반경에 따라 일괄적으로(패키지별, 디렉터리별) 이동하고, 배치당 하나의 티켓을 만들며, 각 티켓은 확장 단계에 의해 차단됩니다. CI는 기존 폼이 여전히 존재하기 때문에 녹색 상태를 유지합니다.

- **계약**: 호출자가 더 이상 남아 있지 않으면 이전 양식을 삭제하며, 모든 마이그레이션 배치에 의해 차단된 티켓 내에서 수행합니다.

배치조차 혼자서 초록색 상태를 유지할 수 없는 경우, 통합 브랜치를 공유하고 모두 최종 통합 및 검증 티켓을 차단합니다. CI는 해당 티켓에서만 초록색이면 됩니다.

## 자주 묻는 질문

**3줄 변경에 대해 12개의 티켓을 생성했습니다.**
과도한 분해는 이 기술에서 가장 많이 보고되는 문제이며, 많은 사용자들이 이를 경험합니다. [모델](./model.md)은 기본적으로 원자 단위로 설정되어 있어 의미 있게 만들 수 있는 그룹화가 사라집니다. 퀴즈 단계에서 이를 수정할 수 있습니다. 티켓을 병합하도록 요청하면 그렇게 됩니다. 또한 하한이 있습니다. 전체 변경 사항이 하나의 컨텍스트 창에 들어맞는다면, 이 기술은 전혀 필요하지 않습니다. 바로 [구현](./skills-implement.md)으로 가세요.

**티켓은 한 레이어당 하나씩 나왔습니다: 모든 스키마는 한 장에, 모든 API는 다른 한 장에.**
이것은 세로-슬라이스 규칙이 만들어진 실패 사례이며, 이 스킬이 가끔 이것을 여전히 발생시킵니다. 퀴즈 단계에서 티켓당 하나의 질문을 하여 그것을 잡아낼 수 있습니다: 이것이 완료되면 무엇을 시연할 수 있습니까? 답변이 없는 티켓은 가로 슬라이스입니다. 일부 사람들은 이러한 이유로 각 티켓에 '시연 경로' 라인을 추가하며, 이것이 모델을 세로 슬라이스로 이끄는 데 도움이 된다고 보고합니다.

**GitHub에서는 티켓이 사양 이슈의 하위 이슈로 생성되지 않았습니다.**
이 문제는 여러 번의 실행과 여러 모델에서 보고되었으며, 대부분은 이슈 #554에서 자세히 다루어졌습니다. 수정 사항: `to-tickets`는 이제 각 티켓을 해당 소스 이슈의 하위 이슈로 만들며, GitHub 트래커 템플릿은 명령어(`gh issue create --parent `, `gh` 2.94+)를 제공합니다. 오래된 `docs/agents/issue-tracker.md`를 새로 고치려면 [setup-me-skills](../docs/engineering/setup-me-skills.md)를 다시 실행하세요.

**실제 차단 링크 대신 문제 본문에 '차단됨'이라고 작성되었습니다.**
이것은 문제 #513에서 보고된 것과 같은 종류의 문제로, 에이전트조차 GitHub에는 기본 차단 관계가 전혀 없다고 언급했습니다. 하지만 존재합니다: `gh issue create --blocked-by 12,15`. 스킬이 먼저 차단자를 게시하기 때문에, 생성 시에 항상 그 수치가 사용 가능합니다. 본문 텍스트는 기본값이 아니라, 기본 엣지가 없는 트래커를 위한 백업용입니다. 이제 티켓 템플릿은 엣지가 기본인 경우 `## Blocked by`를 생략합니다.

**로컬 티켓은 어디로 가나요? v1.1 노트에는 루트 수준 `tickets.md`라고 되어 있었습니다.**
그들은 그랬고, 그것은 버그였습니다. 단일 공유 파일은 병렬 에이전트가 작성할 때 경쟁 조건을 발생시키기도 했습니다. 로컬 모드는 이제 `.scratch//issues/-.md` 아래 티켓별로 한 파일씩 의존성 순서대로 작성하며, 이는 로컬 추적기 템플릿이 이미 설명한 레이아웃과 일치합니다. `NN` 접두사는 실제 티켓 ID이므로, 긴 제목을 다시 입력하는 대신 `/implement 03`를 사용할 수 있습니다.

**내 사양을 읽으려고 할 때 계속 잘렸습니다.**
매우 큰 스펙은 트래커 이슈가 깔끔하게 반환하는 것을 능가할 수 있습니다. 참고할 로컬 사본이 없기 때문에 에이전트는 [도구 호출](./tool-call.md)을 반복해서 가져오며 끝에 도달하지 못합니다. `/to-spec`와 `/to-tickets` 사이에서 [지우기](./clearing.md)나 [압축](./compaction.md)을 하지 마십시오. 동일한 컨텍스트 창에서 실행하면 에이전트는 스펙을 다시 가져올 필요가 없습니다.

**수용 기준은 아무것도 평가하지 않았다: 일부는 작업이 시작되기도 전에 통과했다.**
템플릿은 기준을 요구하고 그것들이 실패할 수 있는지에 대해서는 아무 언급이 없기 때문에 이런 일이 발생합니다. 세 가지 형태가 반복됩니다: 기본 커밋에서 이미 참인 기준, 다른 티켓에서만 수행되는 작업으로 충족될 수 있는 기준, 산출물에서 유도되지 않고 요청을 재진술하는 기준입니다. 수직 분할은 대부분을 방지합니다. 왜냐하면 새로운 동작을 제공하는 분할은 설계상 기본 커밋에서 실패하기 때문입니다. 검사는 여전히 수작업으로 수행할 가치가 있습니다. 각 기준마다 그것이 거짓임을 보여주는 관찰을 명시하고, 구현자가 시작하는 커밋에서 실패하는지 확인하세요.

**티켓이 발행되었습니다. 실제로 어떻게 실행하나요?**
이 기술은 아티팩트에서 멈추며, 자동 디스패치 모드는 없습니다. 디스패치는 수동입니다: 보드를 보고, 열린 차단이 없는 티켓 수를 세고, 그만큼 에이전트 세션을 엽니다. 각 티켓에 새로운 컨텍스트를 부여하고, 그 사이를 초기화합니다. [implement](./skills-implement.md)는 완료 시 GitHub이나 로컬 마크다운에서 티켓을 신뢰성 있게 닫거나 체크하지 않으므로, 티켓 상태를 스스로 업데이트해야 합니다.

## 작동 중이라면

- 모든 티켓에는 "이것이 완료되면 무엇을 데모할 수 있나요?"에 대한 답이 있으며, 답은 계층이 아니라 동작입니다.

- 목록은 번호가 매겨진 상태로 돌아오며, 게시되기 전 각 항목에 "Blocked by" 줄이 있습니다.

- 맨 위에 있는 티켓은 막혀있는 것이 없어서 바로 시작할 수 있습니다.

- 티켓 내용에는 프로토타입이 생성한 코드 스니펫을 제외하고는 파일 경로나 줄 번호가 없습니다.

- 각 티켓은 새로운 세션이 방 안에 없이도 완료할 수 있을 것처럼 읽힙니다.

- 사전 리팩토링(prefactoring)이 있는 경우, 기능 티켓과 섞이지 않고 순서의 앞부분에 있습니다.

## 적합한 위치

`to-tickets`는 주요 빌드 체인의 한 단계입니다:

```text
grill-with-docs → to-spec → to-tickets → implement → code-review → retro
```

업스트림은 [to-spec](./skills-to-spec.md)으로, 이는 슬라이스를 위해 정해진 스펙을 전달합니다. 두 가지를 모두 하나의 컨텍스트 창에 두되, 그 사이에 clear는 없습니다. 다운스트림은 [implement](./skills-implement.md)으로, 새로운 세션마다 하나의 티켓을 만들고 테스트를 위해 [tdd](./skills-tdd.md)를 진행하며 [code-review](./skills-code-review.md)로 종료합니다. [implement-spec](./skills-implement-spec.md)는 반대 방향입니다. 이는 작업 그래프와 동일한 블로킹 엣지를 읽고, 준비된 모든 티켓을 하나의 통합 브랜치에서 병렬로 구축합니다. 어떤 스킬이나 흐름이 적합할지 확실하지 않을 때는, [ask-me](./skills-ask-me.md)가 안내합니다.
