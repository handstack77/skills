# 명세 (Spec)

> 핸드오프

여러 세션에 걸친 작업을 설명하는 핸드오프 산출물. 무엇을 만드는지를 담고, 각 세션이 자기 몫을 어떻게 하는지는 담지 않습니다. 티켓으로 이루어집니다.

여러 [세션](./session.md)에 걸친 작업을 설명하는 [핸드오프 산출물](./handoff-artifact.md)입니다. 무엇을 만드는지를 담고, 각 세션이 자기 몫을 어떻게 하는지는 담지 않습니다. 작업이 진행되면서 바뀝니다. [티켓](./ticket.md)으로 이루어집니다.

명세가 있는 이유는 세션은 일회용이지만 큰 작업은 그렇지 않기 때문입니다. [컨텍스트 창](./context-window.md) 하나 분량 이상의 노력이 드는 것은 무엇이든 [컨텍스트](./context.md) 밖에 둘 곳이 필요합니다. 저장소의 파일이든, GitHub 이슈든, 에이전트가 닿는 이슈 트래커든, 에이전트의 [환경](./environment.md) 안에서 [비우기](./clearing.md)를 견디는 어딘가입니다. 명세가 바로 그 집입니다. 목표, 제약, 지금까지 내린 결정, 상태가 달린 티켓 목록. 새 세션은 어느 것이든 이를 읽고 이전 세션이 쌓은 잡음을 물려받지 않은 채 작업이 어디까지 왔는지 알 수 있습니다.

명세는 알아볼 수 있는 스타일로 나오며, 대부분 팀이 이미 기록하던 방식에서 물려받습니다. _제품 요구사항 문서_(PRD)는 사용자 쪽의 무엇과 왜, 곧 기능, 동작, 인수 기준에 기웁니다. _설계 문서_나 _RFC_는 기술 쪽으로 기울어, 선택한 접근, 기각한 대안, 트레이드오프를 담습니다. 작은 쪽에서는 티켓 체크리스트가 있는 평범한 `plan.md`가 여러 세션에 걸친 기능에 같은 역할을 합니다. 스타일보다 역할이 중요합니다. [에이전트](./agent.md)에게 이것들은 모두 같은 것입니다. 매 세션 시작 때 읽는, 의도에 대한 지속적인 진술입니다.

_사용 예:_

"이걸 전부 한 세션에서 해도 될까요?"

"아니요, 명세로 써서 티켓으로 나누고 각각을 자기 세션에서 실행하세요. 전체를 하나의 컨텍스트에서 하려 하면 절반도 가기 전에 [바보 구간](./smart-zone.md)에 들어갑니다."
