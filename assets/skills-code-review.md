# 코드 리뷰

## 무엇을 하는지

`code-review`는 `HEAD`와 사용자가 지정한 고정 지점(커밋, 브랜치, 태그, `main`, `HEAD~5`) 사이의 차이를 두 축으로 검토합니다. **Standards**는 코드가 이 저장소에서 코드를 작성하는 방식에 따라 작성되었는지를 묻습니다. **Spec**는 코드가 원래 문제나 [명세](./spec.md)가 요구한 대로 작동하는지를 묻습니다. 각 축은 자체 [하위 에이전트](./subagent.md)에서 실행되므로 서로의 추론을 보지 못합니다.

이 스킬은 두 축을 결합하거나 재순위화하지 않습니다. 보고서는 각 축별 최악의 문제로 종료되며, 이들 중 단일 승자를 지정하지 않습니다. 변경 사항은 한 축에서 통과하고 다른 축에서는 실패할 수 있습니다. 모든 규칙을 따르지만 잘못된 기능을 구현한 코드는 표준에서는 통과하고 명세에서는 실패합니다. [티켓](./ticket.md)에서 요청한 정확한 작업을 수행하지만 저장소의 규칙을 위반한 코드는 그 반대입니다. 혼합된 평결은 통과한 축이 실패한 축을 숨기게 합니다.

## 언제 집으면 좋을까

`/code-review`를 입력하거나, 브랜치, PR, 진행 중인 작업을 검토하거나 'X 이후'의 모든 항목을 요청하면 에이전트가 자동으로 집습니다.

| 당신의 상황 | 집으세요 |

| --- | --- |

| 차이가 존재하며 그것이 올바르게 구축되었는지 *그리고* 올바른 것인지 알고 싶습니다 | `code-review` |

| 차이에서 버그를 찾고 싶습니다: null 경로, 경쟁 상태, off-by-one | Claude Code 자체 내장 리뷰, 이 리뷰가 아닙니다 (아래 이름 충돌 참조) |

| 아직 작성된 것이 없으며 테스트 우선으로 작성되길 원합니다 | [tdd](./skills-tdd.md) |
| 전체 스펙이 작성되어야 하며, 리뷰도 포함됨 | [구현](./skills-implement.md), 이 기능을 직접 호출함 |

| 전체 코드베이스가 흩어져 있으며, 단 하나의 차이도 없음 | [코드베이스 아키텍처 개선](./skills-improve-codebase-architecture.md) |

| 무언가 고장났지만 이유를 모름 | [버그 진단](./skills-diagnosing-bugs.md) |

고정 지점을 반드시 제공해야 합니다. 제공하지 않으면, 스킬이 추측하는 대신 하나를 요청합니다. 무언가를 생성하기 전에 참조가 해결되는지, 그리고 차이가 비어 있지 않은지 확인하므로, 잘못 입력된 브랜치 이름은 두 하위 에이전트 내에서가 아니라 사용자 앞에서 실패합니다.

## 전제 조건

Standards 축은 아무것도 필요하지 않습니다. 그것은 저장소 문서(`CODING_STANDARDS.md`, `CONTRIBUTING.md` 등)를 읽고, 저장소에 문서가 없으면 내장 기준선으로 돌아갑니다.

Spec 축은 명세가 존재하고 찾을 수 있어야 합니다. 그것은 다음 순서로 확인합니다:

- 커밋 메시지에서 이슈 참조(`#123`, `Closes #45`, GitLab `!67`), 트래커 문서를 통해 가져옴.

- 인자로 전달하는 경로.

- 브랜치나 기능 이름과 일치하는 `docs/`, `specs/`, 또는 `.scratch/` 아래의 스펙 파일.

- 당신에게 묻는 것.

1단계는 [setup-me-skills](../docs/engineering/setup-me-skills.md)에서 작성한 트래커 문서에 따라 달라집니다. 문서가 없더라도 경로를 지정하면 축은 여전히 작동합니다. 사양이 전혀 없으면, 스킬은 Spec 하위 에이전트를 건너뛰고 보고서에는 요구사항을 만들어내는 대신 "사용 가능한 사양이 없음"이라고 표시됩니다.

## 두 개의 축

| 표준 | 사양 |

| --- | --- | --- |

| 질문 | 제대로 만들어졌는가? | 올바른 것인가? |

| 참고 | 저장소의 문서화된 표준, 그리고 냄새 기준선 | 원본 이슈 또는 사양 |
| 보고서 | 문서화된 위반 사항(어려울 수 있음) 및 냄새(항상 판단이 필요함) | 누락되거나 부분적인 요구사항, 범위 확장, 잘못 구현된 요구사항 |

| 모든 발견 사항에 인용 | 표준 파일과 규칙, 또는 명명된 냄새와 해당 부분 | 명세서의 줄 |

이 설계는 귀하의 기준을 알지 못하는 일반적인 검토 기술을 피하기 위해 존재합니다. 이러한 기술은 코드베이스에서 의도된 부분을 표시하고 코드베이스가 의존하는 불변 조건을 놓칩니다. 따라서 리포지토리 자체 문서는 Standards 축에서 [주요 출처](./primary-source.md)이며, **리포지토리가 항상 우선합니다**.

**냄새 기준(smell baseline)**은 저장소(repo)의 기준 아래에 위치합니다. 이는 Fowler의 *Refactoring* 3장에서 나온 12가지 코드 냄새로 구성되어 있습니다: Mysterious Name, Duplicated Code, Feature Envy, Data Clumps, Primitive Obsession, Repeated Switches, Shotgun Surgery, Divergent Change, Speculative Generality, Message Chains, Middle Man, Refused Bequest. 각각은 명확한 위반이 아닌 라벨이 붙은 휴리스틱("가능한 Feature Envy")입니다. 각각은 냄새가 무엇인지와 이를 어떻게 수정할지 설명하므로, 발견되는 문제에는 단순 불만만 있는 것이 아니라 해결 방법이 함께 제공됩니다. 두 축(axes) 모두 이미 린터가 강제하는 사항은 건너뜁니다.

## 자주 묻는 질문

**그것이 Claude Code 자체의 `/code-review`와 충돌합니다. 어떻게 해야 하나요?**

로컬 `code-review` 스킬은 Claude Code의 같은 이름 내장 스킬보다 우선할 수 있습니다. 이 문서의 리뷰는 저장소 표준과 명세 준수를 확인합니다. Claude Code에서는 `/code-review`, Codex CLI에서는 `$code-review`로 요청하고, 로드한 파일이 이 저장소의 `skills/engineering/code-review/SKILL.md`인지 확인하세요. 이름을 따로 쓰려면 원본 폴더와 `SKILL.md`의 `name`을 함께 바꾸고 연결을 다시 설정하세요.

**그 하위 에이전트들은 계속 `/code-review`를 호출하고 더 많은 에이전트를 생성합니다.**

이것은 알려진 오픈 버그입니다. 여러 사람들이 여러 하네스에서 이를 재현했습니다. 표준 및 스펙 프롬프트는 위임을 금지하지 않으므로, 서브 에이전트가 스킬을 다시 찾고 다시 확산할 수 있습니다. 한 보고서는 50개 이상의 에이전트에 도달했습니다. 포크에서 사람들이 적용한 수정은 두 서브 에이전트 브리핑에 한 줄을 추가하는 것입니다: "`/code-review`를 호출하거나 추가 에이전트를 생성하지 말고: 이 검토를 직접 수행하십시오." 일부는 모든 스킬이 이 보호를 상속받도록 하네스 수준에서 처리하는 것을 선호합니다. 그러나 어느 것도 아직 배송된 스킬에는 포함되지 않았습니다. 무인으로 실행할 경우, 에이전트 수를 주의해서 보십시오.

**코드를 작성한 동일한 [세션](./session.md)에서 실행해야 하나요?**

신선한 것을 선호하세요. 한 독자가 말하길: "같은 맥락에서 자신을 검토하는 것은 검토가 아니라 슬래시 명령어와 함께하는 확인 편향입니다." 작성 세션에서 검토하는 에이전트는 코드의 맥락을 형성한 모든 가정을 갖고 있습니다. 반면, 독립적인 검토자는 그 맥락을 가지지 않습니다. 이것이 사람들이 내장된 검토 단계 없이 [구현](./skills-implement.md)을 요청하는 이유이기도 합니다. 왜냐하면 그 단계는 방금 변경 사항을 작성한 세션 내에서 검토를 실행하기 때문입니다. 독립적인 버전은 깨끗한 세션에서 직접 `/code-review`를 호출하는 것입니다.

**매 티켓 후에, 아니면 마지막에 한 번?**

둘 다 작동하며, 기술이 대신 결정하지 않습니다. 티켓별로 하면 각 차이가 충분히 작아서 Spec 축에서 확인할 단일 스펙이 생기며, 이는 `implement`가 사용하는 모드입니다. 브랜치 끝까지 배치하면 티켓별로는 놓치는 상호작용을 포착할 수 있습니다. 확실하지 않으면 티켓별로 검토하고 브랜치 포인트에 대해 마지막 한 번 실행하세요.

**내가 그 결과를 신뢰할 수 있을까?**

확인하지 않고는 안 됩니다. 서브 에이전트 출력은 가설일 뿐 증거가 아닙니다. 한 팀은 산문 기반 리뷰에서 놓친 12건의 파괴적 변경을 보고했습니다. 이 기술은 두 보고서를 그대로 또는 약간 정리하여 결합합니다. 각 주장을 파일과 재검증하지 않기 때문에, 특정 결과가 잘못된 위치를 인용하거나 영향을 과장할 수 있습니다. 행동을 취하기 전에 각 결과의 인용을 읽으십시오. 이 기술은 모든 결과가 인용을 포함하도록 요구하며(표준 규칙, 냄새와 그 부분, 또는 사양 라인), 이것이 결과를 검증 가능하게 만드는 요소입니다.

**왜 매번 실행할 때마다 새로운 문제를 발견하는 걸까요?**

각 수정은 리뷰할 새로운 코드를 추가하며, Standards 축의 판단이 필요한 부분은 실행할 때마다 다른 결과를 제공합니다. 한 독자는 이 루프를 이렇게 설명했습니다: "/code-review와 /improve-code-architecture는 매번 새로운 것을 발견합니다. 나는 수정을 구현하고, 이 도구들을 다시 실행하며, 계속 반복합니다." 수렴을 보장하지 않습니다. 통과를 잠재적 리드 목록으로 취급하세요. 뒤에 규칙이 있는 항목만 실행한 후 중지하세요. 깨끗해질 때까지 루프에서 실행하지 마세요. 절대 깨끗해지지 않기 때문입니다.

**내 커밋되지 않은 작업을 검토하나요?**

아니요. 그것은 `...HEAD`와 비교합니다. 세 점 형식은 병합 기준을 기준으로 측정하며, 스테이징된 변경사항과 작업 디렉토리 변경사항은 제외합니다. 만약 `implement`가 중간 커밋을 하지 않았다면, 검토는 다음 커밋에 들어갈 작업을 볼 수 없습니다. 먼저 커밋한 후, 검토하고, 그 다음 수정이나 수정을 추가하세요.

## 작동 중

- 서브 에이전트가 생성되기 전에 잘못된 참조나 빈 diff에서는 시작을 거부합니다.

- 리포트는 하나로 병합된 목록이 아니라 `## Standards`와 `## Spec` 아래 두 개의 별도 블록으로 도착합니다.

- 모든 Standards 결과는 리포지토리 파일 중 하나의 규칙이거나 12가지 스멜 중 하나를 이름으로 지정하며, 해당 코드 덩어리를 인용합니다; 모든 Spec 결과는 스펙의 한 줄을 인용합니다.

- 마지막 요약은 축별 최악 문제를 제시하며 전체 우승자를 선정하지 않습니다.

- 사용 가능한 사양이 없으면, Spec 블록은 코드에서 추론한 요구사항을 나열하는 대신 그렇게 표시합니다.

## 적합한 위치

`code-review`는 빌드 체인의 끝 부분에 가까운 검토 단계입니다: `grill-with-docs → to-spec → to-tickets → implement → code-review → retro`. 또한 당신이 지정하는 모든 브랜치나 PR에서 독립적으로 존재합니다.

- [implement](./skills-implement.md)는 가장 가까운 이웃입니다. 이것은 빌드를 실행하고 커밋하기 전에 고유한 클로징 리뷰로 이 기능을 호출합니다. [implement-spec](./skills-implement-spec.md)는 전체 통합 브랜치에서 한 번 동일한 작업을 수행합니다.

- [retro](./skills-retro.md)는 그 뒤를 이어 조정합니다. 세션에서 리뷰가 특정 유형의 실수를 놓친 것으로 나타나면, `retro`가 점검을 제안하거나 `CODING_STANDARDS.md` 규칙을 제안한 후 Standards 축을 읽습니다.

- [pr](./skills-pr.md)는 검토된 작업이 올라가면 풀 리퀘스트 본문을 작성합니다.

- [to-spec](./skills-to-spec.md)와 [to-tickets](./skills-to-tickets.md)는 Spec 축이 확인하는 문서를 생성하므로, 모호한 스펙은 해당 축도 모호하게 만듭니다.

- [improve-codebase-architecture](./skills-improve-codebase-architecture.md)는 전체 코드베이스에 해당하는 counterpart입니다. 이 스킬은 하나의 diff만 보기 때문입니다.

[ask-me](./skills-ask-me.md)은 상황에서 어떤 기술이 필요한지 확실하지 않을 때 전체 세트를 통해 경로를 안내합니다.
