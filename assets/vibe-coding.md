# 바이브 코딩 (Vibe coding)

> 작업 패턴

사용자가 사람의 검토 없이 에이전트의 코드를 받아들이는 작업 방식. diff를 불투명하게 취급합니다.

사용자가 [사람의 검토](./human-review.md) 없이 [에이전트](./agent.md)의 코드를 받아들이는 작업 방식입니다. diff를 불투명하게 취급합니다. 중요한 것은 프로그램이 동작하느냐이지 안에 무엇이 있느냐가 아닙니다. [자동 리뷰](./automated-review.md)와 [자동 검사](./automated-check.md)는 여전히 돌 수 있으며, 바이브 코딩은 둘에 대해 말이 없습니다.

이 용어는 Andrej Karpathy에게서 왔고, [2025년 초에 만들었습니다](https://x.com/karpathy/status/1886192184808149383). "분위기에 완전히 몸을 맡기고" "코드가 존재한다는 것조차 잊는" 것입니다. 원하는 것을 설명하고, 돌아온 것을 받아들이고, 실행해 보고 판단합니다.

바이브 코딩은 검사를 속도와 맞바꿉니다. 에이전트 주도 작업에서 diff를 읽는 것이 보통 가장 느린 단계이므로, 그것을 버리면 주된 병목이 사라집니다. 실패 비용이 싼 코드, 곧 [프로토타입](./prototyping.md), 일회용 스크립트, 사내 도구라면 합리적인 거래입니다. 위험은 코드의 수명과 이해관계에 비례해 커집니다.

비용은 나중에 도착합니다. 바이브 코딩한 변경이 쌓여 아무도 읽지 않은 코드베이스가 되고, 확인된 것은 동작뿐이었습니다. 그래서 로그에 기록된 비밀, 빠진 엣지 케이스, 조용히 틀린 데이터 처리처럼 동작이 드러내지 않는 것은 눈에 띄지 않은 채 출시됩니다. 누군가 시스템을 처음 디버깅할 때가 누군가 코드를 처음 읽는 때입니다. 사람의 검토가 없으면 여전히 도는 자동 검증(테스트, 타입, 자동 리뷰)이 코드가 통과하는 유일한 관문입니다. 같은 태도를 [소프트웨어 팩토리](./software-factory.md)에서 변경이 나오는 코드베이스 전체나 일부에 적용한 것이 [다크 팩토리](./dark-factory.md)입니다.

_피할 표현:_ "저품질 AI 코딩"의 동의어로 쓰는 "바이브 코딩". 이 용어는 결과 코드가 아니라 검토 태도를 가리킵니다.

_사용 예:_

"인증 흐름에서 바뀐 것을 읽어 봤어요?"

"바이브 코딩으로 했어요. 로그인은 여전히 되고, 확인한 건 그게 다예요."

"푸시하기 전에 diff를 읽으세요. 인증을 분위기로 짜면 비밀이 로그로 새게 됩니다."
