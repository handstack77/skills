#

## 무엇을 하는가

`implement`는 이미 결정된 작업을 수행합니다. 이를 [티켓](./ticket.md), [스펙](./spec.md), 또는 대화에서 방금 합의한 계획에 맞추면 코드를 작성하고, 접합부에서 [TDD](./skills-tdd.md)를 수행하며, 진행하면서 타입 체크를 하고, 마지막에는 [코드 리뷰](./skills-code-review.md)를 실행한 후 현재 브랜치에 커밋합니다.

계획을 다시 열지 않습니다. 인터뷰도 없고, 명확히 하는 과정도 없으며, 다른 접근 방식을 제안하지도 않습니다. 상류에서 결정된 것이 입력이며, 스킬의 전체 임무는 그것을 커밋으로 바꾸는 것입니다. 이것이 종종 작업을 재설계하면서 실행하는 신선한 [에이전트](./agent.md)에서 '이거 만들어'라고 입력하는 것과 구별되는 점입니다.

## 언제 사용하는지

당신은 `/implement`를 직접 입력함으로써 이를 호출하며, 에이전트가 스스로 이를 사용하지는 않습니다. 이것은 `disable-model-invocation: true`와 함께 제공되므로, 다른 어떤 기능도 이를 호출할 수 없습니다. [ask-me](./skills-ask-me.md)이나 [to-tickets](./skills-to-tickets.md)에서 'then `/implement` per ticket'라고 말하는 곳은 에이전트가 스스로 실행할 지시가 아니라, 당신에게 주어진 지침입니다.

작업이 현재 위치한 곳이 이 기술이 적합한지 여부를 결정합니다:

| 작업은… | 도달하기 |

| --- | --- |

| 트래커의 티켓 | `/implement #42`, 세션마다 한 티켓, 티켓 간에 컨텍스트 [정리](./clearing.md) |
| 아직 나뉘지 않은 스펙이며, 빌드는 여러 세션에 걸쳐 있습니다 | 먼저 [to-tickets](./skills-to-tickets.md), 그 다음 티켓별로 `/implement` |

| 스펙이며, 빌드는 작습니다 | `/implement` 스펙에 직접 대응 |

| 방금 나눈 대화에서만 해당되며, 여전히 작습니다 | `/implement` 바로 그곳, 같은 창에서 |
| 아직 어디에도 기록되지 않음 | [문서와 함께 그릴](./skills-grill-with-docs.md), 또는 코드베이스가 없다면 [그릴-나](./skills-grill-me.md) |

| 사양 없이 먼저 테스트하고 싶은 구체적인 동작 하나 | [tdd](./skills-tdd.md) 바로 |

| 이미 만들어졌고, 확인을 원함 | [코드-리뷰](./skills-code-review.md) 바로 |

동일 세션 사례는 해당 스킬의 첫 번째 줄이 이를 다루지 않기 때문에 명명할 가치가 있습니다. `SKILL.md`는 "사양 또는 티켓"이라고 말하는데, 이는 [모델](./model.md)이 존재하지 않는 파일을 찾도록 합니다. 계획이 스레드에만 존재한다면, 호출할 때 그렇게 명시하세요.

## 필수 조건

`implement`는 사용자가 있는 브랜치에 커밋합니다. 새 브랜치를 생성하지 않으며, 묻지도 않습니다. 작업을 시작하기 전에 원하는 브랜치에 있는지 확인하세요.

티켓이 [to-tickets](./skills-to-tickets.md)에서 온 경우, [setup-me-skills](../docs/engineering/setup-me-skills.md)에서 그들이 위치한 트래커를 구성했습니다. `code-review`는 동일한 구성을 읽어 종료 시 원래의 스펙을 찾습니다.

## 한 번의 실행이 하는 일

한 번의 실행에는 다섯 가지 단계가 있으며, 순서는 다음과 같습니다:

- 티켓이나 명세서를 읽고 시접을 파악합니다.

- 미리 합의된 시접에서 [tdd](./skills-tdd.md)를 구동하며, 한 번에 하나의 빨강-초록 단계씩 진행합니다.

- 자주 타입체크를 하고, 진행하면서 개별 테스트 파일을 실행합니다.

- 마지막에 전체 테스트 스위트를 한 번 실행하세요.

- [코드 리뷰](./skills-code-review.md)를 실행한 다음, 현재 브랜치에 커밋하세요.

한 번의 작업(run)은 한 장의 티켓을 처리합니다. [to-tickets](./skills-to-tickets.md)에서 생성되는 티켓들은 단일 새로운 [context window](./context-window.md)에 맞도록 크기가 조정된 추적용 세로 슬라이스(tracer-bullet vertical slices)이므로, 의도된 흐름은 다음과 같습니다: 컨텍스트를 지우고, 한 장의 티켓을 구현하고, 커밋하고, 다시 지우기. 각 티켓은 독립적이어서 이전 티켓의 컨텍스트를 버릴 수 있습니다.

## 사전에 합의한 접점

이 기술의 중심 아이디어는 **심**(seam)입니다. 심은 내부로 들어가지 않고 행동을 관찰할 수 있는 공공 경계입니다. 테스트는 심에서 수행됩니다. 코드가 존재하기 전에 심이 합의되면, 테스트는 오래 지속되며, 테스트를 변경하지 않고 그 아래의 구현을 다시 작성할 수 있습니다.

"사전 합의된" 부분이 중요하며, 또한 그것이 이 기술의 가장 약한 점이기도 합니다. `implement` 내부에는 이음새를 합치도록 하는 것이 없습니다. `tdd`는 질문을 하는 기술이며, 확인되지 않은 이음새에서 테스트를 작성하는 것을 거부합니다. 따라서 실제로 합의는 스펙 상류에서 이루어지거나 실행의 첫 번째 교환에서 이루어집니다. 어디에서도 이루어지지 않으면, 실행은 '그냥 코드를 작성하라'가 되고 아무것도 경고하지 않습니다. 스펙에서 이음새의 이름을 지정하는 것이 이를 막는 방법입니다.

## 자주 묻는 질문

**완료되었지만, 제 티켓은 아직 열려 있고 수락 기준은 여전히 체크되지 않았습니다.**

맞습니다, 그리고 예상된 일입니다. `implement`에는 완료 단계가 없습니다. 그것은 커밋에서 끝나며 작업 항목에는 전혀 접근하지 않습니다. 이것은 GitHub Issues와 로컬 마크다운 트래커 모두에서 동일하므로 트래커 통합 문제는 아닙니다. 또한 `code-review`가 생성한 결과에 대해서도 작동하지 않으며, 원래 이슈에서 `- [ ]` 박스를 체크하지 않습니다. 티켓을 닫고 기준을 직접 맞추세요. 이는 의존성 체인에서 가장 중요합니다. 왜냐하면 `to-tickets`는 방해 요소가 모두 닫힌 티켓을 최전선으로 정의하기 때문입니다. 아무것도 닫히지 않으면, 아무것도 눈에 띄게 차단 해제되지 않습니다.
**모든 티켓에 한 번에 지정할 수 있나요, 아니면 여러 개를 병렬로 실행할 수 있나요?**
`/implement`와 함께라면: 한 번 호출에 한 개의 티켓입니다. 한 번 실행으로 전체 사양을 처리하려면 [implement-spec](./skills-implement-spec.md)를 사용하세요. 이 명령은 준비된 프런티어의 각 티켓을 자체 워크트리에 있는 [subagent](./subagent.md)에 할당한 후, 결과를 한 개의 통합 브랜치에 병합합니다. 하나의 체크아웃에서 여러 `/implement` 세션을 나란히 실행하는 것은 지원되지 않는 수준보다 더 위험합니다. 한 현장 보고서는 한 세션의 `git commit --amend`가 다른 세션의 커밋 위에 적용되고, `refs/stash`에서 스태시가 사라지고, 커밋이 잘못된 브랜치에 적용되는 등의 상황이 한 오후 동안 세 개의 이슈에서 발생했다고 설명합니다. 세션들은 하나의 작업 디렉토리, 하나의 인덱스, 하나의 HEAD를 공유합니다. 사용자는 git worktrees를 이용해 이를 우회하지만, `refs/stash` 역시 워크트리 간에 공유되므로 워크트리만으로는 스태시 문제를 해결할 수 없습니다.

**커밋하는 대신 풀 리퀘스트를 열 수 있나요?**

내장되어 있지 않습니다. 현재 브랜치에 바로 커밋합니다. 여러 사람들은 코드가 작동하는지 확인하기 전에 바로 반영되기 때문에 이것을 너무 성급하다고 생각합니다. 설정 플래그도 없고 PR 모드도 없습니다. 사람들은 호출 시에 이를 재정의하거나("브랜치에 커밋하고 PR 열기") 로컬 복사본을 편집하여 재정의합니다. 에이전트가 PR을 작성할 때, [pr](./skills-pr.md)이 그 내용을 형성합니다.

**`code-review`가 내 변경 사항을 볼 수 없다고 합니다.**

`code-review`는 `git diff ...HEAD`를 검토하는데, 여기에는 스테이징된 변경사항과 작업 트리 변화가 제외됩니다. `implement`는 커밋 전에 이를 실행하므로, 중간 커밋이 이미 존재하지 않는 한 검토할 차이가 없습니다. 여러 사람이 이 문제를 보고했으며 양쪽 모두에서 수정되지 않았습니다. 먼저 커밋한 다음, 브랜치를 시작한 시점과 비교하여 검토하세요.

별도로, 일부 사람들은 에이전트가 방금 작성한 코드를 검토하는 것은 자신의 솔루션에 편향되기 때문에 실행 중에 검토를 전혀 원하지 않습니다. 고정 지점에 대해 새로운 세션에서 [code-review](./skills-code-review.md)를 실행하는 것은 유효한 대안입니다. 동일한 편향 때문에 그 기술은 두 축을 별도의 하위 에이전트에서 실행합니다.

**한 장의 티켓으로 15만 토큰이 소모되었어요. 제가 잘못 사용하고 있는 걸까요?**

아마 그렇지 않을 것입니다. 티켓이 너무 클 가능성이 더 높습니다. 실행은 코드베이스 탐색, 심마다의 빨강-초록 루프, 전체 테스트 스위트 및 리뷰를 수행하므로 100k [토큰](./token.md)을 초과하는 비사소한 티켓은 문제가 발생했다는 신호보다는 정상입니다. 수정은 상류에서 이루어져야 합니다. 각 티켓이 새로운 창 하나에 들어가도록 [to-tickets](./skills-to-tickets.md)에서 티켓 크기를 조정하세요. 단일 티켓이 계속 초과된다면 [노력](./effort.md) 수준을 올리기보다 분할하세요.

**`/implement #2`가 새로운 세션에서 전혀 관련 없는 작업을 했습니다.**

에이전트는 구성된 추적기 대신에 todo 파일이나 체크리스트와 같은 문맥에서 다른 번호 매겨진 목록에 대해 `#2`를 해결했습니다. `implement`는 이제 전달된 참조를 이슈 트래커에서 가져와 시작하기 전에 제목을 표시하며, 참조가 모호할 때 물어봅니다. 제목이 의도한 티켓과 일치하는지 확인하세요; 이슈 URL이나 `owner/repo#2`를 전달하면 모호성이 완전히 제거됩니다.

## 작동 중인 경우

- 세션은 사용자가 무엇을 만들지 묻는 대신 티켓이나 사양을 읽고 무엇을 만들 것인지 재진술하며 시작됩니다.

- 차이에서 나타나는 테스트뿐만 아니라 실제 [툴 호출](./tool-call.md)도 트레이스에서 확인할 수 있습니다.

- 타입 체크와 단일 테스트 파일은 실행 중에 반복해서 실행되며, 전체 테스트 스위트는 마지막 근처에 한 번 실행됩니다.

- 실행은 사용자가 계속 진행하도록 지시하지 않아도 현재 브랜치의 커밋에 도달합니다.

- 차이는 한 티켓만큼의 변경 사항입니다: 여러 티켓을 모아 처리한 것이 아니라 모든 계층에 걸친 수직적 분할입니다.

## 어디에 맞는지

`implement`는 메인 체인의 빌드 단계입니다:

```text
grill-with-docs → to-spec → to-tickets → implement → code-review → retro
```

그 이웃은 소비하는 티켓을 생성하고 티켓의 순서를 결정하는 차단 엣지를 선언하는 [to-tickets](./skills-to-tickets.md), 각 접합부에서 내부적으로 구동하는 [tdd](./skills-tdd.md), 커밋하기 전에 실행되는 [code-review](./skills-code-review.md)입니다. 그것은 계획 기능의 하류에 위치하며 이들을 신뢰합니다. 전달받은 것의 구조를 다시 검증하지 않으므로 구조가 잘못된 맵이나 수평으로 층이 나뉜 티켓도 작성된 그대로 빌드됩니다.

그 신뢰 덕분에 [wayfinder](./skills-wayfinder.md)는 지도를 바로 `implement`에 연결시키는 대신 [to-spec](./skills-to-spec.md)에서 체인에 합류합니다. 노력의 정도가 적게 들었을 때만 지도를 통해 바로 `implement`로 가세요.

불확실할 때는 전체 집합에서 [ask-me](./skills-ask-me.md)가 라우터 역할을 합니다.
