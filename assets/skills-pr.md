# pr

## 무엇을 하는지

`pr`는 풀 리퀘스트 본문의 형식을 정의합니다: 변경 사항을 보여주는 **요약**, 그것이 작동함을 증명하는 **증거**, 그리고 병합 위험도를 평가하는 **병합 위험**. 이것은 포맷 참고용이지 워크플로우가 아닙니다. 브랜치를 푸시하거나 PR을 열거나 내용 결정을 하지 않습니다. 본문을 작성할 때 [에이전트](./agent.md)에게 본문이 어떻게 보여야 하는지 알려줍니다.

요약은 단락이 아니라 시각적인 것입니다. 기본 PR 본문은 차이를 산문으로 설명합니다. 이 요약은 핵심을 명확히 하는 **가장 작은 뷰**(의사코드, 호출 트리, 컴포넌트 트리, 파일 트리, Mermaid 다이어그램 또는 형태가 있는 diff)를 선택하고 그 주변의 글은 간단히 유지합니다. 리뷰어는 이미 diff를 열어보았으므로 본문은 읽기 전에 그 형태를 보여줍니다.

## 언제 사용할까

`/pr`를 입력하거나, 에이전트가 PR 본문을 작성할 때 자동으로 사용합니다.

| 상황 | 사용할 항목 |

| --- | --- |
| 브랜치는 준비되어 있으며 리뷰어가 스캔할 본문이 필요합니다 | `pr` |

| 코드는 작성되었지만 아직 아무도 리뷰하지 않았습니다 | 먼저 [코드 리뷰](./skills-code-review.md)를 하고, 그 다음 `pr` |

| PR이 오픈되었고 리뷰 코멘트가 돌아오고 있습니다 | 이 세트에는 아직 아무 것도 없습니다; `pr`는 본문만 작성합니다 |

## 템플릿

세 개의 섹션, 이 순서대로:

- **요약**: 하나 이상의 작은 비주얼, 각각 짧은 텍스트 옆에 배치됩니다. 한 개를 사용하거나, 때로는 여러 개, 드물게 모두 사용합니다. 리뷰어가 필요한 호출, 파일, 소품, 경계만 유지합니다.

- **증거**: 이전과 이후. 변화가 시각적이고 [환경](./environment.md)에서 캡처가 가능할 경우, 스크린샷이 가장 강력한 증거입니다. 그렇지 않으면, 실패했다가 이제 통과한 정확한 테스트를 의사코드로 작성하거나, 변경된 콘솔 출력을 사용하세요.

- **병합 위험**: 변경이 **일방향 문**인지 **양방향 문**인지, 그리고 그 **영향 범위**를 의미합니다. 양방향 문은 되돌리기 쉽습니다. 일방향 문(파괴적인 마이그레이션, 공개 API 제거, 되돌리기 어려운 결정)은 쉽지 않습니다. 영향 범위는 변경이 잘못될 경우 무엇이 깨질 수 있는지를 나타냅니다: 레이아웃 이동, API 사용자, 모바일 반응성.

문 호출은 주요 아이디어입니다. 그것은 "이것을 병합해도 안전한가?"라는 직감적인 느낌을 리뷰어가 반대할 수 있는 명시된 주장으로 바꿉니다. 또한 리뷰어가 어디에 [인간 검토](./human-review.md)를 집중해야 하는지도 알려줍니다. 작은 충격 반경을 가진 양방향 문은 대충 훑어보고, 일방향 문은 천천히 읽으세요.

## 자주 묻는 질문

**에이전트의 자체 도어콜을 믿을 수 있을까?**

맹목적으로 하지 마세요. 이것이 바로 이를 언급하는 이유입니다. 변경을 작성한 에이전트가 그것을 평가하므로, '양방향, 작은 폭발 반경'이라고 말할 때 가장 의심해야 합니다. 또한 diff는 변경 사항을 되돌릴 수 있는지 여부를 숨기는 경우가 많습니다. 한 사용자가 말했듯이, '커밋을 롤백한다고 해서 이메일 배치를 취소할 수 있는 것은 아니다'라고 하였고, 표시된 롤아웃은 첫 번째 쓰기가 새 형식으로 들어갈 때까지 양방향 상태로 남습니다. 이 스킬은 체크리스트가 아니라 에이전트에 정의(파괴적 행동 및 되돌리기 어려운 결정은 단방향)를 제공하므로, Merge Danger 라인을 가장 주의 깊게 확인하세요. 두 가지가 도움이 됩니다: 에이전트가 diff뿐만 아니라 [티켓](./ticket.md) 또는 [스펙](./spec.md)을 보고 있는지 확인하고, 에이전트가 결정을 내리기 전에 읽을 수 있도록 변경 사항 중 항상 단방향으로 취급하는 것(스키마 마이그레이션, 외부로 배송되거나 삭제되는 모든 것)을 기록해 두세요.

**저를 위해 PR을 열어 주나요?**

아니요. `pr`는 본문만을 다룹니다. [implement](./skills-implement.md)는 현재 브랜치에 커밋함으로써 종료됩니다. PR을 여는 기술이나 옵션(`/to-pr`나 `implement`가 커밋 대신 PR을 여는 경우)에 대한 요청은 여전히 열려 있는 제안입니다. 한 사용자의 해결책은 `implement`를 PR을 열도록 지시하는 한 문장짜리 로컬 오버라이드입니다. [implement-spec](./skills-implement-spec.md)는 예외입니다: 이 옵션은 사용자가 이슈 추적기가 PR을 통해 작업을 종료하거나 요청할 때 초안 PR을 엽니다. `pr`는 모델 호출로 실행되기 때문에, 에이전트는 사용자가 PR을 열도록 요청할 때마다 본문에 이 형태를 사용합니다.

**그냥 또 다른 글과 도표의 벽을 만들지 않겠습니까?**

이 기능은 이를 방지하도록 설계되었지만, 여전히 발생할 수 있습니다. 에이전트 PR 본문에 대한 사용자의 불만은 일관적입니다: "긴 요약 말고 내가 알고 싶은 것은 무엇이 바뀌었는지, 어떻게 검증되었는지, 무엇이 깨질 수 있는지, 그리고 안전하게 병합할 수 있는지뿐입니다." 이 기능은 에이전트에게 서두를 건너뛰고, 문장을 간결하게 유지하며, 가장 작은 뷰를 선택하도록 지시합니다. 보통 하나의 시각적 자료만 선택하며 모든 자료를 선택하는 경우는 드뭅니다. 여전히 다수의 다이어그램이 나타난다면, 에이전트가 이를 무시한 것입니다. 만약 본문이 방대하다면, 그 이유는 차이(diff)가 크기 때문이고, `pr`는 이를 분할해주지 않습니다.

**내 저장소에는 이미 PR 템플릿이 있습니다. 어느 것이 우세한가요?**

기본적으로 둘 다 아닙니다. `pr`에는 자체 템플릿이 있으며 `.github/pull_request_template.md`나 이와 비슷한 것을 찾지 않습니다. 여러 사용자가 에이전트가 저장소의 템플릿을 사용하도록 요청했습니다. 아무 것도 하지 않으면 에이전트는 동일한 문서에 대해 두 가지 상충되는 지침을 갖게 됩니다. 예를 들어 저장소의 에이전트 문서에서 해결할 수 있습니다. 저장소 템플릿을 작성하고 그 아래에 요약, 증거 및 병합 위험을 배치하는 방식입니다.

**출력물이 HTML인가요? 왜 Mermaid 다이어그램이 렌더링되지 않나요?**

출력은 HTML 페이지가 아닌 마크다운 PR 본문입니다. GitHub와 GitLab은 PR 설명에서 Mermaid 블록을 렌더링하지만, 터미널에서는 그렇지 않기 때문에 다이어그램이 로컬에서 에이전트가 보여주는 동안에는 원시 텍스트처럼 보입니다. CLI 환경의 사용자는 ASCII Mermaid 렌더러를 사용하거나, 에이전트가 PR에 HTML 버전을 첨부하게 하는 방식으로 이를 우회했습니다. Mermaid는 여섯 가지 뷰 중 하나입니다. 호출 트리, 파일 트리 또는 형태가 지정된(diff) 변경 사항은 어디서나 동일하게 읽힙니다.

**되돌아오는 리뷰 댓글을 선별할 수 있나요?**

아니요. 본문을 작성하고 멈춥니다. 사용자들은 다른 개발자나 리뷰 봇의 댓글을 분류하는 방법(어떤 것은 대응할 가치가 있고, 어떤 것은 문제 없는 것인지) 요청을 여러 번 했습니다. 이 기능은 그것을 수행하지 않습니다.

**PR이 변경될 때 본문을 최신 상태로 유지하나요?**

아니요. 본문은 한 시점에 작성되며, 리뷰 중에 변경되는 PR은 해당 본문을 오래된 상태로 남깁니다. 큰 변경이 있을 경우 에이전트에게 본문을 다시 작성하도록 요청하세요. 에이전트는 PR 본문을 다시 작성하므로 같은 형식을 사용합니다.

**내 변경 사항에는 UI가 없습니다. 증거에는 무엇을 넣어야 하나요?**

스크린샷을 제외한 모든 것. 변경 사항이 시각적인 경우에만 스크린샷이 가장 강력한 증거입니다. 마이그레이션, 백그라운드 작업 또는 리팩터링의 경우, 증거는 이전에 실패했고 지금은 통과하는 정확한 테스트이거나 변경된 콘솔 출력입니다. '테스트가 녹색입니다'라는 말만으로는 주장일 뿐, 전후 비교가 아닙니다.

**본문이 LLM에 의해 작성되었는지 표시할 수 있나요?**

혼자서는 불가능합니다. 한 사용자의 접근 방식은 저장소의 에이전트 문서에 있는 지속적인 지침으로, 에이전트가 작성하는 모든 이슈, 댓글 및 PR은 공개 문구로 끝나도록 되어 있습니다. 이 규칙은 특정 문서 유형의 템플릿에 있는 것이 아니라, 에이전트가 게시하는 모든 것을 다루는 저장소에 있어야 합니다.

## 작동 중입니다

- diff를 열기 전에 Summary 시각화만으로 PR이 변경하는 내용을 알 수 있습니다.

- 본문에는 서문이 없습니다: Summary 헤딩에서 시작합니다.

- 증거 섹션은 테스트가 통과했다는 주장이 아니라, 전과 후를 보여줍니다.

- 모든 PR은 문과 폭발 범위를 명시하며, 일방통행 문은 느려지는 문입니다.

## 어디에 맞는지

`pr`는 빌드가 풀 리퀘스트로 배포될 때 리뷰와 회고 사이에 위치합니다: `to-spec → to-tickets → implement → code-review → pr → retro`. 모델에 의해 호출되므로, 에이전트가 해당 체인 외부에서 PR 본문을 작성할 때마다 스스로 실행되기도 합니다.

- [code-review](./skills-code-review.md)는 그 이전에 실행됩니다. PR 본문은 이미 리뷰된 차이를 설명해야 하기 때문입니다.

- [implement](./skills-implement.md)는 본문에서 설명하는 커밋을 생성합니다.

[ask-me](./skills-ask-me.md)는 상황이 어떤 기술을 원하는지 확실하지 않을 때 전체 세트를 통해 라우팅합니다.
