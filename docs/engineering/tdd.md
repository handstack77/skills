## 하는 일

`tdd`는 기능을 만들거나 버그를 고칠 때 테스트부터 씁니다. 실패하는 테스트 하나, 그것을 통과시킬 만큼의 코드, 그다음 다음 동작. 그 루프가 남길 가치가 있는 테스트를 만들어 내게 하는 표준을 담고 있습니다. 좋은 테스트란 무엇인지, 테스트를 어디에 두는지, 목은 무엇을 위한 것인지, 그리고 테스트 스위트를 무가치하게 만드는 세 가지 안티패턴입니다.

합의하지 않은 이음매에는 테스트를 쓰지 않습니다. 테스트가 존재하기 전에 테스트하려는 공개 경계를 이름으로 대고 당신의 확인을 위해 멈춥니다. 테스트 노력은 유한하고, 이 단계는 그것을 모든 엣지 케이스가 아니라 핵심 경로에 씁니다. `tdd`는 또한 진행자가 아니라 **참고서**입니다. 루프의 규칙을 담고 있으며, 그것을 적용하는 [세션](../../assets/session.md)은 다른 무언가(당신, 또는 [implement](../../assets/skills-implement.md))가 실행합니다.

## 언제 쓰나

`/tdd`를 입력하거나, 과업이 맞을 때(테스트를 먼저 쓰며 기능을 만들거나 버그를 고칠 때, 또는 "red-green-refactor"라고 말할 때) [에이전트](../../assets/agent.md)가 자동으로 꺼내 씁니다.

만들 구체적인 동작이 있고, 입력과 관찰 가능한 출력이 있으며, 리팩터링에서 살아남는 테스트를 원할 때 쓰세요.

| 당신의 상황 | 갈 곳 |
| --- | --- |
| 입출력이 정의된 동작 (비즈니스 로직, 요청/응답 계약, 변환, 검증) | `tdd` |
| 동작이 아직 정해지지 않음 | [to-spec](../../assets/skills-to-spec.md), 코드를 쓰기 전에 테스트 이음매에도 합의함 |
| 질문이 사실은 테스트가 아니라 인터페이스의 형태 | [codebase-design](../../assets/skills-codebase-design.md) |
| [명세](../../assets/spec.md)나 [티켓](../../assets/ticket.md)이 있고 빌드 전체를 대신 실행하길 원함 | 티켓마다 `tdd`를 모는 [implement](../../assets/skills-implement.md) |
| 설정, 배선, 접착 코드, 타입 주석, 단순 CRUD 위임 | 여기에는 잘 맞는 것이 없음. 아래의 열린 틈을 보세요 |

마지막 행은 진짜 틈입니다. 스킬은 이음매가 *어디* 가는지는 정하지만, 변경이 루프를 돌릴 가치가 있는지 *아닌지*는 아무것도 정하지 않습니다. 단언할 독립된 진실의 원천이 없는 변경에 실행하면 구현을 되풀이하는 테스트를 얻습니다. 스킬이 경고하는 동어반복 안티패턴에 반대편에서 도달한 것입니다. 이슈 #746이며 열려 있습니다. 닫힐 때까지는 그 판단을 직접 내리거나 `CLAUDE.md`에 규칙을 쓰세요.

## 선행 조건

[codebase-design](../../assets/skills-codebase-design.md)이 설치되어 있어야 합니다. `tdd`는 예전에 자체 깊은 모듈과 인터페이스 설계 노트를 갖고 있었습니다. v1.0이 그것을 공유 스킬을 위해 삭제했고, `tdd`는 이제 그 인터페이스 설계 어휘를 씁니다. 그 외에는 없습니다. 스킬은 [상태가 없고](../../assets/stateless.md) 자체 파일을 쓰지 않습니다.

## 루프, 그리고 그것이 실행되는 이음매

스킬은 세 용어에 의존합니다.

**Red-green.** 실패하는 테스트를 쓰고, 그것을 통과시킬 만큼의 코드만 씁니다. 다다음 테스트를 위한 코드를 쓰지 마세요. 리팩터링 단계는 없습니다. 2026년 6월에 스킬이 그것을 뺐습니다. 에이전트가 거의 수행하지 않았고, 리뷰와 구현이 별도의 세션일 때 더 잘 동작하기 때문입니다. 리팩터링은 [code-review](../../assets/skills-code-review.md)에 속합니다.

**수직 슬라이스.** 이음매 하나에 테스트 하나를 쓰고, 최소 구현을 쓰고, 반복합니다. 첫 사이클은 단일 경로를 끝에서 끝까지 증명하는 **트레이서 불릿**입니다. 반대는 수평 슬라이싱입니다. 테스트를 전부 먼저, 그다음 코드를 전부. 한꺼번에 쓴 테스트는 *상상한* 동작을 검증합니다. 사용자가 하는 일이 아니라 사물의 형태를 확인하고, 구현을 이해하기도 전에 테스트 구조에 매이게 합니다.

**사전에 합의한 이음매.** 이음매는 내부에 손대지 않고 동작을 관찰하는 공개 경계입니다. 규칙에 예외는 없습니다. 확인되지 않은 이음매에는 어떤 테스트도 가지 않습니다. 전체 체인에서 이음매는 더 일찍, [to-spec](../../assets/skills-to-spec.md) 동안 합의됩니다. "`/tdd`는 사전에 합의한 테스트 이음매에서만 일하라는 말을 듣고, `/code-review`는 합의한 테스트 이음매만 쓰였는지 확인합니다." 단독으로 호출하면 `tdd`가 직접 묻습니다.

방지하려고 쓰인 세 안티패턴:

| 안티패턴 | 징후 |
| --- | --- |
| 구현 결합 | 동작이 바뀌지 않았는데 내부 함수 이름을 바꾸면 테스트가 깨집니다. 내부 협력자를 모킹, 호출 횟수를 단언, 인터페이스 대신 데이터베이스 쿼리로 검증. |
| 동어반복 | 기댓값이 코드가 계산하는 방식 그대로 계산되어 테스트가 구성상 통과합니다. 기댓값은 다른 곳에서 와야 합니다. 검증된 리터럴, 풀이가 있는 예시, 명세. |
| 수평 슬라이싱 | 구현 전에 테스트 묶음이 착지함. |

목은 시스템 경계, 곧 외부 API, 시간, 무작위성, 때로는 파일 시스템이나 데이터베이스에만 씁니다. 자신의 모듈은 절대 모킹하지 마세요.

## 자주 묻는 질문

**왜 리팩터링하지 않나요? description은 "red-green-refactor"라고 합니다.**

리팩터링 단계는 제거되었는데 description은 제거되지 않았기 때문입니다. 제거는 의도적이었습니다. 에이전트가 그 단계를 거의 하지 않았고, 구현과 리뷰를 별도의 세션에 두는 것이 더 잘 동작합니다. 결과가 교과서적 TDD로 여전히 인정되는지는 루프가 더 나은 코드를 만드는지보다 덜 중요합니다. 트리거 문구와 본문의 불일치는 이슈 #589로 등록되어 있고 아직 열려 있으므로, "red-green-refactor"는 계속 스킬을 발동하는 문구로 동작합니다. 얻는 것은 red-green이고, 리팩터링은 [code-review](../../assets/skills-code-review.md)에 있습니다.

**테스트 이음매를 고르라고 했는데 어느 것을 골라야 할지 몰랐습니다.**

이 스킬에서 가장 많이 보고되는 마찰입니다(이슈 #607). 프롬프트가 후보 이음매를 이름으로만 나열하고 각각이 무엇을 잡고 놓치는지는 없어서, 레이블 사이에서 고르게 됩니다. 아직 배포된 해결책은 없습니다. 실용적인 우회책은 답하기 전에 에이전트에게 트레이드오프를 묻는 것입니다. 컴포넌트 수준 이음매가 놓치는데 통합 이음매가 잡는 것은 무엇이고, 얼마나 더 느린가. 그래서 체인이 프롬프트 하나가 아니라 기능 전체가 시야에 있는 `to-spec`에서 이음매를 미리 합의하는 이유이기도 합니다.

**스킬이 red 먼저라고 하는데도 테스트 전에 구현을 썼습니다.**

일어납니다. 한 사용자가 [모델](../../assets/model.md)을 몰아붙였고 유난히 솔직한 답을 얻었습니다. "스킬이 '한 번에 테스트 하나, 올바른 이유로 실패하는지 지켜보라'고 한다는 것을 알았습니다. 읽었습니다. 그냥 평소 습관으로 기본값이 되었습니다." 스킬은 이를 받아들입니다. 어떤 지시도 에이전트가 100% 따르게 하지 못하고, 더 엄격한 표현은 얻는 것 없이 에이전트의 창의성을 제한합니다. 에이전트가 엄격히 따르지 않더라도 결과가 전반적으로 여전히 더 낫기 때문에 루프를 돌릴 가치가 있습니다. 특정 슬라이스에서 엄격한 준수가 중요하다면, 스킬이 강제하리라 믿지 말고 실행을 지켜보세요.

**브라우저나 종단간 테스트를 먼저 써야 하나요?**

보통은 아니며, 스킬이 막지도 않습니다. 한 사용자는 에이전트가 Playwright 테스트를 먼저 쓰고, 그것을 다시 실행하는 긴 루프를 돌다가 아직 존재하지 않는 기능에 대해 *테스트*가 고장 났다고 결론짓는 것을 보고했습니다. 브라우저 테스트는 red-green 피드백 루프가 값을 못 할 만큼 느립니다. 저장소의 `CLAUDE.md`에 브라우저 테스트는 동작이 작동한 뒤에 온다고 명시하세요.

**`/tdd`가 `/implement`나 강의의 `/do-work`를 대체하나요?**

아니요. `/tdd`는 방법론을 문서화하고, `/implement`는 단순한 작업→피드백→커밋 루프이며 `/do-work`의 직접적인 대역입니다. 강의의 단일 `/do-work` 단계는 이제 `/implement`, `/tdd`, `/code-review`로 나뉩니다. 티켓에 대해 어느 것을 실행할지 묻는다면 답은 거의 항상 `/implement`입니다.

**깊은 모듈과 인터페이스 설계 지침은 어디로 갔나요?**

v1.0에서 [codebase-design](../../assets/skills-codebase-design.md)으로 갔고, 여러 스킬이 하나의 어휘를 공유하도록 일반화되었습니다. `refactoring.md`도 같은 때 떠났습니다. 리팩터링은 이제 [code-review](../../assets/skills-code-review.md)의 일이며, 그 스킬이 Fowler 스멜 기준선을 지닙니다.

**제 다른 티켓에 대해 아나요?**

아니요. 티켓 하나에 대해 실행하면, 이슈 그래프의 나머지를 볼 수 없으므로 형제 티켓에 속하는 작업을 제안할 수 있습니다(이슈 #129). `tdd`의 일이 아닙니다. 티켓과 함께 명세를 전달하면 도움이 되고, 애초에 티켓 크기를 맞추면 더 도움이 됩니다.

## 잘 작동하는 신호

- 테스트 파일이 존재하기 전에, 테스트하려는 이음매를 이름으로 대고 멈춰서 기다립니다.
- 테스트 하나가 나타나고, 빨갛게 되고, 통과할 만큼의 코드를 받고, 그 뒤에야 다음 테스트가 나타납니다. 테스트 묶음 뒤에 코드 묶음이 오지 않습니다.
- 테스트 이름이 내부("checkout calls paymentService.process")가 아니라 능력("user can checkout with valid cart")으로 읽힙니다.
- 단언의 기댓값이 코드가 계산하는 방식대로 다시 계산한 값이 아니라 명세로 추적할 수 있는 리터럴입니다.
- 내부 함수 이름을 바꿔도 스위트의 어떤 것도 깨지지 않습니다.
- 목이 외부 경계(결제 API, 시계)에서만 나타나고 자신의 모듈 주변에는 결코 나타나지 않습니다.

## 전체 흐름에서의 위치

`tdd`는 메인 체인의 빌드 단계 안에서 실행됩니다. 자체 단계는 아닙니다.

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review → retro
```

[to-spec](../../assets/skills-to-spec.md)이 테스트 이음매를 미리 합의하고, [implement](../../assets/skills-implement.md)가 티켓마다 `tdd`를 몰고, [code-review](../../assets/skills-code-review.md)가 나중에 합의한 이음매만 쓰였는지 확인하며 `tdd`가 더 이상 하지 않는 리팩터링을 맡습니다. 다른 이웃은 `tdd`가 쓰는 이음매와 깊은 모듈 어휘의 공유 출처인 [codebase-design](../../assets/skills-codebase-design.md)입니다. 만들 구체적인 동작이 있고 완전한 명세가 없을 때는 언제든 단독으로도 쓸 수 있습니다. 어느 스킬이 상황에 맞는지 확신이 없을 때는 [ask-me](../../assets/skills-ask-me.md)가 안내합니다.
