## 하는 일

`grill-with-docs`는 당신과 [에이전트](../../assets/agent.md)가 계획이나 설계에 대해 하나의 이해를 공유할 때까지 인터뷰하고, 그러는 동안 어휘와 어려운 결정을 저장소에 씁니다. [grill-me](../../assets/skills-grill-me.md)가 실행하는 것과 같은 인터뷰(질문 한 라운드, 기다림, 다음 라운드)를 코드베이스에 겨눈 것입니다.

**[상태가 있습니다](../../assets/stateful.md)**. 다른 모든 집요한 질문 스킬은 [세션](../../assets/session.md)을 당신의 머릿속에 남기지만, 이 스킬은 파일을 디스크에 남깁니다. 용어가 정리되면 스킬은 마지막에 모아서가 아니라 즉시 `GLOSSARY.md`에 씁니다. 결정이 세 관문을 통과하면 스킬은 그것을 ADR로 씁니다. 그것이 차이의 전부이며, 사람들이 이 스킬로 겪는 문제의 대부분을 일으키기도 합니다. 산출물은 실제 저장소의 실제 파일이므로, 기대한 때에 없을 수 있고, 둘 이상이 쓰면 어긋날 수 있습니다.

## 언제 쓰나

`/grill-with-docs`를 입력해서 호출하며, 에이전트가 스스로 꺼내지는 않습니다.

저장소에서 변경을 시작할 때, 계획이 아직 모호하고 그것을 가리키는 단어가 아직 정해지지 않았을 때 쓰세요. 단일 세션 도구입니다. 어느 집요한 질문 스킬을 원하는지는 눈앞의 상황에 달려 있습니다.

| 가진 것 | 쓸 것 |
| --- | --- |
| 작업 디렉터리에서 작업하고 있지 않다 | [grill-me](../../assets/skills-grill-me.md) |
| 저장소가 있고, 한 세션에 정리할 수 있는 변경 | `grill-with-docs` |
| 세션 하나로는 담을 수 없는 큰 작업 (새 프로젝트 빌드, 큰 기능) | [wayfinder](../../assets/skills-wayfinder.md) |
| 도메인 문서가 전혀 없는 저장소이고, 특별히 생각한 기능도 없다 | 변경이 아니라 저장소를 겨냥한 `grill-with-docs` |
| 다른 사람의 머릿속에 있는 지식 때문에 막힌 결정 | [to-questionnaire](../../assets/skills-to-questionnaire.md) |

wayfinder와의 갈림은 세션 수로 귀결됩니다. 단일 세션 계획에는 `/grill-with-docs`, 여러 세션에 걸친 계획에는 `/wayfinder`입니다.

## 선행 조건

스킬이 저장소에 쓰므로 안전하게 쓸 수 있는 곳에 있어야 합니다. 정리된 용어는 루트의 `GLOSSARY.md` 용어집에, 또는 루트의 `GLOSSARY-MAP.md`가 저장소를 다중 컨텍스트로 표시하면 해당 컨텍스트의 `GLOSSARY.md`에 갑니다. 결정은 `docs/adr/`에 갑니다. 스킬은 필요할 때만 둘을 만듭니다. 첫 용어나 결정이 정리되기 전에는 아무것도 없으므로, 미리 설정할 것은 없습니다.

다른 스킬 두 개도 있어야 합니다. 자신의 `SKILL.md`가 그것들에 위임하는 한 줄이기 때문입니다. [grilling](../../assets/skills-grilling.md)이 인터뷰를, [domain-modeling](../../assets/skills-domain-modeling.md)이 쓰기를 제공합니다. `grill-with-docs`만 설치하면 동작하지 않는 스킬을 얻습니다.

## 기록

세션에서 세 가지가 나오며, 같지 않습니다.

| 정리된 것 | 도착하는 곳 |
| --- | --- |
| 용어: 프로젝트 고유의 단어 | `GLOSSARY.md`, 정리되는 순간 인라인으로 |
| 되돌리기 어렵고, 맥락 없이는 의외이고, 진짜 트레이드오프인 결정 | `docs/adr/` 아래의 ADR |
| 당신이 결정한 나머지 모든 것 | 대화, 그리고 그 외에는 어디에도 없음 |

세 번째 행이 사람들을 놀라게 합니다. `GLOSSARY.md`는 용어집일 뿐입니다. 구현 세부 사항도, [명세](../../assets/spec.md)도, 메모도 담지 않습니다. ADR은 세 조건이 동시에 필요하므로 대부분의 결정은 해당되지 않고 대부분의 세션은 ADR을 만들지 않습니다. 더 날카로운 용어집과 ADR 0개를 낳는 세션은 설계대로 동작한 것이지만, 합의한 것의 대부분이 합의한 [컨텍스트 창](../../assets/context-window.md)에만 존재한다는 뜻입니다. 같은 대화를 [비우지](../../assets/clearing.md) 말고 [to-spec](../../assets/skills-to-spec.md)에 넘기세요.

용어집이 주된 산출물입니다. 이 스킬은 도메인 언어를 만듭니다. 프로젝트 고유의 단어를 한 번 합의해서, 당신과 에이전트와 동료가 다시 알아내지 않아도 되게 합니다. 이것이 에이전트의 성능을 개선한다는 데 모두가 동의하는 것은 아닙니다. 가장 강한 반론은 용어와 그것의 쉬운 영어 풀이가 [모델](../../assets/model.md)에게 같은 결과를 주며, 어휘는 주로 그것을 공유하는 사람들 사이의 소통을 줄인다는 것입니다. 그 관점에서도 용어집은 여전히 가치 있지만, 그 가치는 사람에게 돌아갑니다.

## 자주 묻는 질문

**이것과 `/wayfinder` 중 무엇을 쓰나요?**
범위가 정합니다. 한 세션에 정리할 수 있는 것에는 이것을 쓰고, 작업이 한 세션에 담기에 너무 클 때는 [wayfinder](../../assets/skills-wayfinder.md)를 쓰세요. 작업을 먼저 의사결정 [티켓](../../assets/ticket.md)의 지도로 그립니다. Wayfinder는 더 느리고 밀도가 높으며, 범위가 잘 잡힌 기능에 그것을 쓰는 것이 흔한 실수입니다. 이 스킬을 대체하지 않고, 지도에서 그에 맞는 부분에 대해 집요한 질문 세션을 시작할 수 있습니다.

**실행은 됐는데 `GLOSSARY.md`도 ADR도 나타나지 않았습니다.**
알려진 원인이 둘입니다. 첫째는 해당되는 것이 없었던 것입니다. ADR은 세 관문이 모두 필요하며, 새 어휘가 없는 변경에 대한 세션은 쓸 것이 없습니다. 둘째는 진짜 버그입니다. 스킬이 다른 오케스트레이션 계층(명세 주도 개발 래퍼, 다중 에이전트 프레임워크, 다른 사람의 파이프라인 단계로 이것을 호출하는 규칙) 안에서 실행될 때, 인터뷰는 실행되는데 파일 쓰기 절반은 조용히 일어나지 않는다고 사용자들이 보고합니다. 버그는 등록되었고 고쳐지지 않았습니다. 그런 구성에 있다면 세션의 출력을 믿기 전에 작업 디렉터리를 확인하세요.

**모든 것을 한꺼번에, 추천 없이 물었고 `GLOSSARY.md`는 언급하지 않았습니다.**
스킬이 두 의존성을 로드하지 못한 것입니다. `SKILL.md`가 한 줄짜리 위임이므로, [grilling](../../assets/skills-grilling.md)과 [domain-modeling](../../assets/skills-domain-modeling.md)을 가져오지 못한 에이전트는 집요한 질문이 무엇인지 짐작하고, 구조 없이 모든 질문이 한꺼번에 나옵니다. 부분 로드는 더 혼란스럽습니다. `grilling`은 로드되고 `domain-modeling`은 로드되지 않아서, 좋은 인터뷰는 있지만 기록은 없습니다. 얼마나 자주 일어나는지는 모델과 [노력](../../assets/effort.md) 수준에 달려 있으며, 이 스킬에서 가장 많이 보고되는 문제입니다. 의심되면 에이전트에게 직접 어떤 스킬을 로드했는지 물으세요.

**제 다른 결정들은 어디로 갔나요?**
대화에만 있습니다. 이 스킬에 대해 열려 있는 가장 심각한 불만입니다. 용어집은 명세가 아니고, 대부분의 답은 ADR이 될 자격이 없으며, 정리된 각 답을 명세, 티켓, 테스트에 연결하는 기록이 없습니다. 이후 단계가 정밀한 답(순서 보장, 부정 요구 사항, 숫자 기본값)을 약한 산문으로 무르게 만들고, 결과는 완전해 보이는데 당신이 결정한 것이 빠져 있을 수 있습니다. 지금은 세션을 유지하고 곧바로 [to-spec](../../assets/skills-to-spec.md)에 넘기세요. 그다음 명세가 담았다고 가정하지 말고 자신의 답에 비추어 명세를 다시 읽으세요.

**문서가 전혀 없는 기존 저장소에 겨눌 수 있나요?**
네. ADR도, 도메인 언어도, 설계 원칙도 없는 코드베이스에는 이것이 맞는 스킬입니다. 호출하고 "내 저장소를 문서화하도록 도와줘"라고 말하세요. 사용자들은 `GLOSSARY.md`를 만들거나 고치기 위해 이것을 [improve-codebase-architecture](../../assets/skills-improve-codebase-architecture.md)와 짝짓는 일이 많습니다. 조종해야 할 것으로 예상하세요. 코드를 읽고 발견한 것에 대해 당신에게 묻고, 코드베이스에 이미 있는 단어 중 어느 것이 맞는지는 당신이 결정합니다.

**세션이 끝나면 무엇을 해야 하나요?**
스킬의 마무리 메시지는 열려 있는 경우가 많으며 알려진 문제입니다. 메인 흐름에서 답은 같은 대화에서 [to-spec](../../assets/skills-to-spec.md)입니다. 변경이 곧바로 만들 수 있을 만큼 작다면 대신 [implement](../../assets/skills-implement.md)로 곧바로 가세요.

**왜 이런 이름인가요?**
이름에 만족하는 사람이 없습니다. 동작을 더 정확하게 설명하는 `grill-domain-model`로 이름을 바꾸자는 제안이 열려 있습니다. 진전은 없습니다. 이름이 바뀌면 문서 페이지도 함께 옮겨 가고 URL이 바뀝니다.

## 잘 작동하는 신호

- `GLOSSARY.md`가 마지막에 한 덩어리로 나타나지 않고 세션 *중에* 용어마다 바뀝니다.
- 용어집이 순수한 어휘(간결한 정의가 붙은 프로젝트의 단어)로 읽히고, 구현 세부 사항이나 명세 같은 산문이 없습니다.
- 코드베이스가 답할 수 있는 질문은 당신에게 묻지 않고 코드베이스를 읽어서 답합니다.
- ADR이 거의 또는 전혀 없고, 있는 것은 다시 논쟁하게 되면 짜증날 결정입니다.
- 기존 용어집이 다르게 정의하기 때문에 당신이 쓴 단어에 이의를 제기합니다.

## 전체 흐름에서의 위치

`grill-with-docs`는 메인 빌드 체인의 머리입니다.

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review → retro
```

명세로 무언가를 적기 전에 옵니다. [to-spec](../../assets/skills-to-spec.md)이 다시 인터뷰하지 않고 종합하는 공유된 이해와 정리된 어휘를 만듭니다. 가까운 이웃은 저장소도 파일도 없는 같은 인터뷰인 [grill-me](../../assets/skills-grill-me.md)와, 이것이 모는 용어집과 ADR 규율인 [domain-modeling](../../assets/skills-domain-modeling.md)입니다. 둘 다 인터뷰에 [grilling](../../assets/skills-grilling.md) 프리미티브를 씁니다. 이것의 Upstream에서 [wayfinder](../../assets/skills-wayfinder.md)는 한 세션에 너무 큰 작업을 지도로 그리고 지도의 일부를 이것에 다시 내려보낼 수 있습니다. 어느 스킬이나 흐름이 맞는지 확신이 없을 때는 [ask-me](../../assets/skills-ask-me.md)가 안내합니다.
