## 하는 일

`code-review`는 `HEAD`와 당신이 지명한 고정 기준점(커밋, 브랜치, 태그, `main`, `HEAD~5`) 사이의 diff를 두 축으로 검토합니다. **표준(Standards)**은 코드가 이 저장소가 코드를 쓰는 방식을 따르는지 묻습니다. **명세(Spec)**는 코드가 원래 이슈나 [명세](../../assets/spec.md)가 요구한 일을 하는지 묻습니다. 각 축은 자기 [서브에이전트](../../assets/subagent.md)에서 실행되어 어느 쪽도 상대의 추론을 보지 않습니다.

스킬은 두 축을 합치거나 순위를 다시 매기지 않습니다. 보고서는 *축마다* 가장 심각한 문제로 끝나고, 축들을 가로지르는 단일 승자를 지명하기를 거부합니다. 변경은 한 축은 통과하고 다른 축은 실패할 수 있습니다. 모든 관례를 따르지만 엉뚱한 것을 구현한 코드는 표준을 통과하고 명세에서 실패합니다. [티켓](../../assets/ticket.md)이 요구한 일을 정확히 하지만 저장소의 관례를 깨는 코드는 그 반대입니다. 혼합된 판정은 통과한 축이 실패한 축을 가리게 합니다.

## 언제 쓰나

`/code-review`를 입력하거나, 브랜치, PR, 진행 중인 작업, 또는 "X 이후"의 무엇이든 리뷰해 달라고 할 때 에이전트가 자동으로 꺼내 씁니다.

| 당신의 상황 | 쓸 것 |
| --- | --- |
| diff가 있고 제대로 만들어졌는지 *그리고* 맞는 것인지 알고 싶음 | `code-review` |
| diff에서 버그를 사냥하고 싶음: null 경로, 경합, off-by-one | 이것이 아니라 Claude Code 자체의 내장 리뷰 (아래의 이름 충돌 참고) |
| 아직 아무것도 쓰이지 않았고 테스트부터 쓰고 싶음 | [tdd](../../assets/skills-tdd.md) |
| 리뷰를 포함해 명세 전체를 만들어야 함 | 이 스킬을 스스로 호출하는 [implement](../../assets/skills-implement.md) |
| diff 하나가 아니라 코드베이스 전체가 표류함 | [improve-codebase-architecture](../../assets/skills-improve-codebase-architecture.md) |
| 무언가 고장 났는데 이유를 모름 | [diagnosing-bugs](../../assets/skills-diagnosing-bugs.md) |

기준점은 당신이 제공해야 합니다. 그렇지 않으면 스킬이 짐작하지 않고 묻습니다. 무언가를 띄우기 전에 ref가 해석되는지, diff가 비어 있지 않은지 확인하므로, 잘못 입력한 브랜치 이름이 서브에이전트 둘 안이 아니라 눈앞에서 실패합니다.

## 선행 조건

표준 축은 아무것도 필요 없습니다. 저장소가 문서화한 모든 것(`CODING_STANDARDS.md`, `CONTRIBUTING.md` 등)을 읽고, 저장소가 아무것도 문서화하지 않았을 때는 내장 기준선으로 되돌아갑니다.

명세 축은 명세가 존재하고 찾을 수 있어야 합니다. 이 순서로 찾습니다.

1. 커밋 메시지의 이슈 참조(`#123`, `Closes #45`, GitLab `!67`). 트래커 문서를 통해 가져옵니다.
2. 인자로 전달한 경로.
3. 브랜치나 기능 이름과 일치하는 `docs/`, `specs/`, `.scratch/` 아래의 명세 파일.
4. 당신에게 묻기.

1단계는 [setup-me-skills](setup-me-skills.md)가 쓰는 트래커 문서에 의존합니다. 그것이 없어도 경로를 건네면 축이 동작합니다. 명세가 전혀 없으면 스킬은 명세 서브에이전트를 건너뛰고, 보고서는 요구 사항을 지어내는 대신 "사용 가능한 명세 없음"이라고 말합니다.

## 두 축

| | 표준 | 명세 |
| --- | --- | --- |
| 질문 | 제대로 만들어졌나? | 맞는 것인가? |
| 읽는 것 | 저장소의 문서화된 표준과 스멜 기준선 | 원래 이슈나 명세 |
| 보고하는 것 | 문서화된 위반(확정적일 수 있음)과 스멜(항상 판단의 영역) | 빠졌거나 부분적인 요구 사항, 범위 확장, 잘못 구현된 요구 사항 |
| 모든 발견 사항이 인용하는 것 | 표준 파일과 규칙, 또는 이름 붙인 스멜과 hunk | 명세의 줄 |

이 설계는 당신의 표준을 모르는 일반적인 리뷰 스킬을 피하려고 존재합니다. 그런 스킬은 코드베이스에서 의도적인 것을 지적하고 코드베이스가 의존하는 불변식을 놓칩니다. 그래서 표준 축에서는 저장소 자신의 문서가 [1차 자료](../../assets/primary-source.md)이며, **저장소가 항상 우선합니다**.

**스멜 기준선**은 저장소 표준 밑에 놓입니다. Fowler의 _Refactoring_ 3장의 코드 스멜 열두 가지입니다. Mysterious Name, Duplicated Code, Feature Envy, Data Clumps, Primitive Obsession, Repeated Switches, Shotgun Surgery, Divergent Change, Speculative Generality, Message Chains, Middle Man, Refused Bequest. 각각은 레이블을 붙인 휴리스틱("Feature Envy 가능성")이며 확정적인 위반이 아닙니다. 각각이 스멜이 무엇인지와 어떻게 고치는지를 밝히므로, 발견 사항에는 불평만이 아니라 해결책이 딸려 있습니다. 두 축 모두 린터가 이미 강제하는 것은 건너뜁니다.

## 자주 묻는 질문

**Claude Code 자체의 `/code-review`와 충돌합니다. 어떻게 하나요?**

로컬 `code-review` 스킬은 Claude Code의 같은 이름 내장 스킬보다 우선할 수 있습니다. 이 문서의 리뷰는 저장소 표준과 명세 준수를 확인합니다. Claude Code에서는 `/code-review`, Codex CLI에서는 `$code-review`로 요청하고, 로드한 파일이 이 저장소의 `skills/engineering/code-review/SKILL.md`인지 확인하세요. 이름을 따로 쓰려면 원본 폴더와 `SKILL.md`의 `name`을 함께 바꾸고 연결을 다시 설정하세요.

**서브에이전트가 `/code-review`를 계속 다시 호출하고 에이전트를 더 띄웁니다.**

알려진 열린 버그입니다. 여러 사람이 둘 이상의 하니스에서 재현했습니다. 표준과 명세 프롬프트가 위임을 금지하지 않으므로 서브에이전트가 스킬을 다시 찾아 또 퍼질 수 있습니다. 한 보고는 에이전트 50개 이상에 이르렀습니다. 사람들이 포크에서 적용한 해결책은 두 서브에이전트 브리프 모두에 한 줄을 덧붙이는 것입니다. "`/code-review`를 호출하거나 추가 에이전트를 띄우지 말고 이 리뷰를 직접 수행하라." 어떤 사람들은 모든 스킬이 가드를 상속하도록 하니스 수준에서 처리하기를 선호합니다. 둘 다 아직 배포된 스킬에는 없습니다. 무인으로 실행한다면 에이전트 수를 지켜보세요.

**코드를 쓴 같은 [세션](../../assets/session.md)에서 실행해야 하나요?**

새 세션을 선호하세요. 한 독자의 말로, "같은 컨텍스트가 스스로를 리뷰하는 것은 리뷰가 아니라 슬래시 명령이 붙은 확증 편향입니다." 작성 세션에서 리뷰하는 에이전트는 코드를 빚은 모든 가정을 컨텍스트에 갖고 있습니다. 독립적인 리뷰어는 그 컨텍스트가 없을 것입니다. 이것이 사람들이 내장 리뷰 단계 없는 [implement](../../assets/skills-implement.md)를 요청하는 이유이기도 합니다. 그 단계는 방금 diff를 쓴 세션 안에서 리뷰를 실행하기 때문입니다. 독립적인 방식은 깨끗한 세션에서 직접 `/code-review`를 호출하는 것입니다.

**티켓마다 할까요, 마지막에 한 번 할까요?**

둘 다 동작하며 스킬이 대신 정하지 않습니다. 티켓마다 하면 각 diff가 작아서 명세 축이 확인할 분명한 명세 하나를 갖게 되며, `implement`가 쓰는 방식입니다. 브랜치 끝에 모아서 하면 티켓별 패스가 각자 놓치는 티켓 사이의 상호작용을 잡아냅니다. 확신이 없다면 티켓마다 리뷰하고, 브랜치를 딴 지점에 대해 마지막 패스를 한 번 실행하세요.

**발견 사항을 믿어도 되나요?**

확인 없이는 안 됩니다. 서브에이전트의 출력은 증거가 아니라 가설입니다. 한 팀은 산문 기반 리뷰가 놓친 호환성을 깨는 변경 열두 개를 보고했습니다. 스킬은 두 보고를 있는 그대로, 또는 가볍게 정리해서 합칩니다. 각 주장을 파일에 대해 다시 검증하지 않으므로, 발견 사항이 잘못된 위치를 인용하거나 영향을 과장할 수 있습니다. 행동하기 전에 각 발견 사항의 인용을 읽으세요. 스킬은 모든 발견 사항이 인용(표준 규칙, 스멜과 그 hunk, 또는 명세 줄)을 달도록 요구하며, 그것이 발견 사항을 확인할 수 있게 합니다.

**실행할 때마다 새로운 문제를 찾는 이유는 무엇인가요?**

수정마다 리뷰할 새 코드가 늘고, 표준 축의 판단 영역 절반은 실행마다 다른 결과를 냅니다. 한 독자가 루프를 설명했습니다. "/code-review와 /improve-code-architecture는 매번 새로운 것을 찾습니다. 수정을 구현하고, 스킬을 다시 실행하고, 계속 반복합니다." 수렴 보장은 없습니다. 패스를 단서 목록으로 취급하세요. 인용된 규칙이 뒷받침하는 것에 대해 행동하고, 그다음 멈추세요. 깨끗하게 돌아올 때까지 루프로 실행하지 마세요. 결코 그렇게 되지 않습니다.

**커밋하지 않은 작업도 리뷰하나요?**

아니요. `<fixed-point>...HEAD`를 diff합니다. 점 세 개 형태는 merge-base부터 측정하며 스테이징된 변경과 작업 트리 변경을 제외합니다. `implement`가 중간 커밋을 하지 않았다면 리뷰는 다음 커밋에 들어갈 작업을 볼 수 없습니다. 먼저 커밋하고, 리뷰하고, 그다음 amend하거나 fixup을 추가하세요.

## 잘 작동하는 신호

- 서브에이전트를 띄우기 전에 잘못된 ref나 빈 diff에서 시작을 거부합니다.
- 보고서가 합쳐진 하나의 목록이 아니라 `## 표준 (Standards)`와 `## 명세 (Spec)` 아래의 두 개의 별도 블록으로 도착합니다.
- 모든 표준 발견 사항이 당신 저장소 파일의 규칙이나 hunk를 인용한 열두 스멜 중 하나를 이름으로 대고, 모든 명세 발견 사항이 명세의 줄을 인용합니다.
- 마무리 요약이 축마다 가장 심각한 문제를 주고 전체 승자를 지명하기를 거부합니다.
- 사용 가능한 명세가 없으면, 코드에서 추론한 요구 사항을 나열하는 대신 명세 블록이 그렇다고 말합니다.

## 전체 흐름에서의 위치

`code-review`는 빌드 체인 끝부분의 리뷰 단계입니다. `grill-with-docs → to-spec → to-tickets → implement → code-review → retro`. 가리키는 어느 브랜치나 PR에서든 단독으로도 쓰입니다.

- [implement](../../assets/skills-implement.md)가 가장 가까운 이웃입니다. 빌드를 몰고 커밋하기 전에 이 스킬을 자체 마무리 리뷰로 호출합니다. [implement-spec](../../assets/skills-implement-spec.md)은 통합 브랜치 전체에 대해 한 번 같은 일을 합니다.
- [retro](../../assets/skills-retro.md)가 그 뒤에 와서 이것을 조정합니다. 세션에서 리뷰가 한 부류의 실수를 놓쳤음이 드러나면, `retro`가 표준 축이 읽을 검사나 `CODING_STANDARDS.md` 규칙을 제안합니다.
- [pr](../../assets/skills-pr.md)이 리뷰된 작업이 올라갈 때 풀 리퀘스트 본문을 씁니다.
- [to-spec](../../assets/skills-to-spec.md)과 [to-tickets](../../assets/skills-to-tickets.md)가 명세 축이 대조하는 문서를 만들므로, 모호한 명세는 그 축을 모호하게 만듭니다.
- [improve-codebase-architecture](../../assets/skills-improve-codebase-architecture.md)는 코드베이스 전체의 대응물입니다. 이 스킬은 diff 하나만 보기 때문입니다.

어느 스킬이 상황에 맞는지 확신이 없을 때는 [ask-me](../../assets/skills-ask-me.md)가 전체 집합에 걸쳐 안내합니다.
