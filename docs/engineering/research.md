## 하는 일

`research`는 답을 소유한 출처를 읽어서 질문에 답하고, 저장소에 출처가 달린 Markdown 파일을 남깁니다. **[1차 자료](../../assets/primary-source.md)**, 곧 공식 문서, 소스 코드, 명세, 퍼스트파티 API만으로 작업합니다. 모든 주장을 그것을 소유한 출처까지 거슬러 따라가므로, API 자체의 문서에 접근할 수 있다면 블로그 글이 설명한 API 이야기를 되풀이하지 않습니다.

대화 안에서 답하지 않습니다. 출력은 저장소가 이미 그런 노트를 두는 곳에 쓰인 파일이며, 주장마다 링크가 달려 있습니다. [세션](../../assets/session.md)이 끝나면 사라지는 답이 아니라, 반응하고, 다른 에이전트에게 넘기고, 버릴 수 있는 문서를 얻습니다.

## 언제 쓰나

`/research`를 입력하거나, 과업이 읽기 수고로 바뀔 때 [에이전트](../../assets/agent.md)가 자동으로 꺼내 씁니다.

다음 단계가 작업 디렉터리 밖에서 *무언가를 알아내는 것*(서드파티 API가 어떻게 동작하는지, 명세가 무엇을 말하는지, 버전 주장이 성립하는지)이고, 읽느라 자신의 스레드가 멈추는 것을 원하지 않을 때 쓰세요. 필요한 것이 어느 스킬을 쓸지 정합니다.

| 필요한 것 | 쓸 것 |
| --- | --- |
| 결정이 기다리는 외부 사실 | `research` |
| 인터뷰로 *당신과 함께* 내리는 결정 | [grilling](../../assets/skills-grilling.md) |
| `GLOSSARY.md`와 ADR에 기록되는 지속적인 아키텍처 결정 | [grill-with-docs](../../assets/skills-grill-with-docs.md) |
| 어떤 접근이 코드베이스에서 동작하는지 알아내기 | [prototype](../../assets/skills-prototype.md) |
| 세션 하나로는 담을 수 없는 큰 계획 | [wayfinder](../../assets/skills-wayfinder.md) |

`research`와 `grill-with-docs`의 경계는 **돌아오는 것의 유통기한**입니다. 조사는 이 라이브러리의 인증 메커니즘이 이번 주 기준으로 무엇을 하는가 같은 짧은 수명의 사실을 만듭니다. ADR은 유지하는 결정을 기록합니다. 만들어 내는 것이 사실이 아니라 결정이라면, 조사하는 것이 아니라 [집요하게 질문하는](../../assets/grilling.md) 것입니다.

## 위임된 수고

읽기는 **백그라운드 에이전트**로 실행됩니다. 에이전트가 각 주장을 1차 자료까지 따라가고, Markdown 파일 하나를 쓰고, 보고하는 동안 당신은 계속 작업합니다. 조사는 위임하는 수고이지 외주 주는 사고가 아닙니다. 집요하게 질문하고, 계획하고, 설계할 문서를 얻으며, 결정은 여전히 당신이 내립니다.

백그라운드 에이전트가 자기 백그라운드 에이전트를 또 띄우는 것을 막는 것은 없습니다. 이것이 스킬에서 가장 잘 문서화된 문제입니다.

파일이 어디로 가는지는 스킬이 아니라 저장소가 정합니다. 노트에 대해 이미 있는 관례를 따릅니다. 없다면 적당한 곳을 골라 어디인지 알려 줍니다. 실행마다 파일 하나를 씁니다.

## 자주 묻는 질문

**조사 에이전트가 두 번째 에이전트를 띄웠습니다. 의도된 건가요?**

아니요. 열려 있는 버그이며 이슈 #530입니다. 스킬은 호출자에게 백그라운드 에이전트를 띄우라고 말하지만 에이전트 유형을 제한하지 않습니다. 그래서 호출자가 `Agent` 도구와 같은 지시를 가진 `general-purpose` 에이전트를 띄우고, 그 에이전트가 그것을 다시 따릅니다. 한 보고자는 겹치는 세 번의 실행에 걸쳐 조사 과업 하나에 약 450k [토큰](../../assets/token.md)이 들었고, 중복 실행은 사용자가 볼 수 없는 곳에서 30분 뒤에 끝났다고 측정했습니다. Claude Code 밖에서도 일어납니다. 사용자들은 GPT-5.6-sol의 Codex에서도 같은 중첩을 확인했습니다. 배포된 해결책은 없습니다. 사용자들은 이미 [서브에이전트](../../assets/subagent.md)인 에이전트에게 직접 작업하라고 알리는 한 줄을 설치한 사본에 직접 패치했습니다. 도움이 되지만 지시일 뿐 구조적 해결책은 아닙니다. 스킬을 호출한 뒤에는 백그라운드 작업 목록을 지켜보고 중복을 멈추세요.

반대의 실패도 일어납니다. 자신의 전역 지시가 에이전트의 작업 재위임을 금지하면, 백그라운드 에이전트가 과업을 거부하고 스킬은 알리지 않고 아무것도 하지 않습니다.

**파일은 어디에 두어야 하고, 커밋해야 하나요?**

스킬은 저장소가 이미 노트를 두는 곳에 파일을 놓고 그 이상의 의견은 없습니다. 커뮤니티의 견해는 대체로 정리되어 있습니다. ADR은 보관하고 조사 파일은 보관하지 않는다는 것입니다. 이 질문에 대한 Discord 스레드 하나가 가장 분명하게 말했습니다. "ADR은 예. 나머지는 끝나면 보관하거나 삭제하세요. 그렇지 않으면 작업의 찌꺼기가 되고, 명세/조사에서 멀어졌을 때 미래의 저장소 읽기를 오염시킬 수 있습니다." 조사 파일은 쓰인 날 참이었던 것을 기록하므로, 낡은 파일은 없는 것보다 나쁩니다. 대체로 이 파일들은 git에 속하지 않으며 표준적인 집도 없습니다. 사람들은 대신 Obsidian, 별도의 지식 저장소, 이슈 트래커를 씁니다.

**무엇이 "신뢰도 높은" 1차 자료이고, 누가 정하나요?**

[모델](../../assets/model.md)이 정합니다. 스킬은 자격이 되는 출처의 *종류*(공식 문서, 소스 코드, 명세, 퍼스트파티 API)를 이름으로 부르며, 허용 목록도, 도메인 관문도, 검증 패스도 없습니다. 스킬이 처음 제안되었을 때 가장 큰 반론이었고 아무도 공개적으로 답하지 않았습니다. "쓰레기를 가리키는 조사 서브에이전트 다섯 개는 자신 있게 틀린 답 다섯 개를 더 빨리 줄 뿐입니다. 무엇이 신뢰도 높은 출처인지 어떻게 걸러 내나요?" 유일한 보호는 주장마다 달린 인용입니다. 두세 개를 따라가 보세요. 그것 자체가 아니라 그것의 요약에 이르면 그 실행은 실패한 것입니다.

**이후 세션이 이전 실행이 찾은 것을 재사용하나요?**

아니요. 과거의 조사 파일을 자동으로 로드하는 것은 없습니다. 파일은 사람이나 스킬이 가리킬 때까지 저장소에 남아 있습니다. 설계에 대한 가장 강력한 초기 도전이었습니다. "가치는 가져오기 자체가 아니라 에이전트가 나중에 다시 읽는 컨텍스트가 되는 마크다운입니다. 한 번 쓰고 마는 죽은 파일은 그저 화려한 검색일 뿐입니다." 배포된 스킬은 이를 해결하지 않습니다. 실제로 파일이 유용한 것은 다음 단계에 직접 넣어 줄 때뿐입니다. 명세에 첨부하거나, 집요한 질문 세션에 인용하거나, [티켓](../../assets/ticket.md)이 그것을 가리키게 하세요.

**왜 그냥 에이전트에게 문서를 읽어 달라고 하면 안 되나요?**

됩니다. 정확히 그렇게 말하는 두 줄짜리 프롬프트가 이 스킬이 대체한 관행이었습니다. 스킬은 프롬프트가 주지 못하는 두 가지를 줍니다. 백그라운드에서 실행되므로 세션의 [컨텍스트](../../assets/context.md)가 깨끗하게 유지됩니다. 그리고 1차 자료 제약과 출처가 달린 파일 출력은 프롬프트를 어떻게 표현했는지에 의존하지 않고 매번 같습니다. [하니스](../../assets/harness.md) 자체의 딥 리서치 모드와 비교하면 차이는 검색이 아니라 파일과 1차 자료 규칙입니다. 작은 질문에서 두 줄짜리 프롬프트로 필요한 것을 얻을 수 있다면 두 줄짜리 프롬프트를 쓰세요.

**언제 읽기를 멈추나요?**

스킬에는 중단 기준이 없습니다. 이는 반대처럼 보이지만 원인이 같은 두 불만으로 나타납니다. 너무 깊이 들어가는 에이전트, 그리고 주제를 넓게 다루지만 중요했던 세부 하나를 놓치는 에이전트입니다. 한 실무자는 이렇게 말했습니다. "딥 리서치 스킬은 때로 너무 깊습니다. 그리고 에이전트에게 조사하라고 하면 보통 결정적인 세부를 놓칩니다." 범위는 당신이 정해야 합니다. 좁고 답할 수 있는 질문(API 하나, 동작 하나, 버전 주장 하나)은 "X를 조사하라"보다 훨씬 잘 돌아옵니다.

**`/wayfinder`가 조사 티켓을 만들었습니다. 제가 직접 해결하나요?**

아니요, 이제 대신 발사합니다. v1.1 이후 릴리스되지 않은 변경에서, 지도를 그리는 세션이 조사 티켓마다 `/research` 서브에이전트 하나를 띄우고 병렬로 실행합니다. 각각은 티켓에서 [컨텍스트 포인터](../../assets/context-pointer.md)와 함께 일회용 `research/<name>` 브랜치에 발견한 내용을 기록합니다. 조사 티켓은 [AFK](../../assets/afk.md)이므로, 아무도 당신을 기다리지 않기 때문에 wayfinder의 세션당 티켓 하나 규칙의 유일한 예외입니다. 알려진 문제가 하나 있습니다. 나중에 브랜치를 삭제하면 티켓의 컨텍스트 포인터가 깨집니다.

## 잘 작동하는 신호

- 자신의 세션이 계속 진행됩니다. 읽는 것을 앉아서 지켜보고 있다면 위임이 일어나지 않은 것입니다.
- 새 백그라운드 작업이 정확히 하나 나타납니다. 거의 같은 이름의 두 번째가 있다면 중첩 버그입니다.
- 새 Markdown 파일 하나가 저장소가 이미 노트에 쓰는 폴더에 나타나고, 에이전트가 경로를 알려 줍니다.
- 모든 주장에 링크가 달려 있고, 무작위로 둘을 따라가면 누군가의 정리글이 아니라 공식 문서, 명세, 소스 파일 자체에 도달합니다.
- 출처로 직접 돌아가지 않고도 파일만으로 막혀 있던 결정을 내릴 수 있습니다.

## 전체 흐름에서의 위치

`research`는 언제든 찾는 독립형입니다. 사고하는 스킬들에 재료를 대며 빌드 체인의 한 단계가 아닙니다. 그 파일을 흐름 *안으로* 가져갑니다. [grilling](../../assets/skills-grilling.md)과 [grill-with-docs](../../assets/skills-grill-with-docs.md)는 사실을 이미 가지고 있으면 더 날카로운 질문을 하고, [to-spec](../../assets/skills-to-spec.md)은 그것에 맞춰 종합할 수 있습니다. [wayfinder](../../assets/skills-wayfinder.md)가 이것을 직접 호출하는 유일한 스킬입니다. 지도의 조사 티켓마다 `/research` 서브에이전트로 해결합니다. 전체 지도는 [ask-me](../../assets/skills-ask-me.md)를 보세요.
