## 하는 일

`prototype`은 **질문에 답하는 일회용 코드**를 씁니다. 이 상태 모델이 맞게 느껴지는가, 또는 이 화면은 어떻게 생겨야 하는가. 질문이 먼저이고 무엇을 만들지 정합니다. 엉뚱한 질문에 답하는 프로토타입은 아무리 근사해 보여도 낭비입니다.

일회용은 코드를 *쓰는 방식*에 대한 제약이지, 파기하겠다는 약속이 아닙니다. 테스트도, 실행에 필요한 것 이상의 에러 처리도, 추상화도, 영속성도 없습니다. 그중 어느 것도 배우려는 한 가지를 배우는 데 도움이 되지 않기 때문입니다. 두 가지가 살아남습니다. 답은 실제 코드에 들어가고, 프로토타입은 답의 증거로 main이 아닌 브랜치에 갑니다.

## 언제 쓰나

`/prototype`을 입력하거나, 과업이 맞을 때 [에이전트](../../assets/agent.md)가 자동으로 꺼내 씁니다.

말로는 정리할 수 없는 질문을 만나는 순간 쓰세요. 머릿속에 담을 수 없는 엣지 케이스가 있는 상태 머신, 나란히 세 버전을 보기 전에는 그려지지 않는 화면. [집요한 질문](../../assets/grilling.md) 세션은 이런 질문에서 길어집니다. 에이전트는 말을 바꿔 묻고, 당신은 짐작하고, 범위가 커집니다. 집요한 질문을 멈추고, 일회용 버전을 만들고, 보고, 한 줄로 답하세요. 반대로 이미 만들어진 것이 잘못 동작하는데 이유를 알고 싶다면 [diagnosing-bugs](../../assets/skills-diagnosing-bugs.md)를 쓰세요. 프로토타이핑은 무엇을 만들지 탐색하는 것이지, 만들어진 것이 왜 고장 났는지가 아닙니다.

선택하지 않고도 여기에 도착하게 됩니다. [wayfinder](../../assets/skills-wayfinder.md)가 지도에 `prototype` 의사결정 [티켓](../../assets/ticket.md)을 올리고, 당신은 이 스킬로 하나를 처리합니다.

## 두 갈래

질문이 갈래를 고르며, 갈래마다 다른 산출물이 나옵니다.

- **"이 로직 / 상태 모델이 맞게 느껴지는가?"**: **공유 가능한 HTML 파일 하나**. 빌드도 서버도 없는 독립적인 페이지 하나이며 더블클릭으로 열립니다. 클릭할 때마다 다시 렌더링되는 레이블이 붙은 상태 패널, 아무 순서로나 모델을 찔러볼 수 있는 자유 조작 버튼, 탭으로 나뉜 **안내형 워크스루**(탭마다 시나리오 하나, 각각 그 아래에 누를 버튼이 순서대로 있음)를 담습니다. 모든 것이 도메인 언어로 레이블이 붙어 있어서 디자이너, PM, 도메인 전문가에게 건네 직접 모델을 시험해 보게 할 수 있습니다. 페이지 뒤의 로직은 DOM 코드가 없는 작은 순수 모듈(리듀서, 머신, 함수 모음)이므로, 검증된 버전을 곧바로 실제 코드로 옮길 수 있습니다.
- **"이것은 어떻게 생겨야 하는가?"**: 하나의 라우트에 **근본적으로 다른** UI 변형 여러 개를, 화면 아래에 떠 있는 바와 `?variant=` URL 파라미터로 전환합니다. 변형은 색이 아니라 구조에 대해 의견이 달라야 합니다. 살짝 손본 카드 그리드 셋은 아무것도 답하지 못합니다. 가능하면 실제 페이지 안에서, 실제 데이터와 실제 밀도로 렌더링합니다. 빈 페이지에서 판단한 변형은 항상 괜찮아 보이기 때문입니다.

둘 다 상태를 메모리에 두고, 설정 없이 시작하며, 매 단계 뒤에 전체 상태를 보여 줍니다. 하나를 단단하게 만들고 있는 자신을 발견하는 순간(테스트 추가, 실제 데이터베이스 연결, 나중에 필요할지 모를 경우를 위한 일반화) 프로토타이핑을 멈춘 것입니다.

## 프로토타입은 1차 자료입니다

완성된 프로토타입은 두 가지를 남기고, 서로 다른 곳으로 갑니다.

**답**(판결과 그것이 정리한 질문)은 영구적인 곳에 기록합니다. 커밋 메시지, ADR, 구현 이슈입니다. main은 실제 코드 안에 답을 보관합니다.

**프로토타입**은 답이 나온 실행 가능한 증거이며 삭제하지 않습니다. main에도 속하지 않습니다. 아무도 유지하지 않고 금세 낡기 때문입니다. 그래서 main이 아닌 일회용 `prototype/<name>` 브랜치에 커밋하고, 절대 병합하지 않으며, 구현 이슈에 그 브랜치를 가리키는 [컨텍스트 포인터](../../assets/context-pointer.md)를 남깁니다. main은 깨끗하게 유지되고, 다음에 작업을 넘겨받는 사람이 프로토타입을 찾아 다시 실행할 수 있습니다.

## 자주 묻는 질문

**잠깐, 프로토타입은 삭제해야 하는 것 아니었나요?**
이제는 아닙니다. 전에는 그랬습니다. 만들고, 답을 보관하고, 코드는 버립니다. 그에 대한 가장 강한 반론은 속도에 관한 것이 아니었습니다. *다음 [세션](../../assets/session.md)에서 작업을 넘겨받는 사람이 무엇을 바탕으로 일하는가?*였습니다. 프로토타입의 산문 요약은 그것을 설득력 있게 만든 것을 잃습니다. 그래서 스킬은 이제 프로토타입을 [1차 자료](../../assets/primary-source.md)로 취급합니다. main이 아닌 `prototype/<name>` 브랜치에 착지하고 구현 이슈가 그것을 가리킵니다. 바뀐 것은 코드가 사는 곳이지 규율이 아닙니다. 여전히 main에 병합되지 않습니다.

**전에는 터미널 앱을 만들었습니다. 그건 어떻게 됐나요?**
로직 갈래는 이제 대신 공유 가능한 HTML 파일 하나를 내보냅니다. 터미널 앱은 저장소를 클론하고 런타임을 설치한 사람만 조작할 수 있어서, 프로토타입이 의견을 필요로 하는 사람들, 곧 디자이너, PM, 상태 모델이 무엇을 뜻해야 하는지 아는 도메인 전문가를 배제합니다. 더블클릭으로 열리고 이메일로 보내도 동작하는 독립적인 파일 하나는 누구나 조작할 수 있습니다. 그 밑의 순수 로직 모듈은 그대로이고, 여전히 실제 코드로 옮기는 부분입니다.

**구현해야 하는데 에이전트가 `/prototype` 하라고 했습니다.**
알려진 이름 문제입니다. 흐름을 모르는 에이전트는 `prototype`이라는 일반적이고 매력적인 단어를, 티켓이 존재하면 "뻔한 다음 단계"로 읽습니다. 그래서 대화에서 설계가 정리된 곳에서도 에이전트가 이름으로 추천합니다. 무엇을 만들지 이미 안다면 다음 단계는 티켓마다 `/implement`입니다. 구체적인 설계 질문이 풀리지 않았고 말로는 풀 수 없을 때만 프로토타입을 쓰세요.

**프로덕션 기능을 만들기 전에 애플리케이션 전체를 프로토타이핑해야 하나요(예를 들어 잠재 고객에게 시연하려고)?**
그것은 이 스킬과 이름만 같은 다른 산출물입니다. 여기서 프로토타입은 질문 하나로 범위가 한정되며, "앱 전체는 무엇인가?"는 질문이 아닙니다. 앱 전체 프로토타입은 자연스러운 멈춤 지점이 없어서 프로덕션 앱으로 표류합니다. 정리 패스는 일어나지 않고, 프로토타입 규칙(테스트 없음, 에러 처리 없음) 아래서 쓴 코드가 사용자 앞에 놓입니다. 영업용 시연이 필요하다면 일부러 시연으로 만들고 그중 어느 것도 프로덕션이 아니라고 분명히 하세요. 설계 질문을 정리해야 한다면 그 질문으로 줄이세요.

**별도의 세션에서 어떻게 실행하나요?**
프로토타입은 자기 디렉터리에 있고 질문을 던진 스레드에는 원치 않는 [컨텍스트](../../assets/context.md)를 많이 만들어 내므로, 다른 곳에서 실행하고 답만 가져오세요. 작업을 그 세션으로 옮기고 답을 되가져올 때는 [handoff](../../assets/skills-handoff.md)를 쓰세요.

**이건 토큰을 태우는 가장 빠른 방법 아닌가요?**
그럴 수 있습니다. 말로 답할 수 있었던 질문을 프로토타이핑하거나, 프로토타입 하나가 기능 전체로 번지게 두면 그렇습니다. 중요한 비교는 [토큰](../../assets/token.md) 대 0이 아니라, 토큰 대 잘못된 상태 모델을 만들고 프로덕션 호출자가 생긴 뒤에 알아내는 것입니다. 질문을 좁게 하고 실행을 짧게 유지하면 지출이 비례하게 유지됩니다.

## 잘 작동하는 신호

- 프로토타입이 답하려고 존재하는 질문을 한 문장으로 말할 수 있고, 그것이 머릿속에만 있지 않고 데모 맨 위에 적혀 있습니다.
- 코드를 읽지 않는 사람이 로직 데모를 조작할 수 있습니다. 파일을 열고, 워크스루 탭의 버튼을 누르고, 본 것을 자기 말로 설명합니다.
- 누군가 "잠깐, 이건 불가능해야 하는데"나 "어, 난 X라고 생각했는데"라고 말합니다. 그것이 *아이디어*의 버그이며, 프로토타입이 존재하는 이유입니다.
- UI 변형이 색과 카피만이 아니라 레이아웃과 정보 위계에 대해 의견이 다르고, 받는 피드백이 "B의 헤더에 C의 사이드바"입니다.
- 한 자리에서 답이 나옵니다. 하루 뒤에도 여전히 만들고 있다면 질문이 너무 컸으니 쪼개세요.
- 끝났을 때 main에는 결정이 있고 프로토타입은 하나도 없으며, 구현 이슈가 프로토타입을 여전히 담은 브랜치를 가리킵니다.

## 전체 흐름에서의 위치

`prototype`은 **언제든 찾는 독립형**입니다. 설계 질문 하나를 정리하려고 쓰고, 그다음 작업으로 돌아갑니다. 다른 스킬도 이것을 실행합니다.

이것을 가장 많이 실행하는 스킬은 [wayfinder](../../assets/skills-wayfinder.md)입니다. wayfinder 지도는 **의사결정 티켓**으로 이루어지고, `prototype`은 티켓의 네 유형 중 하나입니다. 막고 있는 질문이 "어떻게 보여야 하는가"나 "어떻게 동작해야 하는가"이고 어떤 논의로도 풀리지 않을 때 쓰는 것입니다. 논의가 모호할 때 wayfinder는 반응할 구체적인 무언가를 만들고, 이 스킬이 그것을 만듭니다. 답이 프로토타입 티켓을 해결하고, 지도는 프로토타입을 자산으로 링크합니다.

다른 이웃은 그 Upstream과 Downstream에 있습니다. [grill-me](../../assets/skills-grill-me.md)와 [grill-with-docs](../../assets/skills-grill-with-docs.md)는 집요하게 질문할 수 있는 질문에 답하고, 질문할 수 없는 것은 대신 여기로 오며, 한 줄짜리 답이 인터뷰로 돌아갑니다. Downstream에서는 검증된 상태 모델이나 UI 방향이 [to-spec](../../assets/skills-to-spec.md)의 정리된 입력이 되며, to-spec은 프로토타입이 만든 결정이 풍부한 조각을 산문으로 설명하지 않고 인라인으로 넣을 수 있습니다. 그 밖의 모든 것에는 [ask-me](../../assets/skills-ask-me.md)가 전체 집합에 걸쳐 안내합니다.
