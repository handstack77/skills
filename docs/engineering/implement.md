## 하는 일

`implement`는 이미 결정된 작업을 만듭니다. [티켓](../../assets/ticket.md), [명세](../../assets/spec.md), 또는 방금 대화에서 합의한 계획을 가리키면, 코드를 쓰고, 이음매에서 [tdd](../../assets/skills-tdd.md)를 몰고, 진행하면서 타입 검사를 하고, 끝에 [code-review](../../assets/skills-code-review.md)를 실행하고, 현재 브랜치에 커밋합니다.

계획을 다시 열지 않습니다. 인터뷰도, 되묻는 라운드도, 다른 접근의 제안도 없습니다. Upstream에서 정리된 것이 입력이고, 스킬의 일은 그것을 커밋으로 바꾸는 것입니다. 이것이 새 [에이전트](../../assets/agent.md)에게 "이걸 만들어"라고 입력하는 것과 다른 점입니다. 그 경우 만들면서 작업을 다시 설계하는 일이 자주 있습니다.

## 언제 쓰나

`/implement`를 직접 입력해서 호출하며, 에이전트가 스스로 꺼내지는 않습니다. `disable-model-invocation: true`로 배포되므로 다른 어떤 스킬도 이것을 호출할 수 없습니다. [ask-me](../../assets/skills-ask-me.md)나 [to-tickets](../../assets/skills-to-tickets.md)가 "그다음 티켓마다 `/implement`"라고 말하는 곳은 에이전트가 요청 없이 할 일이 아니라 당신에 대한 지시입니다.

작업이 현재 어디에 있는지가 이것이 맞는 스킬인지 정합니다.

| 작업이... | 쓸 것 |
| --- | --- |
| 트래커의 티켓 | `/implement #42`, [세션](../../assets/session.md)당 티켓 하나, 티켓 사이에 컨텍스트를 [비우기](../../assets/clearing.md) |
| 아직 쪼개지 않은 명세이고 빌드가 여러 세션에 걸침 | 먼저 [to-tickets](../../assets/skills-to-tickets.md), 그다음 티켓마다 `/implement` |
| 명세이고 빌드가 작음 | 명세에 대해 곧바로 `/implement` |
| 방금 한 대화 안에만 있고 여전히 작음 | 바로 그 창에서 `/implement` |
| 아직 어디에도 적혀 있지 않음 | [grill-with-docs](../../assets/skills-grill-with-docs.md), 코드베이스가 없으면 [grill-me](../../assets/skills-grill-me.md) |
| 명세 없이 테스트부터 만들고 싶은 구체적인 동작 하나 | [tdd](../../assets/skills-tdd.md)를 직접 |
| 이미 만들어졌고 검토받고 싶음 | [code-review](../../assets/skills-code-review.md)를 직접 |

같은 세션인 경우는 스킬 자신의 첫 줄이 다루지 않으므로 이름을 붙일 만합니다. `SKILL.md`는 "명세나 티켓"이라고 말해서 [모델](../../assets/model.md)이 존재하지 않는 파일을 찾게 몰아갑니다. 계획이 스레드에만 있다면 호출할 때 그렇게 말하세요.

## 선행 조건

`implement`는 지금 있는 브랜치에 커밋합니다. 브랜치를 만들지도, 묻지도 않습니다. 시작하기 전에 작업을 두고 싶은 브랜치에 있는지 확인하세요.

티켓이 [to-tickets](../../assets/skills-to-tickets.md)에서 왔다면, 그것이 있는 트래커는 [setup-me-skills](setup-me-skills.md)가 설정했습니다. `code-review`도 같은 설정을 읽어 마무리할 때 원래 명세를 찾습니다.

## 한 번의 실행이 하는 일

실행은 다섯 단계를 순서대로 거칩니다.

1. 티켓이나 명세를 읽고 이음매를 파악합니다.
2. 사전에 합의한 이음매에서 [tdd](../../assets/skills-tdd.md)를 몰며, 한 번에 red-green 슬라이스 하나씩 진행합니다.
3. 타입 검사를 자주 하고, 진행하면서 단일 테스트 파일을 실행합니다.
4. 전체 테스트 스위트는 끝에서 한 번 실행합니다.
5. [code-review](../../assets/skills-code-review.md)를 실행한 뒤 현재 브랜치에 커밋합니다.

한 번의 실행은 티켓 하나를 다룹니다. [to-tickets](../../assets/skills-to-tickets.md)가 만드는 티켓은 새로운 [컨텍스트 창](../../assets/context-window.md) 하나에 맞는 크기의 트레이서 불릿 수직 슬라이스이므로, 의도된 리듬은 이렇습니다. 컨텍스트 비우기, 티켓 하나 구현, 커밋, 다시 비우기. 각 티켓은 독립적이어서 직전 티켓의 컨텍스트는 버려도 됩니다.

## 사전에 합의한 이음매

스킬의 중심 아이디어는 **이음매(seam)**, 곧 내부에 손대지 않고 동작을 관찰하는 공개 경계입니다. 테스트는 이음매에 둡니다. 코드가 존재하기 전에 이음매에 합의하면 테스트가 오래가고, 테스트를 바꾸지 않고도 그 밑의 구현을 다시 쓸 수 있습니다.

"사전에 합의"가 중요하며, 스킬의 가장 약한 지점이기도 합니다. `implement` 안에서 이음매에 합의하는 것은 없습니다. 묻는 것은 `tdd` 스킬이며, 확인되지 않은 이음매에서는 테스트 쓰기를 거부합니다. 그래서 실제로 합의는 Upstream의 명세에서, 또는 실행의 첫 교환에서 이루어집니다. 어디서도 일어나지 않으면 실행이 "그냥 코드를 써라"가 되는데 아무것도 경고해 주지 않습니다. 명세에 이음매를 명시하는 것이 이를 막습니다.

## 자주 묻는 질문

**끝났는데 티켓이 여전히 열려 있고 인수 기준도 체크되지 않았습니다.**

맞고, 예상된 동작입니다. `implement`에는 완료 단계가 없습니다. 커밋에서 끝나고 작업 항목은 건드리지 않습니다. GitHub Issues와 로컬 마크다운 트래커에서 똑같으므로 트래커 통합 문제가 아닙니다. `code-review`가 만든 발견 사항에 따라 행동하지도 않고, 원래 이슈의 `- [ ]` 상자를 체크하지도 않습니다. 티켓을 닫고 기준을 직접 정리하세요. 의존성 사슬에서 가장 중요합니다. `to-tickets`가 프런티어를 차단하는 것이 모두 닫힌 티켓으로 정의하기 때문입니다. 아무것도 닫히지 않으면 눈에 보이게 차단이 풀리는 것이 없습니다.

**티켓을 한꺼번에 가리키거나 여러 개를 병렬로 실행할 수 있나요?**

`/implement`로는 안 됩니다. 호출 하나에 티켓 하나입니다. 명세 전체를 한 번에 하려면 [implement-spec](../../assets/skills-implement-spec.md)을 쓰세요. 준비된 프런티어의 각 티켓을 자기 워크트리의 [서브에이전트](../../assets/subagent.md)에게 주고, 결과를 하나의 통합 브랜치에 병합합니다. 한 체크아웃에서 `/implement` 세션 여럿을 나란히 실행하는 것은 지원되지 않는 것보다 나쁩니다. 한 현장 보고는 한 세션의 `git commit --amend`가 다른 세션의 커밋에 얹히고, stash가 `refs/stash`에서 사라지고, 커밋이 잘못된 브랜치에 착지한 일이 세 이슈에 걸쳐 한 오후에 모두 일어났다고 설명합니다. 세션들은 하나의 작업 디렉터리, 하나의 인덱스, 하나의 HEAD를 공유합니다. 사용자들은 git 워크트리로 우회하지만 `refs/stash`도 워크트리 사이에 공유되므로, 워크트리만으로는 stash 문제가 고쳐지지 않습니다.

**커밋하는 대신 풀 리퀘스트를 열 수 있나요?**

내장되어 있지 않습니다. 현재 브랜치에 곧바로 커밋합니다. 동작하는지 검증하기도 전에 코드가 착지하기 때문에 여러 사람이 이것을 너무 성급하다고 봅니다. 설정 플래그도 PR 모드도 없습니다. 사람들은 호출할 때("브랜치에 커밋하고 PR을 열어라") 또는 스킬의 로컬 사본을 편집해서 재정의합니다. 에이전트가 PR을 쓸 때는 [pr](../../assets/skills-pr.md)이 본문의 형태를 잡습니다.

**`code-review`가 제 변경 사항을 볼 수 없다고 합니다.**

`code-review`는 스테이징된 변경과 작업 트리 변경을 제외하는 `git diff <fixed-point>...HEAD`를 검토합니다. `implement`는 커밋하기 전에 이것을 실행하므로, 중간 커밋이 이미 있지 않으면 그 diff에는 검토할 것이 없습니다. 여러 사람이 이를 보고했고 양쪽 모두 아직 고쳐지지 않았습니다. 먼저 커밋하고, 브랜치를 딴 지점을 기준으로 검토하세요.

별개로, 어떤 사람들은 실행 안에서 리뷰하는 것을 전혀 원하지 않습니다. 방금 쓴 코드를 리뷰하는 에이전트는 자기 해결책에 편향되기 때문입니다. 새 세션에서 고정된 기준점에 대해 [code-review](../../assets/skills-code-review.md)를 실행하는 것은 유효한 대안입니다. 같은 편향이 그 스킬이 두 축을 별도의 서브에이전트에서 실행하는 이유입니다.

**티켓 하나가 150k 토큰을 태웠습니다. 잘못 쓰고 있나요?**

아마 아닙니다. 티켓이 너무 클 가능성이 더 높습니다. 한 번의 실행은 코드베이스 탐색, 이음매당 red-green 루프, 전체 스위트, 리뷰를 하므로, 사소하지 않은 티켓이 100k [토큰](../../assets/token.md)을 넘는 것은 무언가 고장 났다는 신호가 아니라 정상입니다. 해결은 Upstream에 있습니다. 각 티켓이 새 창 하나에 맞도록 [to-tickets](../../assets/skills-to-tickets.md)에서 티켓 크기를 맞추세요. 티켓 하나가 계속 넘친다면 [노력](../../assets/effort.md) 수준을 올리지 말고 쪼개세요.

**새 세션에서 `/implement #2`가 전혀 무관한 것을 작업했습니다.**

에이전트가 `#2`를 설정된 트래커가 아니라 컨텍스트의 다른 번호 매긴 목록, 예를 들어 할 일 파일이나 체크리스트에 대해 해석했습니다. `implement`는 이제 전달된 참조를 이슈 트래커에서 가져오고 시작하기 전에 제목을 말하며, 참조가 모호하면 되묻습니다. 그 제목이 의도한 티켓과 맞는지 확인하세요. 이슈 URL이나 `owner/repo#2`를 전달하면 모호함이 아예 사라집니다.

## 잘 작동하는 신호

- 세션이 무엇을 만들지 묻는 대신, 티켓이나 명세를 읽고 만들 것을 다시 말하며 시작합니다.
- 트레이스에서 단순히 diff에 테스트가 나타나는 것이 아니라 실제 `tdd` Skill 도구 호출이 보입니다.
- 실행 중에 타입 검사와 단일 테스트 파일이 반복해서 실행되고, 전체 스위트는 끝 무렵에 한 번 실행됩니다.
- 계속하라고 재촉하지 않아도 실행이 현재 브랜치의 커밋에 도달합니다.
- diff가 티켓 하나 분량의 변경입니다. 모든 계층을 통과하는 수직 슬라이스이지, 여러 티켓을 한꺼번에 쓸어 담은 것이 아닙니다.

## 전체 흐름에서의 위치

`implement`는 메인 체인의 빌드 단계입니다.

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review → retro
```

이웃은 이렇습니다. 소비하는 티켓을 만들고 순서를 정하는 차단 관계를 선언하는 [to-tickets](../../assets/skills-to-tickets.md), 각 이음매에서 내부적으로 모는 [tdd](../../assets/skills-tdd.md), 커밋하기 전에 실행하는 [code-review](../../assets/skills-code-review.md). 계획 스킬의 Downstream에 있으며 그것들을 신뢰합니다. 건네받은 것의 형태를 다시 검증하지 않으므로, 구조가 나쁜 지도나 수평으로 나뉜 티켓은 쓰인 그대로 만들어집니다.

그 신뢰가 [wayfinder](../../assets/skills-wayfinder.md)가 지도를 곧바로 `implement`로 돌리지 않고 [to-spec](../../assets/skills-to-spec.md)에서 체인에 합류하는 이유입니다. 지도에서 곧바로 `implement`로 가는 것은 작업이 작은 것으로 밝혀졌을 때만입니다.

어떤 흐름에 있는지 확신이 없을 때 전체 집합의 라우터는 [ask-me](../../assets/skills-ask-me.md)입니다.
