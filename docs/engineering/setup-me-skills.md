## 하는 일

`setup-me-skills`는 한 저장소에 대한 세 가지 질문에 답합니다. 이슈가 어디 있는지, 트리아지 라벨을 뭐라고 부르는지, 도메인 문서가 어디 있는지. 답은 `docs/agents/` 아래의 마크다운 파일로 기록합니다.

그 파일들이 저장소 사이에서 달라지는 유일한 것입니다. 스킬 자체는 어디서나 동일합니다. 실행할 때 `docs/agents/issue-tracker.md`를 읽고 그것이 말하는 대로 합니다. 그래서 이 모음이 GitHub에 묶여 있지 않고, 스킬 파일을 편집해 다른 트래커를 가리키게 할 필요가 없습니다. "스킬을 커스텀 이슈 트래커에 연결하라"로 호출하면 프로그램으로 연결할 수 있는 무엇이든 스킬 변경 없이 동작합니다.

결정적인 스크립트가 아니라 프롬프트 주도 스킬입니다. `git remote`, `CLAUDE.md`, `GLOSSARY.md`를 읽고, 찾은 것을 제안하고, 무엇이든 쓰기 전에 당신의 확인을 기다립니다.

## 언제 쓰나

Claude Code와 Codex CLI에서 플러그인을 설치한 뒤 각각 `/junchul-skills:setup-me-skills`, `$junchul-skills:setup-me-skills`로 호출하며, [에이전트](../../assets/agent.md)가 스스로 꺼내지는 않습니다. 메타데이터가 일부러 호출 불가로 표시해 두었으므로 다른 어떤 스킬도 대신 발동할 수 없습니다.

다른 엔지니어링 스킬을 처음 쓰기 전에 저장소당 한 번 쓰세요. [triage](../../assets/skills-triage.md), [to-spec](../../assets/skills-to-spec.md), [to-tickets](../../assets/skills-to-tickets.md), [wayfinder](../../assets/skills-wayfinder.md)가 이슈가 어디 가는지 짐작하기 시작하거나 트래커에 없는 라벨을 적용한다면, 이 저장소는 아직 설정되지 않은 것입니다. 프로젝트 중간의 저장소에서도 실행할 수 있습니다. 스킬이 이미 있는 것을 읽으므로 이전 작업을 잃지 않습니다.

## 선행 조건

실행한 저장소에 씁니다.

| 쓰는 것 | 위치 |
| --- | --- |
| `issue-tracker.md` | `docs/agents/` |
| `domain.md` | `docs/agents/` |
| `triage-labels.md` | `docs/agents/`, `triage` 스킬이 설치된 경우에만 |
| `## Agent skills` 블록 | `CLAUDE.md`나 `AGENTS.md` 중 이미 있는 쪽 |

전부 마크다운으로 커밋합니다. 사용자 수준이나 전역 모드는 없습니다. 설정이 저장소에 있으므로 저장소마다 자체 사본을 갖습니다.

## 세 가지 결정

각 섹션을 추천 답으로 시작하고, 탐색이 이미 답한 질문은 건너뜁니다. 대부분의 실행은 확인이 두 번이면 됩니다.

| 결정 | 제안하는 것 | 묻는 때 |
| --- | --- | --- |
| **이슈 트래커** | `git remote`와 일치하는 것 | 항상. 진짜 선택이 이것 하나이기 때문 |
| **트리아지 라벨** | 다섯 가지 표준 이름 유지(`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`) | `triage` 스킬이 설치된 경우에만 |
| **도메인 문서** | 단일 컨텍스트: 루트에 `GLOSSARY.md` 하나와 `docs/adr/` | 모노레포 신호를 발견한 경우에만이며, 그때 다중 컨텍스트 `GLOSSARY-MAP.md`를 제안 |

트래커 옵션:

| 옵션 | 이슈가 있는 곳 | 필요한 것 |
| --- | --- | --- |
| **GitHub** | 저장소의 GitHub Issues | `gh` CLI |
| **GitLab** | 저장소의 GitLab Issues | `glab` CLI |
| **로컬 마크다운** | 이 저장소의 `.scratch/<feature>/` 아래 파일 | 없음, 원격조차 필요 없음 |
| **기타** | 말하는 곳 어디든 | 워크플로를 설명하는 당신의 문단 하나 |

앞의 셋은 스킬에 템플릿으로 들어 있어 바로 동작합니다. 로컬 마크다운은 대체 수단이 아니라 완전한 옵션입니다. 스킬은 원격이 없는 혼자 하는 프로젝트를 지원합니다. 한 가지 주의: GitHub를 쓴다면 로컬 마크다운을 쓰지 마세요. 서로 대안이므로 하나만 고르세요.

"기타"도 완전한 옵션입니다. Jira, Linear, Azure DevOps, Beads가 모두 이렇게 동작합니다. 워크플로를 설명하면 스킬이 당신의 산문을 `docs/agents/issue-tracker.md`에 기록하고, Downstream의 스킬이 그 산문을 따릅니다. 사용자들이 이미 만들었습니다. [MCP](../../assets/mcp.md)를 통한 Jira 변형, `gh`와 비슷한 모양의 Gitea CLI, 손으로 만든 로컬 대시보드.

## 자주 묻는 질문

**GitHub를 써야 하나요?**

아니요. GitHub, GitLab, `.scratch/` 아래의 로컬 마크다운이 모두 준비된 템플릿으로 들어 있고, 그 밖의 것은 "기타" 경로로 동작합니다. 가장 많이 반복되는 질문이며, 대략 이런 표현입니다. *"github에 완전히 묶여 있다"*, *"GitLab / Jira를 쓸 수 있나요"*, *"Azure DevOps는요"*. 답은 늘 같습니다. 트래커를 고르는 것은 스킬이 아니라 설정입니다.

**스킬을 업데이트한 뒤 다시 실행해야 하나요?**

v1.1 이후의 직접적인 답은 예였습니다. 스킬 자신의 마무리 메시지는 더 부드럽습니다. 트래커를 바꾸거나 처음부터 다시 시작할 때만 다시 실행하라고 말합니다. 둘 다 방어할 수 있습니다. 시드 템플릿은 버전 사이에 바뀌므로, 이전 릴리스의 `docs/agents/issue-tracker.md`는 지금 그것을 읽는 스킬과 어긋나 낡을 수 있습니다. Downstream의 스킬이 문서가 설명하는 것과 다르게 동작하면 설정을 다시 실행하세요. 비용이 쌉니다.

**`CLAUDE.md`에 썼는데 저는 Codex를 씁니다.**

현재 CLI에 맞는 프로젝트 지침을 사용합니다. Claude Code에서는 `CLAUDE.md`, Codex CLI에서는 `AGENTS.md`에 `## Agent skills` 포인터를 기록합니다. 두 CLI를 함께 쓰면 두 파일이 동일한 `docs/agents/*.md`를 가리키도록 유지하세요. 기존 문서가 다른 파일에만 기록되어 있다면 현재 CLI의 지침 파일에도 공통 문서 포인터를 추가하세요.

**트리아지 라벨을 만들어 주지 않았습니다.**

만들지 않습니다. `docs/agents/triage-labels.md`는 *매핑*입니다. 트래커의 어떤 문자열이 다섯 가지 표준 역할에 해당하는지 `/triage`에 알려 줍니다. `gh label create`를 실행하지는 않습니다. 새 GitHub 저장소에는 라벨이 아직 없고, 사용자들이 이를 버그로 한 번 이상 등록했습니다. 두 가지 귀결:

- 트래커가 이미 표준 이름을 쓴다면 매핑은 항등 표이고 설정할 것이 없습니다. 빠진 단계가 아니라 의도된 흔한 경우입니다.
- 이 스킬은 [wayfinder](../../assets/skills-wayfinder.md)의 `wayfinder:map`과 `wayfinder:<type>` 라벨도 만들지 않으며, `gh issue create --label <missing>`은 라벨을 만들지 않고 실패합니다. GitHub 저장소에서 첫 wayfinder 실행 전에 손으로 만드세요.

**여기서 다른 스킬의 동작([집요한 질문](../../assets/grilling.md) 리듬, 질문 형식, 어조)을 설정할 수 있나요?**

아니요. 세 가지, 곧 트래커, 라벨, 문서 레이아웃만 설정합니다. 사용자별 선호의 자리로 만들어 달라는 요청이 있었습니다. 답은 스킬이 고집을 유지하고 사용자별 설정을 받지 않는다는 것입니다. 선호는 Claude Code의 `CLAUDE.md` 또는 Codex CLI의 `AGENTS.md`에 평범한 지시로 두세요.

**모든 저장소에 커밋하지 않고 `~/.claude`에 설정을 둘 수 있나요?**

지금은 안 됩니다. 스킬을 많은 저장소에서 쓰는 한 사용자가 이에 대한 열린 요청을 갖고 있지만, 사용자 수준 모드는 없습니다. 모든 저장소가 자체 `docs/agents/`를 갖습니다.

**다른 스킬을 설정하는 스킬이 있다는 게 이상하지 않나요?**

오래된 불만 하나가 그렇다고 말합니다. *"다른 스킬을 설정하는 스킬이 있다는 게 저는 옳게 느껴지지 않습니다. LLM이 자기 스킬을 스스로 설정한다는 뜻이니까요."* 트레이드오프는 진짜입니다. 설정 단계가 없다면 이슈에 닿는 모든 스킬이 트래커 지시의 자체 사본을 가져야 합니다. 출력이 읽고 편집할 수 있는 마크다운이어서 위험이 제한됩니다. 쓰인 모든 파일을 읽고 손으로 바꿀 수 있습니다. 일상적인 변경은 또 한 번 실행하는 대신 그렇게 하세요.

## 잘 작동하는 신호

- `docs/agents/issue-tracker.md`와 `docs/agents/domain.md`가 있고, `triage`가 설치되었다면 `triage-labels.md`도 있습니다.
- 하니스가 읽는 지시 파일에 `## Agent skills` 섹션이 나타나며, 각 파일을 가리키는 한 줄 요약이 있습니다.
- 제안한 트래커가 쓰는 원격과 일치하고, 라벨 문자열이 트래커에 있는 라벨과 일치합니다.
- 그 뒤에 `/to-tickets`가 이슈가 어디 있는지 묻지 않고 게시하고, `/triage`가 라벨을 지어내지 않고 적용합니다.
- 스킬 파일 자체에서는 아무것도 바뀌지 않았습니다. 설정이 `SKILL.md`를 편집했다면 무언가 잘못된 것입니다.

## 전체 흐름에서의 위치

`setup-me-skills`는 엔지니어링 흐름의 **한 번만 실행하는 설정**이며, 체인의 한 단계가 아니라 다른 모든 것이 가정하는 전제 조건입니다. 이웃은 읽는 쪽입니다. 여기서 쓴 라벨 어휘를 적용하는 [triage](../../assets/skills-triage.md), 여기서 지명한 트래커에 게시하는 [to-spec](../../assets/skills-to-spec.md)과 [to-tickets](../../assets/skills-to-tickets.md), 같은 트래커 파일의 "Wayfinding operations" 섹션을 읽어 지도와 자식 [티켓](../../assets/ticket.md)을 어떻게 저장할지 배우는 [wayfinder](../../assets/skills-wayfinder.md). [domain-modeling](../../assets/skills-domain-modeling.md)은 나중에 설정이 기록한 도메인 문서 레이아웃을 채웁니다. 용어나 결정을 정리할 때만 `GLOSSARY.md`와 ADR을 만들므로, 설정 뒤에 도메인 문서가 없는 저장소는 정상입니다. 다음에 어느 스킬을 쓸지는 [ask-me](../../assets/skills-ask-me.md)가 전체 집합에 걸쳐 안내합니다.
