## 하는 일

`implement-spec`은 [명세](../../assets/spec.md)와 그 [티켓](../../assets/ticket.md)을 받아서 전체를 한 번의 실행으로 착지시킵니다. 조율하는 [에이전트](../../assets/agent.md)가 각 티켓을 자기 git 워크트리에서 일하는 구현자 [서브에이전트](../../assets/subagent.md)에게 넘기고, 끝난 각 브랜치를 하나의 **통합 브랜치**에 병합하고, 결과에 대해 [code-review](../../assets/skills-code-review.md)를 실행하고, 티켓을 해결합니다.

티켓을 목록이 아니라 **작업 그래프**로 읽습니다. 차단 관계가 무엇이 시작할 수 있는지 정하므로, 어느 순간에든 차단하는 것이 모두 착지한 티켓의 **프런티어**가 있고, 프런티어의 모든 티켓이 한꺼번에 실행됩니다. 티켓을 하나씩 처리하는 것과의 차이가 그것입니다. 속도를 정하는 것은 트래커에 있는 티켓의 순서가 아니라 그래프의 모양입니다.

## 언제 쓰나

`/implement-spec`을 입력해서 호출하며, 에이전트가 스스로 꺼내지는 않습니다.

| 당신의 상황 | 쓸 것 |
| --- | --- |
| 차단 관계가 있는 티켓으로 쪼갠 명세를 한 번의 실행으로 착지시키고 싶음 | `/implement-spec` |
| 한 번에 티켓 하나, 자신의 [컨텍스트 창](../../assets/context-window.md)에서 티켓 사이에 [비우기](../../assets/clearing.md) | [implement](../../assets/skills-implement.md) |
| 아직 티켓으로 쪼개지 않은 명세 | 먼저 [to-tickets](../../assets/skills-to-tickets.md) |
| 실제 그래프가 없는 작은 작업 | [implement](../../assets/skills-implement.md)를 직접 |

## 선행 조건

- **이슈 트래커.** 스킬은 [setup-me-skills](setup-me-skills.md)가 설정한 트래커에서 티켓을 읽고 거기서 해결합니다. 설정된 것이 없으면 짐작하지 않고 멈춰서 먼저 그것을 실행하라고 알려 줍니다.
- [to-tickets](../../assets/skills-to-tickets.md)가 쓰는 대로의 **차단 관계가 있는 티켓**. 관계가 없으면 그래프가 평평하고 모든 티켓이 한꺼번에 시작합니다.
- **서브에이전트를 백그라운드로 실행하고 각각에 git 워크트리를 주는 [하니스](../../assets/harness.md).** 스킬은 티켓을 동시에 실행하려고 존재하므로, 서브에이전트를 한 번에 하나씩 실행하는 하니스에서는 더 느린 `implement`일 뿐입니다.

## 통합 브랜치

모든 것이 한 브랜치에 착지합니다. 각 구현자는:

1. 시작하기 전에 워크트리가 통합 브랜치를 기반으로 하는지 확인하고,
2. [tdd](../../assets/skills-tdd.md)로 티켓을 구현하며 한 번에 red-green 슬라이스 하나씩 진행하고,
3. 완료를 보고하기 전에 통합 브랜치의 끝을 자기 브랜치에 병합하므로, 착지는 fast-forward입니다.

풀 리퀘스트가 아예 존재하는지는 트래커가 정합니다. 트래커가 PR로 작업을 닫거나 당신이 요청하면, 스킬은 첫 병합 뒤에 초안 PR을 열고 끝에 리뷰 준비 상태로 표시합니다. 그렇지 않으면 실행은 트래커가 작업을 닫는 방식대로 모든 티켓이 해결된 채로 통합 브랜치에서 멈추며, 로컬 마크다운 트래커에서는 완전히 오프라인으로 동작합니다.

구현자는 붙여 넣은 요약이 아니라 [컨텍스트 포인터](../../assets/context-pointer.md)(명세, 티켓, 공유 탐색 노트, 이전 커밋)로 조율자와 소통합니다. 이렇게 하면 각 서브에이전트의 프롬프트가 작게 유지되고 조율자의 창에 그래프를 위한 여유가 남습니다.

## 자주 묻는 질문

**티켓마다 직접 `/implement`를 실행하는 것과 무엇이 다른가요?**

스킬이 답하려고 존재하는 질문입니다. 이것이 배포되기 전에 사람들은 자기만의 버전을 계속 만들었고, 한 사용자는 필요를 이렇게 설명했습니다. "명세에 티켓이 5개 넘게 있을 수 있는데 새 세션을 하나하나 만들어 티켓을 하나씩 구현하라고 말하는" 대신 "서브에이전트가 티켓을 구현하길" 원했습니다. `implement`에서는 당신이 디스패처입니다. 티켓당 [세션](../../assets/session.md) 하나, 사이에 비우기, 어느 티켓의 차단이 풀렸는지 직접 추적하기. `implement-spec`은 그 일을 조율하는 세션 하나에 넘깁니다. 대가는 각 티켓의 작업이 착지할 때 읽지 못하고 끝에 통합 브랜치를 검토한다는 점입니다. 실행을 시작하려면 컨텍스트를 비우고 명세를 가리키는 포인터(이슈 번호나 파일 경로)와 함께 `/implement-spec`을 입력하세요. 실제 그래프가 없는 작은 변경이라면 건너뛰고 `implement`를 직접 쓰세요.

**GitHub가 필요한가요? 브랜치에서 멈추게 하고 싶습니다.**

아니요, 이제는 아닙니다. 진행 중이던 버전을 좋아한 한 사용자가 바로 이 불만을 가졌습니다. "끝에 GitHub 같은 온라인 저장소가 필요한 PR을 만듭니다. 같은 작업을 오프라인으로 하고 모든 작업이 병합된 브랜치에서 멈췄으면 좋겠습니다." 실행은 이제 통합 브랜치에서 끝납니다. PR은 설정된 트래커가 PR로 작업을 닫거나 당신이 요청할 때만 열리므로, 로컬 마크다운 트래커에서는 모든 티켓이 해결되고 작업이 브랜치에 병합된 채로 실행이 끝납니다.

**리뷰와 수정 루프가 몇 시간 돌았거나, 아직 만들어지지 않은 티켓을 계속 "수정"했습니다.**

둘 다 스킬이 `code-review`에 준 단 한 지점이 아닌 곳에서 `code-review`가 실행될 때 일어납니다. 코드를 명세 전체와 비교하므로 모든 티켓이 착지한 뒤에야 의미가 있습니다. 실행 도중에 돌면 만들어지지 않은 모든 티켓이 실패로 읽힙니다. 그러면 에이전트가 그 티켓을 만들고, 그것이 또 다른 리뷰를 발동합니다. 끝에서 스킬은 `code-review`를 한 번 실행하고 모든 발견 사항을 수정 서브에이전트 하나에 보내지만, 그 수정 뒤에 언제 멈출지는 아직 말하지 않습니다. 한 사용자는 티켓 다섯 개짜리 기능에서 "리뷰와 수정 루프에 대략 네 시간이 걸렸다"고 보고했습니다. 두 번째 넓은 리뷰가 시작되는 것이 보이면 수정된 발견 사항에 대한 집중 검사를 실행하고 멈추라고 하세요. 첫 리뷰가 실제 문제를 찾을 것으로 예상하세요. 실행의 출력은 리뷰가 완성하는 초안이지, 그 자체로 출시할 것이 아닙니다.

**implement처럼 tdd를 모나요?**

이제는 합니다. 처음에는 그러지 않았습니다. 진행 중이던 버전을 쓴 사용자들은 "구현자 서브에이전트가 /tdd 지시를 상속하지 않는다"는 것을 알아차렸고, 그래서 티켓 하나에서 명세 전체로 규모를 키우자마자 red-green이 멈췄습니다. 각 구현자는 이제 `tdd`로 티켓을 구현합니다. `implement` 세션에서처럼 이음매에 대화로 합의하는 단계는 여전히 없으므로, 이음매를 고정하고 싶다면 명세나 티켓에 이음매를 명시하세요.

**병렬로 실행하던 구현자 둘이 같은 파일에서 충돌했거나, 같은 것에 다른 이름을 골랐습니다.**

워크트리는 충돌을 없애지 않고 병합 시점으로 미룹니다. 티켓 텍스트에서 쓴 차단 관계는 각 티켓이 어떤 파일을 건드릴지에 대한 짐작이고, "코드베이스의 다른 부분"에 있는 두 티켓도 메시지 카탈로그, 설정 레지스트리, 타입 하나를 공유합니다. 각 구현자는 자기 티켓과 공유 노트만 보고 다른 구현자의 진행 중인 작업은 보지 못하므로, 한 사용자의 웹과 모바일 티켓은 같은 문자열을 `blockedSince`와 `blockedOn`으로 추가했습니다. 프런티어의 두 티켓이 공유 파일 하나를 건드릴 때는 둘 사이에 차단 관계를 추가해 차례로 실행하게 하거나, 탐색 노트에서 각 티켓이 추가하는 정확한 이름을 고정하세요.

**차단하는 것이 병합된 뒤에도 차단된 티켓이 시작되지 않습니다.**

GitHub의 알려진 문제입니다. 트래커의 blocked-by 수는 차단자가 *닫힐* 때만 줄어들고, 티켓은 보통 PR이 병합될 때 닫히며 그것은 실행의 끝입니다. 트래커는 시작 그래프의 올바른 출처이지만 실행 도중에는 낡은 것입니다. 조율자에게 어떤 티켓이 통합 브랜치에 병합되었는지 스스로 추적하고 그것으로 프런티어를 계산하라고 말하세요.

**티켓의 핵심 테스트가 워크트리 안에서 건너뛰어졌는데 초록으로 보고되었습니다.**

워크트리는 git이 추적하는 것만 담습니다. gitignore된 픽스처, 로컬 데이터베이스, 자격 증명을 읽는 테스트는 거기서 조용히 건너뛰어질 수 있습니다. 검증이 추적되지 않는 자료에 의존하는 티켓은 조율자에게 대신 메인 체크아웃에서 실행하라고 말하세요.

## 잘 작동하는 신호

- 그래프가 허락할 때마다 구현자 여럿이 차례로가 아니라 동시에 실행됩니다.
- 티켓이 실행 전체가 끝날 때가 아니라 마지막 차단자가 통합 브랜치에 착지하자마자 시작합니다.
- 모든 티켓의 트레이스에서 코드보다 먼저 실패하는 테스트와 함께 `tdd`가 실행됩니다.
- 통합 브랜치로의 병합이 충돌 해결이 아니라 fast-forward입니다.
- 실행이 모든 티켓이 해결된 하나의 브랜치에서 끝나며, 트래커가 원할 때만 PR이 있습니다.

## 전체 흐름에서의 위치

`implement-spec`은 티켓마다 [implement](../../assets/skills-implement.md)를 한 번씩 실행하는 것의 병렬 대안으로서 메인 체인의 빌드 단계입니다.

```txt
grill-with-docs → to-spec → to-tickets → implement-spec → retro
```

이웃은 작업 그래프로 읽는 차단 관계를 선언하는 [to-tickets](../../assets/skills-to-tickets.md)와, 마무리 전에 통합 브랜치에 대해 실행하는 [code-review](../../assets/skills-code-review.md)입니다. 어떤 흐름에 있는지 확신이 없을 때 전체 집합의 라우터는 [ask-me](../../assets/skills-ask-me.md)입니다.
