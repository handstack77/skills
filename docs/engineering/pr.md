## 하는 일

`pr`은 풀 리퀘스트 본문의 형태를 정의합니다. 변경을 보여 주는 **요약**, 동작함을 보여 주는 **증거**, 병합하는 것이 얼마나 위험한지에 대한 **병합 위험** 판단입니다. 워크플로가 아니라 형식 참고서입니다. 브랜치를 푸시하지도, PR을 열지도, 무엇이 들어갈지 결정하지도 않습니다. [에이전트](../../assets/agent.md)가 본문을 쓸 때 어떤 모습이어야 하는지를 알려 줍니다.

요약은 문단이 아니라 시각 자료입니다. 기본 PR 본문은 diff를 산문으로 설명합니다. 이것은 핵심을 분명히 하는 **가장 작은 뷰**(의사코드, 호출 트리, 컴포넌트 트리, 파일 트리, Mermaid 다이어그램, 또는 형태를 잡은 diff)를 고르고 그 주변의 말은 짧게 유지합니다. 리뷰어는 이미 diff를 열어 놓았으므로, 본문은 읽기 전에 그 형태를 보여 줍니다.

## 언제 쓰나

`/pr`을 입력하거나, 에이전트가 PR 본문을 쓸 때마다 자동으로 꺼내 씁니다.

| 당신의 상황 | 쓸 것 |
| --- | --- |
| 브랜치가 준비되었고 리뷰어가 훑어볼 수 있는 본문이 필요함 | `pr` |
| 코드는 쓰였지만 아직 아무도 리뷰하지 않음 | 먼저 [code-review](../../assets/skills-code-review.md), 그다음 `pr` |
| PR이 열렸고 리뷰 댓글이 돌아옴 | 아직 이 모음에는 없음. `pr`은 본문만 씁니다 |

## 템플릿

세 섹션이며 이 순서입니다.

- **요약**: 작은 시각 자료 하나 이상, 각각 그것이 뒷받침하는 짧은 글 옆에 둡니다. 하나, 때로는 여러 개를 쓰고 전부 쓰는 일은 드뭅니다. 리뷰어에게 필요한 호출, 파일, props, 경계만 남기세요.
- **증거**: 이전과 이후. 변경이 시각적이고 [환경](../../assets/environment.md)이 하나 찍을 수 있다면 스크린샷이 가장 강한 증거입니다. 그렇지 않다면 실패했다가 이제 통과하는 정확한 테스트를 의사코드로 쓰거나, 바뀐 콘솔 출력을 쓰세요.
- **병합 위험**: 변경이 **일방향 문**인지 **양방향 문**인지, 그리고 그 **영향 범위**. 양방향 문은 되돌리기 쉽고, 일방향 문(파괴적인 마이그레이션, 공개 API 제거, 되돌리기 어려운 결정)은 그렇지 않습니다. 영향 범위는 변경이 틀렸을 때 무엇이 깨질 수 있는지를 이름으로 부릅니다. 레이아웃 이동, API 소비자, 모바일 반응형.

문 판단이 핵심 아이디어입니다. "병합해도 안전한가?"를 직감에서 리뷰어가 반박할 수 있는 명시된 주장으로 바꿉니다. 그리고 [사람의 검토](../../assets/human-review.md)를 어디에 쓸지도 알려 줍니다. 영향 범위가 작은 양방향 문은 훑어보고, 일방향 문은 천천히 읽으세요.

## 자주 묻는 질문

**에이전트 자신의 문 판단을 믿어도 되나요?**

맹목적으로는 안 되며, 그것이 명시하는 요점입니다. 변경을 쓴 에이전트가 그것을 채점하는 것이므로, "양방향, 작은 영향 범위"라고 할 때 가장 의심하세요. diff는 변경을 되돌릴 수 있는지를 숨기는 경우도 많습니다. 한 사용자의 말로, "커밋을 롤백해도 보낸 이메일 묶음은 취소되지 않습니다." 플래그를 건 롤아웃은 새 형식으로 첫 쓰기가 착지하기 전까지만 양방향입니다. 스킬은 에이전트에게 체크리스트가 아니라 정의(파괴적인 동작과 되돌리기 어려운 결정은 일방향)를 줍니다. 그러니 병합 위험 줄을 가장 신중하게 확인하세요. 두 가지가 도움이 됩니다. 에이전트가 diff만이 아니라 [티켓](../../assets/ticket.md)이나 [명세](../../assets/spec.md)를 앞에 두게 하고, 저장소가 항상 일방향으로 취급하는 변경(스키마 마이그레이션, 바깥으로 나가거나 삭제하는 모든 것)을 에이전트가 판단하기 전에 읽을 곳에 적어 두세요.

**PR도 대신 열어 주나요?**

아니요. `pr`은 본문만 다룹니다. [implement](../../assets/skills-implement.md)는 현재 브랜치에 커밋하는 것으로 끝납니다. PR을 여는 스킬이나 옵션(`/to-pr`, 또는 커밋하는 대신 PR을 여는 `implement`)에 대한 요청은 아직 열려 있는 제안입니다. 한 사용자의 우회책은 `implement`에 PR을 열라고 알리는 한 문장짜리 로컬 재정의입니다. [implement-spec](../../assets/skills-implement-spec.md)은 예외입니다. 이슈 트래커가 PR로 작업을 닫거나 당신이 요청하면 초안 PR을 엽니다. `pr`은 모델 호출형이므로, PR을 열어 달라고 할 때마다 에이전트가 본문에 이 형태를 씁니다.

**그냥 또 다른 텍스트와 다이어그램의 벽이 나오지 않을까요?**

스킬은 그것을 막도록 설계되었지만 여전히 일어날 수 있습니다. 에이전트 PR 본문에 대한 사용자들의 불만은 일관됩니다. "긴 요약이지만 내가 알아야 할 것은 무엇이 바뀌었는지, 어떻게 검증했는지, 무엇이 깨질 수 있는지, 병합해도 안전한지뿐입니다." 스킬은 에이전트에게 서두를 건너뛰고, 산문을 짧게 하고, 가장 작은 뷰(보통 시각 자료 하나이고 전부는 드묾)를 고르라고 합니다. 그래도 다이어그램 더미를 받는다면 에이전트가 그것을 무시한 것입니다. diff가 커서 본문이 크다면 문제는 PR의 크기이며, `pr`이 쪼개 주지는 않습니다.

**저장소에 이미 PR 템플릿이 있습니다. 어느 쪽이 이기나요?**

기본적으로 어느 쪽도 아닙니다. `pr`은 자체 템플릿이 있고 `.github/pull_request_template.md` 같은 것을 찾지 않습니다. 여러 사용자가 스킬이 저장소의 템플릿을 쓰기를 요청했습니다. 아무것도 하지 않으면 에이전트는 같은 문서에 대해 충돌하는 지시를 둘 가집니다. 저장소의 에이전트 문서에서 정리하세요. 예를 들어 저장소 템플릿을 채우고 그 아래에 요약, 증거, 병합 위험을 넣는 식입니다.

**출력이 HTML인가요? Mermaid 다이어그램이 왜 렌더링되지 않나요?**

출력은 HTML 페이지가 아니라 마크다운 PR 본문입니다. GitHub와 GitLab은 PR 설명의 Mermaid 블록을 렌더링하지만 터미널은 하지 않으므로, 에이전트가 로컬에서 보여 주는 동안 다이어그램은 원문 텍스트로 보입니다. CLI 하니스 사용자들은 ASCII Mermaid 렌더러를 쓰거나 에이전트가 HTML 버전을 PR에 첨부하게 해서 우회했습니다. Mermaid는 여섯 뷰 중 하나입니다. 호출 트리, 파일 트리, 형태를 잡은 diff는 어디서나 똑같이 읽힙니다.

**돌아오는 리뷰 댓글을 분류해 줄 수 있나요?**

아니요. 본문을 쓰고 멈춥니다. 사용자들은 다른 개발자나 리뷰 봇의 댓글을 분류하는 방법(어느 것이 대응할 가치가 있고 어느 것이 문제가 아닌지)을 여러 번 요청했습니다. 이 스킬은 그것을 하지 않습니다.

**PR이 바뀌면 본문을 최신으로 유지하나요?**

아니요. 한 시점에 본문을 쓰고, 리뷰 중에 바뀌는 PR은 그 본문을 낡게 둡니다. 큰 변경 뒤에는 에이전트에게 본문을 다시 쓰라고 요청하세요. 에이전트가 PR 본문을 다시 쓰는 것이므로 같은 형태를 씁니다.

**제 변경에는 UI가 없습니다. 증거에 무엇을 넣나요?**

스크린샷을 뺀 모든 것입니다. 스크린샷이 가장 강한 증거인 것은 변경이 시각적일 때뿐입니다. 마이그레이션, 백그라운드 잡, 리팩터링이라면 증거는 이전에 실패했다가 이제 통과하는 정확한 테스트나 바뀐 콘솔 출력입니다. "테스트가 초록"만으로는 이전과 이후가 아니라 주장입니다.

**본문에 LLM이 썼다고 표시할 수 있나요?**

스스로는 안 됩니다. 한 사용자의 방식은 에이전트가 쓰는 모든 이슈, 댓글, PR이 공개 고지 줄로 끝나게 하는 상시 지시를 저장소의 에이전트 문서에 두는 것입니다. 그 규칙은 한 종류의 문서를 위한 템플릿이 아니라, 에이전트가 게시하는 모든 것을 다루는 저장소에 속합니다.

## 잘 작동하는 신호

- diff를 열기 전에 요약의 시각 자료만으로 PR이 무엇을 바꾸는지 알 수 있습니다.
- 본문에 서두가 없습니다. 요약 제목에서 시작합니다.
- 증거 섹션이 테스트가 통과한다는 주장이 아니라 이전과 이후를 보여 줍니다.
- 모든 PR이 문과 영향 범위를 밝히며, 일방향 문은 당신이 속도를 늦추는 것들입니다.

## 전체 흐름에서의 위치

빌드가 풀 리퀘스트로 출시될 때 `pr`은 리뷰와 회고 사이에 옵니다. `to-spec → to-tickets → implement → code-review → pr → retro`. 모델 호출형이므로 그 체인 밖에서 에이전트가 PR 본문을 쓸 때마다 스스로 발동하기도 합니다.

- [code-review](../../assets/skills-code-review.md)가 그 앞에서 실행됩니다. PR 본문은 이미 리뷰된 diff를 설명해야 하기 때문입니다.
- [implement](../../assets/skills-implement.md)가 본문이 설명하는 커밋을 만듭니다.

어느 스킬이 상황에 맞는지 확신이 없을 때는 [ask-me](../../assets/skills-ask-me.md)가 전체 집합에 걸쳐 안내합니다.
