# TS 깊은 모듈 설정

이 저장소의 모든 패키지를 **깊은 모듈**로 만드세요. 작은 인터페이스 뒤에 많은 동작이 있는 모듈입니다. 패키지의 공개 표면은 **진입점**(패키지 루트의 파일들)이고, 그 하위 폴더에 있는 모든 것은 숨겨집니다. 이 스킬은 [dependency-cruiser](https://github.com/sverweij/dependency-cruiser)와, 진입점을 유일한 출입구로 만드는 규칙을 설치한 뒤 규칙이 실제로 작동함을 증명합니다.

어휘(깊은 모듈, 인터페이스, 이음매, 깊이)는 Skill 도구로 "codebase-design"을 호출해서 확인하고, 그 언어를 끝까지 쓰세요.

## 이 스킬이 강제하는 형태

```
src/packages/
  <name>/
    index.ts        ← 진입점(공개). 바깥에서는 이것을 import한다.
    client.ts       ← 또 다른 진입점. 패키지는 여러 개를 노출할 수 있다.
    lib/            ← 구현: 바깥에는 숨겨지고, 서로는 자유롭게 import한다.
    tests/          ← 같은 위치의 테스트 + 픽스처 (하위 폴더이므로 비공개).
```

공개 표면은 지정된 `index.ts` 하나가 아니라 패키지의 **루트 파일들**입니다. 관례상 구현은 `lib/`에, 테스트는 `tests/`에 두어서 모든 패키지가 같은 두 폴더 형태를 갖습니다. 하지만 규칙 자체는 일반적입니다. *어떤* 하위 폴더에 있는 *무엇이든* 비공개이므로, 폴더를 추가하려고 설정을 확장할 일이 없습니다.

규칙 네 개, 모두 `error`입니다.

1. **진입점 경계**: 패키지 바깥의 코드(앱 코드나 다른 패키지)는 그 패키지의 진입점(루트 파일들)만 import할 수 있고, 하위 폴더에 있는 것은 절대 import할 수 없다.
2. **패키지 내부의 자유**: 패키지 자신의 파일들은 서로 자유롭게 import한다.
3. **진입점을 통한 테스트**: `<pkg>/tests/` 아래의 파일은 모든 패키지의 진입점과 자신의 `tests/` 픽스처를 import할 수 있지만, 어떤 패키지의 하위 폴더 내부(자기 것도)는 절대 안 된다. 패키지를 가로지르는 통합 테스트는 괜찮고, 깊은 import는 안 된다.
4. **순환 없음**: 의존성 순환이 없다.

**배럴이 아닌 진입점.** 공개 표면이 *모든* 루트 파일이므로, 패키지는 모든 것을 거대한 `index.ts` 하나로 몰아넣는 대신 작은 진입점 여럿(`index.ts`, `client.ts`, `server.ts`)을 노출할 수 있습니다. 하위 트리 전체를 다시 export하는 배럴 파일은 권장하지 않습니다. 진입점은 작게 유지하고 구현은 하위 폴더에 숨기세요.

계층화(어떤 패키지가 어떤 패키지에 의존할 수 있는지)는 *다른* 관심사이며, 이 저장소가 채우도록 설정에 주석 처리된 스텁으로 남겨 둡니다.

## 단계

### 1. 환경 감지

- **패키지 매니저**: `pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, `bun.lockb` → bun, 그 외 npm. 아래 모든 명령에 이것을 쓰세요(`pnpm`/`yarn`/`npm run`/`bunx`).
- **패키지 루트**: `src/`가 있으면 `src/packages`, 없으면 `packages`를 쓰세요. 저장소에 이미 뚜렷이 다른 관례가 있다면 사용자와 선택을 확인하세요.
- **기존 설정**: `.dependency-cruiser.*` 파일이 있는지 확인하세요. 있다면 덮어쓰지 **마세요**. 규칙 네 개와 옵션을 병합하고, 무엇을 추가했는지 사용자에게 알리세요.

**완료 조건:** 패키지 매니저, 패키지 루트, 기존 설정 상태를 모두 알고 있습니다.

### 2. dependency-cruiser 설치

감지한 패키지 매니저로 `dependency-cruiser`를 devDependency로 설치하세요.

**완료 조건:** `dependency-cruiser`가 `devDependencies`에 있습니다.

### 3. 설정 쓰기

[`dependency-cruiser.config.cjs`](./dependency-cruiser.config.cjs)를 저장소 루트에 `.dependency-cruiser.cjs`로 복사하세요. `PACKAGES_ROOT`를 1단계에서 감지한 루트로 설정하세요. 규칙은 경로 깊이를 기반으로 하고 확장자에 구애받지 않으므로 다른 것은 맞출 필요가 없습니다.

**완료 조건:** 올바른 `PACKAGES_ROOT`로 `.dependency-cruiser.cjs`가 존재하고, 금지 규칙 네 개가 있습니다.

### 4. 검사에 연결

- `lint:boundaries` 스크립트를 추가하세요: `depcruise <packages-root>`(또는 `depcruise src`).
- 저장소의 포괄 검사 명령, 곧 이미 타입 검사를 실행하는 것(예: `check` / `ci` / `validate` 스크립트)에 넣으세요. `tsconfig`를 건드리거나 경로 별칭을 추가하지 **마세요**.
- 포괄 스크립트가 없다면 `lint:boundaries`를 추가하고 사용자에게 CI에 포함하라고 알리세요.

**완료 조건:** `lint:boundaries`가 있고 타입 검사와 같은 명령의 일부로 실행됩니다.

### 5. 예시 패키지 뼈대 만들기

복사해서 쓰는 템플릿으로 커밋된 `<packages-root>/example/`를 만드세요.

- `index.ts`는 진입점입니다. 내부 파일에 위임하는 함수 하나를 export하세요(패키지가 단순 통과가 아니라 눈에 보이게 *깊도록*).
- `lib/impl.ts`: **하위 폴더**에 있는 내부 파일이며, `index.ts`가 import하고 바깥에서는 도달할 수 없습니다.
- `tests/example.test.ts`는 **오직** `../index`(진입점)만 import하고 공개 함수에 대해 단언합니다.

사용자에게 이것은 복사하거나 삭제할 시작 템플릿이라고 알리세요.

**완료 조건:** 예시 패키지가 존재하고, 루트 진입점을 통해 동작을 노출하며, `impl`을 하위 폴더에 숨깁니다.

### 6. 규칙이 실제로 작동함을 증명

이것이 스킬 전체의 완료 기준입니다. 위반에서 실패하지 않는 설정은 가치가 없습니다.

1. `lint:boundaries`를 실행합니다. 깨끗한 예시에서는 **통과**해야 합니다.
2. `tests/example.test.ts`에 깊은 import를 임시로 추가합니다(예: `import { thing } from "../lib/impl"`). `lint:boundaries`를 다시 실행하면 `tests-through-entrypoints`로 **실패**해야 합니다.
3. 깊은 import를 되돌립니다. 한 번 더 실행하면 **통과**해야 합니다.

**완료 조건:** 통과, 그다음 깊은 import에서의 실패, 그다음 다시 통과를 관찰했습니다. 2단계가 실패하지 않으면 규칙이 올바르게 연결되지 않은 것이므로 끝내기 전에 고치세요.

### 7. 관례 문서화

**패키지 폴더 안에** `README.md`(`<packages-root>/README.md`, 그것이 관장하는 패키지들 옆)를 쓰세요. 다음을 담습니다. `src/packages/<name>/` 레이아웃(루트의 진입점, 구현용 `lib/`, 테스트용 `tests/`), "패키지의 진입점(루트 파일들)을 통해서만 import한다", 그리고 `lint:boundaries` 실행 방법. **배럴 파일을 명시적으로 권장하지 않는다고 적으세요.** 하위 트리 전체를 index 하나로 다시 export하는 대신 작은 진입점 여럿을 노출합니다. 복사해서 쓰는 스니펫과 규칙 네 개를 각각 한 문단으로 담는 정도로 유지하세요.

그다음 저장소의 에이전트 지시 파일(`CLAUDE.md`가 있으면 그것, 아니면 `AGENTS.md`이며 둘 다 없으면 `AGENTS.md`를 만듭니다)에서 그것을 가리키는 **컨텍스트 포인터**를 추가하세요. 한 줄이면 충분합니다. 예: `Packages are deep modules: see [src/packages/README.md](./src/packages/README.md) before adding or importing one.` 이것이 에이전트가 경계 규칙에 걸려 넘어지지 않고 발견하게 만듭니다.

**완료 조건:** `<packages-root>/README.md`가 존재하고 배럴을 권장하지 않으며, 저장소의 `CLAUDE.md`/`AGENTS.md`가 그것을 링크합니다.

## 참고

- 설정의 `$1` 역참조(dependency-cruiser의 그룹 매칭)가 패키지 자신은 내부에 도달하게 하고 외부인은 못 하게 하는 것입니다. 이것을 패키지별 개별 규칙으로 평탄화하지 마세요.
- 공개와 비공개는 **깊이**로 정해집니다. 패키지의 루트 파일은 진입점이고, 하위 폴더에 있는 것은 비공개입니다. 관례상의 하위 폴더는 `lib/`(구현)와 `tests/`이지만, 규칙은 이를 하드코딩하지 않습니다. 어떤 하위 폴더든 비공개이므로 새 폴더에 설정 변경이 필요 없습니다. 진입점을 추가하는 것은 루트 파일을 추가하는 것일 뿐입니다(배럴 없음).
- 패키지는 **평평합니다**. 루트 아래 직계 자식 한 단계. 패키지의 내부는 원하는 만큼 깊이 중첩될 수 있지만, 패키지가 다른 패키지를 포함할 수는 없습니다.
- `"type": "module"` 저장소에서도 설정의 `module.exports`가 동작하도록 `.cjs`(`.js`가 아니라)를 쓰세요.
