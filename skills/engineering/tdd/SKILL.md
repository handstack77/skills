# 테스트 주도 개발

TDD는 red → green 루프입니다. 이 스킬은 그 루프가 남길 가치가 있는 테스트를 만들어 내게 하는 참고서입니다. 좋은 테스트란 무엇인지, 테스트를 어디에 두는지, 안티패턴, 루프의 규칙을 다룹니다. 모든 섹션은 매 사이클마다 적용됩니다. 루프 전과 루프 중에 참고하고, 끝난 뒤에 보지 마세요.

코드베이스를 탐색할 때 `GLOSSARY.md`가 있으면 읽어서 테스트 이름과 인터페이스 어휘가 프로젝트의 도메인 언어와 맞게 하고, 건드리는 영역의 ADR을 존중하세요.

## 좋은 테스트란

테스트는 구현 세부 사항이 아니라 공개 인터페이스를 통해 동작을 검증합니다. 코드는 완전히 바뀔 수 있어도 테스트는 바뀌지 않아야 합니다. 좋은 테스트는 명세처럼 읽힙니다. "user can checkout with valid cart"는 어떤 기능이 존재하는지 정확히 알려 주고, 내부 구조에 관심이 없으므로 리팩터링에도 살아남습니다.

예시는 [tests.md](tests.md), 모킹 지침은 [mocking.md](mocking.md)를 보세요.

## 이음매(seam): 테스트를 두는 곳

**이음매(seam)**는 테스트하는 공개 이음매입니다. 내부에 손대지 않고 동작을 관찰하는 인터페이스입니다. 테스트는 이음매에 두고, 내부를 겨냥해서는 안 됩니다.

**사전에 합의한 이음매에서만 테스트하세요.** 테스트를 쓰기 전에 테스트 대상 이음매를 적고 사용자와 확인하세요. 확인되지 않은 이음매에서는 테스트를 쓰지 않습니다. 모든 것을 테스트할 수는 없으므로, 이음매를 미리 합의하는 것이 테스트 노력을 모든 엣지 케이스가 아니라 핵심 경로와 복잡한 로직에 쏟는 방법입니다.

"공개 인터페이스는 무엇이고, 어떤 이음매를 테스트해야 할까요?"라고 물으세요. 제안하는 이음매마다 무엇을 잡고 무엇을 놓치는지 한 줄 메모를 붙이세요.

인터페이스의 형태 자체가 문제일 때(모듈이 얼마나 깊은지, 이음매가 어디에 있어야 하는지, 인터페이스가 무엇을 노출해야 하는지)는 Skill 도구로 "codebase-design"을 호출해 어휘를 확인하세요. 모듈, 인터페이스, 깊이, 이음매, 어댑터, 레버리지, 지역성 용어의 공용 출처이며, 실행할 세션이 아니라 참고할 자료입니다.

## 안티패턴

- **구현 결합**: 내부 협력자를 모킹하거나, private 메서드를 테스트하거나, 부수 채널로 검증합니다(인터페이스를 쓰지 않고 데이터베이스를 직접 조회하는 식). 징후: 동작은 그대로인데 리팩터링하면 테스트가 깨집니다.
- **동어반복**: 단언이 코드가 하는 방식 그대로 기댓값을 다시 계산합니다(`expect(add(a, b)).toBe(a + b)`, 같은 방식으로 손으로 만든 스냅샷, 자기 자신과 같다고 단언하는 상수). 구성상 통과하고 코드와 절대 어긋날 수 없습니다. 기댓값은 독립된 진실의 원천에서 와야 합니다. 검증된 리터럴, 풀이가 있는 예시, 명세 같은 것입니다.
- **수평 슬라이싱**: 테스트를 전부 먼저 쓰고 나서 구현을 전부 쓰는 것. 한꺼번에 쓴 테스트는 _상상한_ 동작을 검증합니다. 사용자에게 보이는 동작이 아니라 사물의 _형태_를 테스트하게 되고, 실제 변경에 둔감해지며, 구현을 이해하기도 전에 테스트 구조에 매이게 됩니다. 대신 **수직 슬라이스**로 작업하세요. 테스트 하나 → 구현 하나 → 반복하며, 각 테스트는 직전 사이클에서 배운 것에 반응하는 **트레이서 불릿**입니다.

## 루프의 규칙

- **green 전에 red.** 실패하는 테스트를 먼저 쓰고, 그것을 통과시킬 만큼의 코드만 쓰세요. 미래의 테스트를 예상하거나 추측성 기능을 더하지 마세요.
- **한 번에 한 슬라이스.** 사이클마다 이음매 하나, 테스트 하나, 최소 구현 하나입니다.
- **리팩터링은 루프의 일부가 아닙니다.** 리팩터링은 red → green 구현 사이클이 아니라 리뷰 단계(`code-review` 스킬 참고)에 속합니다.
