# 도메인 모델링

설계하면서 프로젝트의 도메인 모델을 능동적으로 구축하고 다듬으세요. 이것은 *능동적인* 규율입니다. 용어에 이의를 제기하고, 엣지 케이스 시나리오를 만들어 내고, 용어집과 결정이 굳어지는 즉시 적어 둡니다. (어휘를 얻으려고 `GLOSSARY.md`를 *읽기만* 하는 것은 이 스킬이 아닙니다. 그건 어떤 스킬이든 할 수 있는 한 줄짜리 습관입니다. 이 스킬은 모델을 단순히 소비하는 게 아니라 바꿀 때를 위한 것입니다.)

## 파일 구조

대부분의 저장소는 컨텍스트가 하나입니다.

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

루트에 `GLOSSARY-MAP.md`가 있으면 저장소에 컨텍스트가 여러 개 있다는 뜻입니다. 맵이 각 컨텍스트의 위치를 가리킵니다.

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 시스템 전체 결정
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 컨텍스트별 결정
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

파일은 필요할 때 만드세요. 쓸 내용이 생겼을 때만 만듭니다. `GLOSSARY.md`가 없으면 첫 용어가 정리될 때 만들고, `docs/adr/`가 없으면 첫 ADR이 필요할 때 만듭니다.

## 세션 중에

### 용어집에 비추어 이의 제기하기

사용자가 `GLOSSARY.md`의 기존 언어와 충돌하는 용어를 쓰면 즉시 짚으세요. "용어집은 'cancellation'을 X로 정의하는데, Y를 뜻하시는 것 같네요. 어느 쪽인가요?"

### 모호한 언어 다듬기

사용자가 모호하거나 여러 뜻으로 쓰이는 용어를 쓰면 정확한 표준 용어를 제안하세요. "'account'라고 하셨는데, Customer를 말씀하시나요, User를 말씀하시나요? 둘은 다른 것입니다."

### 구체적인 시나리오 논의하기

도메인 관계를 논의할 때는 구체적인 시나리오로 압박 테스트를 하세요. 엣지 케이스를 파고드는 시나리오를 만들어서, 개념 사이의 경계에 대해 사용자가 정밀하게 답하도록 하세요.

### 코드와 교차 확인하기

사용자가 무언가의 동작 방식을 말하면 코드가 그와 일치하는지 확인하세요. 모순을 발견하면 드러내세요. "코드는 Order 전체를 취소하는데, 방금 부분 취소가 가능하다고 하셨어요. 어느 쪽이 맞나요?"

### GLOSSARY.md를 그 자리에서 갱신하기

용어가 정리되면 바로 `GLOSSARY.md`를 갱신하세요. 모아서 한꺼번에 하지 말고 일어나는 대로 기록하세요. [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)의 형식을 사용하세요.

`GLOSSARY.md`에는 구현 세부 사항이 전혀 없어야 합니다. `GLOSSARY.md`를 명세, 메모장, 구현 결정의 저장소로 취급하지 마세요. 용어집이고, 그 외에는 아무것도 아닙니다.

### ADR은 아껴서 제안하기

세 가지가 모두 참일 때만 ADR 작성을 제안하세요.

1. **되돌리기 어려움**: 나중에 마음을 바꾸는 비용이 의미 있게 크다
2. **맥락 없이는 의외임**: 미래의 독자가 "왜 이렇게 했지?" 하고 궁금해할 것이다
3. **진짜 트레이드오프의 결과**: 실제 대안이 있었고 구체적인 이유로 하나를 골랐다

셋 중 하나라도 빠지면 ADR은 건너뛰세요. [ADR-FORMAT.md](./ADR-FORMAT.md)의 형식을 사용하세요.
