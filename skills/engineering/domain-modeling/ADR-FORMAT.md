# ADR 형식

ADR은 `docs/adr/`에 두며 순번을 매깁니다. `0001-slug.md`, `0002-slug.md` 같은 식입니다.

`docs/adr/` 디렉터리는 필요할 때 만드세요. 첫 ADR이 필요할 때만 만듭니다.

## 템플릿

```md
# {결정의 짧은 제목}

{1~3문장: 맥락은 무엇이고, 무엇을 결정했으며, 왜 그렇게 했는가.}
```

이게 전부입니다. ADR은 한 문단일 수도 있습니다. 가치는 섹션을 채우는 데 있지 않고, 결정이 *내려졌다는 사실*과 *이유*를 기록하는 데 있습니다.

## 선택 섹션

진짜 가치를 더할 때만 넣으세요. 대부분의 ADR에는 필요 없습니다.

- **Status** frontmatter (`proposed | accepted | deprecated | superseded by ADR-NNNN`): 결정을 다시 검토할 때 유용
- **Considered Options**: 기각한 대안을 기억해 둘 가치가 있을 때만
- **Consequences**: 뻔하지 않은 Downstream 영향을 짚어야 할 때만

## 번호 매기기

`docs/adr/`에서 가장 큰 기존 번호를 찾아 1을 더하세요.

## ADR을 제안할 때

다음 세 가지가 모두 참이어야 합니다.

1. **되돌리기 어려움**: 나중에 마음을 바꾸는 비용이 의미 있게 크다
2. **맥락 없이는 의외임**: 미래의 독자가 코드를 보고 "도대체 왜 이렇게 했지?" 하고 궁금해할 것이다
3. **진짜 트레이드오프의 결과**: 실제 대안이 있었고 구체적인 이유로 하나를 골랐다

결정을 되돌리기 쉽다면 건너뛰세요. 그냥 되돌리면 됩니다. 의외가 아니라면 아무도 이유를 궁금해하지 않습니다. 진짜 대안이 없었다면 "뻔한 일을 했다" 외에는 기록할 것이 없습니다.

### 해당되는 경우

- **아키텍처의 형태.** "모노레포를 쓴다." "쓰기 모델은 이벤트 소싱이고, 읽기 모델은 Postgres로 프로젝션한다."
- **컨텍스트 사이의 통합 패턴.** "Ordering과 Billing은 동기 HTTP가 아니라 도메인 이벤트로 통신한다."
- **종속성을 낳는 기술 선택.** 데이터베이스, 메시지 버스, 인증 제공자, 배포 대상. 모든 라이브러리가 아니라, 교체하는 데 한 분기가 걸릴 만한 것만 해당합니다.
- **경계와 범위에 대한 결정.** "고객 데이터는 Customer 컨텍스트가 소유하며, 다른 컨텍스트는 ID로만 참조한다." 명시적인 "안 한다"도 "한다"만큼 가치가 있습니다.
- **뻔한 길에서 의도적으로 벗어난 선택.** "X 때문에 ORM 대신 수작업 SQL을 쓴다." 합리적인 독자가 반대로 짐작할 만한 모든 것. 다음 엔지니어가 의도적이었던 것을 "고치지" 못하게 막아 줍니다.
- **코드에서 보이지 않는 제약.** "컴플라이언스 요건 때문에 AWS를 쓸 수 없다." "파트너 API 계약 때문에 응답 시간은 200ms 미만이어야 한다."
- **기각 이유가 뻔하지 않은 기각된 대안.** GraphQL을 검토하고 미묘한 이유로 REST를 골랐다면 기록하세요. 그렇지 않으면 6개월 뒤에 누군가 다시 GraphQL을 제안할 것입니다.
