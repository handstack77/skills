이 스킬은 현재 대화의 맥락과 코드베이스에 대한 이해를 가져와 명세를 만듭니다. 사용자를 인터뷰하지 마세요. 이미 알고 있는 내용을 종합하기만 하세요.

이슈 트래커와 트리아지 라벨 어휘는 이미 제공되어 있어야 합니다. 그렇지 않다면 사용자에게 `/setup-me-skills`를 실행하라고 알려 주세요.

## 절차

1. 아직 하지 않았다면 저장소를 탐색해 코드베이스의 현재 상태를 파악하세요. 명세 전체에서 프로젝트의 도메인 용어집 어휘를 사용하고, 건드리는 영역의 ADR을 존중하세요.

2. 기능을 테스트할 이음매(seam)를 스케치하세요. 새 이음매보다 기존 이음매를 선호하세요. 가능한 한 가장 높은 이음매를 사용하세요. 새 이음매가 필요하면 가능한 가장 높은 지점에 제안하세요. 코드베이스 전체에서 이음매는 적을수록 좋고, 이상적인 개수는 하나입니다.

이 이음매가 사용자의 기대와 맞는지 확인하세요.

3. 아래 템플릿으로 명세를 쓰고 프로젝트 이슈 트래커에 게시하세요. `ready-for-agent` 트리아지 라벨을 붙이세요. 추가 트리아지는 필요 없습니다.

## Problem Statement

사용자가 직면한 문제를 사용자의 관점에서 서술합니다.

## Solution

문제에 대한 해결책을 사용자의 관점에서 서술합니다.

## User Stories

사용자 스토리의 번호 매긴 긴 목록. 각 사용자 스토리는 다음 형식이어야 합니다.

1. As an <actor>, I want a <feature>, so that <benefit>

<user-story-example>
1. As a mobile bank customer, I want to see balance on my accounts, so that I can make better informed decisions about my spending
</user-story-example>

이 사용자 스토리 목록은 매우 광범위해야 하며 기능의 모든 측면을 다뤄야 합니다.

## Implementation Decisions

내려진 구현 결정의 목록. 다음을 포함할 수 있습니다.

- 만들거나 수정할 모듈
- 수정될 해당 모듈의 인터페이스
- 개발자의 기술적 설명
- 아키텍처 결정
- 스키마 변경
- API 계약
- 구체적인 상호작용

구체적인 파일 경로나 코드 조각은 포함하지 마세요. 금세 낡아 버릴 수 있습니다.

예외: 프로토타입이 만든 코드 조각이 산문보다 정밀하게 결정을 담고 있다면(상태 머신, 리듀서, 스키마, 타입 형태), 해당 결정 안에 인라인으로 넣고 프로토타입에서 나왔다고 짧게 밝히세요. 동작하는 데모가 아니라 결정이 풍부한 부분만 추려서 중요한 부분만 넣으세요.

## Testing Decisions

내려진 테스트 결정의 목록. 다음을 포함하세요.

- 좋은 테스트란 무엇인지에 대한 설명 (구현 세부 사항이 아니라 외부 동작만 테스트)
- 어떤 모듈을 테스트할 것인가
- 테스트의 선행 사례 (예: 코드베이스의 비슷한 종류의 테스트)
