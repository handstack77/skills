name: code-review
description: "고정된 기준점(커밋, 브랜치, 태그, 또는 merge-base) 이후의 변경 사항을 두 축으로 검토합니다. 표준(코드가 이 저장소에 문서화된 코딩 표준을 따르는가?)과 명세(코드가 원래 이슈/명세가 요구한 것과 일치하는가?)입니다. 두 검토를 병렬 서브에이전트로 실행하고 나란히 보고합니다. 사용자가 브랜치, PR, 진행 중인 변경을 검토하고 싶을 때, 또는 \"X 이후로 리뷰해 줘\"라고 요청할 때 사용합니다."
---

`HEAD`와 사용자가 제공한 고정 기준점 사이의 diff에 대한 두 축 검토입니다.

- **표준(Standards)**: 코드가 이 저장소에 문서화된 코딩 표준을 따르는가?
- **명세(Spec)**: 코드가 원래 이슈 / 명세를 충실히 구현하는가?

두 축은 서로의 컨텍스트를 오염시키지 않도록 **병렬 서브에이전트**로 실행하고, 이 스킬이 그 결과를 취합합니다.

이슈 트래커는 이미 제공되어 있어야 합니다. 그렇지 않다면 사용자에게 `/setup-me-skills`를 실행하라고 알려 주세요.

## 절차

### 1. 기준점 고정하기

사용자가 말한 것이 기준점입니다(커밋 SHA, 브랜치 이름, 태그, `main`, `HEAD~5` 등). 지정하지 않았다면 물어보세요.

diff 명령을 한 번 확정하세요. `git diff <fixed-point>...HEAD`(점 세 개, 그래서 merge-base와 비교합니다). 커밋 목록도 `git log <fixed-point>..HEAD --oneline`으로 확인해 두세요.

더 나아가기 전에 기준점이 해석되는지(`git rev-parse <fixed-point>`), diff가 비어 있지 않은지 확인하세요. 잘못된 ref나 빈 diff는 병렬 서브에이전트 두 개 안이 아니라 여기서 실패해야 합니다.

### 2. 명세 출처 찾기

원래 명세를 다음 순서로 찾으세요.

1. 커밋 메시지의 이슈 참조(`#123`, `Closes #45`, GitLab `!67` 등). 트래커 문서의 워크플로로 가져옵니다.
2. 사용자가 인자로 전달한 경로.
3. 브랜치 이름이나 기능과 일치하는 `docs/`, `specs/`, `.scratch/` 아래의 명세 파일.
4. 아무것도 찾지 못하면 사용자에게 명세가 어디 있는지 물으세요. 없다고 하면 **명세** 서브에이전트는 건너뛰고 "사용 가능한 명세 없음"이라고 보고합니다.

### 3. 표준 출처 찾기

코드를 어떻게 써야 하는지 문서화한 모든 파일을 저장소에서 검색하세요. `CODING_STANDARDS.md`나 `CONTRIBUTING.md`가 있다면 반드시 목록에 있어야 합니다.

저장소가 문서화한 것에 더해, 표준 축에는 항상 아래의 **냄새 기준선**이 따라붙습니다. 저장소가 아무것도 문서화하지 않았을 때도 적용되는 Fowler 코드 스멜(_Refactoring_ 3장)의 고정된 집합입니다. 두 가지 규칙이 이를 묶습니다.

- **저장소가 우선합니다.** 문서화된 저장소 표준이 항상 이기며, 기준선이 지적할 것을 저장소가 허용한다면 그 스멜은 억제합니다.
- **항상 판단의 영역입니다.** 각 스멜은 레이블을 붙인 휴리스틱("Feature Envy 가능성")이며, 확정적인 위반이 아닙니다. 여기서 다른 표준들과 마찬가지로, 도구가 이미 강제하는 것은 건너뜁니다.

각 스멜은 *무엇인지* → *어떻게 고치는지* 순으로 적혀 있습니다. diff와 대조하세요.

- **Mysterious Name(알 수 없는 이름)**: 이름이 무엇을 하는지 또는 담는지 드러내지 않는 함수, 변수, 타입. → 이름을 바꾸세요. 정직한 이름이 떠오르지 않으면 설계가 불분명한 것입니다.
- **Duplicated Code(중복 코드)**: 같은 로직 형태가 변경 안의 둘 이상의 hunk나 파일에 나타남. → 공통 형태를 추출해 양쪽에서 호출하세요.
- **Feature Envy(기능 편애)**: 자기 데이터보다 다른 객체의 데이터에 더 많이 손을 뻗는 메서드. → 부러워하는 데이터 쪽으로 메서드를 옮기세요.
- **Data Clumps(데이터 뭉치)**: 같은 몇 개의 필드나 파라미터가 계속 함께 다님(태어나고 싶은 타입). → 하나의 타입으로 묶어 그것을 넘기세요.
- **Primitive Obsession(기본 타입 집착)**: 자기만의 타입을 가질 만한 도메인 개념을 대신하는 기본 타입이나 문자열. → 그 개념에 작은 전용 타입을 주세요.
- **Repeated Switches(반복되는 switch)**: 같은 타입에 대한 같은 `switch`/`if` 연쇄가 변경 곳곳에서 반복됨. → 다형성이나 두 곳이 공유하는 맵 하나로 바꾸세요.
- **Shotgun Surgery(산탄총 수술)**: 하나의 논리적 변경이 diff의 여러 파일에 걸친 흩어진 수정을 강요함. → 함께 바뀌는 것을 한 모듈로 모으세요.
- **Divergent Change(발산적 변경)**: 하나의 파일이나 모듈이 서로 무관한 여러 이유로 수정됨. → 각 모듈이 한 가지 이유로만 바뀌도록 쪼개세요.
- **Speculative Generality(추측성 일반화)**: 명세에 없는 필요를 위해 추가된 추상화, 파라미터, 훅. → 지우세요. 실제 필요가 나타날 때까지 다시 인라인하세요.
- **Message Chains(메시지 체인)**: 호출자가 의존해서는 안 되는 긴 `a.b().c().d()` 탐색. → 그 탐색을 첫 객체의 메서드 하나 뒤로 숨기세요.
- **Middle Man(중개자)**: 대부분 그냥 다음으로 위임하기만 하는 클래스나 함수. → 없애고 실제 대상을 직접 호출하세요.
- **Refused Bequest(거부된 유산)**: 상속받은 것의 대부분을 무시하거나 재정의하는 서브클래스나 구현체. → 상속을 버리고 컴포지션을 쓰세요.

### 4. 서브에이전트 둘을 병렬로 띄우기

두 서브에이전트 호출을 함께, 포그라운드로 보내고 돌아온 보고를 취합하세요.

**표준 서브에이전트 프롬프트**에 포함할 것:

- 전체 diff 명령과 커밋 목록.
- 3단계에서 찾은 표준 출처 파일 목록, **그리고 3단계의 냄새 기준선** 전문(서브에이전트는 달리 접근할 방법이 없습니다).
- 브리프: "필요한 경우 파일/hunk별로 다음을 보고하라. (a) diff가 문서화된 표준을 위반하는 모든 곳: 표준(파일 + 규칙)을 인용하라. (b) 발견한 기준선 스멜: 이름을 대고 해당 hunk를 인용하라. 확정적 위반과 판단의 영역을 구별하라. 문서화된 표준 위반은 확정적일 수 있지만 기준선 스멜은 항상 판단의 영역이며, 문서화된 저장소 표준이 기준선보다 우선한다. 도구가 강제하는 것은 건너뛰어라. 400단어 이내."

**명세 서브에이전트 프롬프트**에 포함할 것:

- diff 명령과 커밋 목록.
- 명세의 경로 또는 가져온 내용.
- 브리프: "다음을 보고하라. (a) 명세가 요구했지만 빠졌거나 부분적인 요구 사항. (b) 요구되지 않았는데 diff에 있는 동작(범위 확장). (c) 구현된 것처럼 보이지만 구현이 잘못된 것으로 보이는 요구 사항. 각 발견 사항마다 명세의 해당 줄을 인용하라. 400단어 이내."

명세가 없으면 명세 서브에이전트는 건너뛰고 최종 보고에 그 사실을 적으세요.

### 5. 취합

두 보고를 `## 표준 (Standards)`와 `## 명세 (Spec)` 제목 아래에, 원문 그대로 또는 가볍게 정리해서 제시하세요. 발견 사항을 합치거나 순위를 다시 매기지 **마세요**. 두 축은 의도적으로 분리되어 있기 때문입니다(_두 축인 이유_ 참고).

한 줄 요약으로 끝내세요. 축별 총 발견 건수와 _각 축 안에서_ 가장 심각한 문제(있다면)입니다. 축을 가로질러 하나의 승자를 고르지 마세요. 그것은 분리가 막으려는 바로 그 재순위화입니다.

## 두 축인 이유

변경은 한 축은 통과하고 다른 축은 실패할 수 있습니다.

- 모든 표준을 따르지만 엉뚱한 것을 구현한 코드 → **표준 통과, 명세 실패.**
- 이슈가 요구한 것을 정확히 하지만 프로젝트의 관례를 깨는 코드 → **명세 통과, 표준 실패.**

따로 보고하면 한 축이 다른 축을 가리는 것을 막을 수 있습니다.
