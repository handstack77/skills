# 트리아지

프로젝트 이슈 트래커의 이슈를 작은 트리아지 역할 상태 머신에 따라 이동시킵니다.

이 저장소가 외부 풀 리퀘스트를 요청 접점으로 취급한다면(이슈 트래커 설정 참고) 트리아지는 그것도 다룹니다. **PR은 코드가 첨부된 이슈**이며, 같은 역할, 같은 상태, 같은 머신을 쓰되 아래에서 "PR의 경우"로 표시한 몇 가지 차이가 있습니다. 단순한 `#42`는 트래커 설정에 따라 이슈 또는 PR로 해석하세요.

트리아지 중에 이슈 트래커에 게시하는 모든 댓글이나 이슈는 **반드시** 이 고지문으로 시작해야 합니다.

```
> *이 내용은 트리아지 중에 AI가 생성했습니다.*
```

## 참고 문서

- [AGENT-BRIEF.md](AGENT-BRIEF.md): 오래가는 에이전트 브리프를 쓰는 방법
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md): `.out-of-scope/` 지식 베이스가 동작하는 방식

## 역할

**범주** 역할 둘:

- `bug`: 무언가가 고장 남
- `enhancement`: 새 기능 또는 개선

**상태** 역할 다섯:

- `needs-triage`: 메인테이너가 평가해야 함
- `needs-info`: 제보자의 추가 정보를 기다리는 중
- `ready-for-agent`: 완전히 명세되어, AFK 에이전트가 바로 착수 가능
- `ready-for-human`: 사람이 구현해야 함
- `wontfix`: 처리하지 않음

PR의 경우 같은 상태를 첨부된 코드에 비추어 읽습니다. `ready-for-agent`는 브리프가 첨부되어 있고 에이전트가 diff에 대해 다음 단계를 밟아야 한다는 뜻이고, `ready-for-human`은 사람이 병합할 준비가 되었다는 뜻입니다.

트리아지된 모든 이슈는 범주 역할 정확히 하나와 상태 역할 정확히 하나를 달고 있어야 합니다. 상태 역할이 충돌하면 다른 무엇을 하기 전에 표시하고 메인테이너에게 물으세요.

이것은 표준 역할 이름입니다. 이슈 트래커에서 실제로 쓰는 라벨 문자열은 다를 수 있습니다. 그 매핑은 이미 제공되어 있어야 합니다. 그렇지 않다면 사용자에게 `/setup-me-skills`를 실행하라고 알려 주세요.

상태 전이: 라벨이 없는 이슈는 보통 먼저 `needs-triage`로 가고, 거기서 `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix` 중 하나로 이동합니다. `needs-info`는 제보자가 답하면 `needs-triage`로 돌아갑니다. 메인테이너는 언제든 재정의할 수 있습니다. 평소와 다른 전이는 표시하고 진행하기 전에 물으세요.

## 호출

메인테이너가 `/triage`를 호출하고 원하는 것을 자연어로 설명합니다. 요청을 해석해서 행동하세요. 예시:

- "내가 신경 써야 할 게 있으면 보여 줘"
- "#42를 살펴보자" (이슈 또는 PR)
- "#42를 ready-for-agent로 옮겨 줘"
- "에이전트가 집어 갈 수 있는 게 뭐지?"

## 주의가 필요한 것 보여 주기

이슈 트래커를 조회해서 오래된 순으로 세 개의 묶음을 제시하세요.

1. **라벨 없음**: 한 번도 트리아지되지 않음.
2. **`needs-triage`**: 평가 진행 중.
3. **마지막 트리아지 노트 이후 제보자 활동이 있는 `needs-info`**: 재평가가 필요함.

PR이 범위에 있으면 외부 PR을 이 묶음에 포함하고 각 줄에 `[PR]` 또는 `[issue]` 태그를 붙이세요. 발견은 *외부* PR만 보여 줍니다(누가 외부인지는 트래커 설정이 정의합니다). 따라서 협업자의 진행 중인 PR은 트리아지 대상이 아닙니다. 이 필터는 발견에만 적용됩니다. 명시적으로 지명된 PR은 작성자와 무관하게 항상 트리아지합니다.

개수와 항목당 한 줄 요약을 보여 주고, 메인테이너가 고르게 하세요.

## 특정 이슈나 PR 트리아지

1. **컨텍스트 모으기.** 이슈나 PR 전체(본문, 댓글, 라벨, 작성자, 날짜. PR이면 diff도)를 읽으세요. 이미 해결된 질문을 다시 묻지 않도록 이전 트리아지 노트를 파싱하세요. 프로젝트의 도메인 용어집을 사용해 코드베이스를 탐색하고, 해당 영역의 ADR을 존중하세요. 코드베이스에 대해 두 가지 확인을 하세요. (a) **중복**: 요청의 표현만이 아니라 도메인 개념으로 요청된 동작의 기존 구현을 검색하고, 어디를 찾아봤는지 보고하세요. 찾으면 이미 구현된 `wontfix`입니다(5단계). (b) **이전 기각**: `.out-of-scope/*.md`를 읽고 이 요청과 비슷한 것을 드러내세요.

2. **권고.** 메인테이너에게 당신의 범주와 상태 권고를 근거와 함께 알리고, 요청과 관련된 간단한 코드베이스 요약(이미 구현되어 있는지 포함)을 덧붙이세요. 지시를 기다리세요.

3. **주장 검증.** 집요한 질문을 던지기 전에 주장이 성립하는지 확인하세요. 버그라면 제보자의 단계로 재현하세요. PR이라면 diff가 주장하는 일을 하는지 확인하세요. 체크아웃하고 관련 테스트나 명령을 실행하세요. 일어난 일을 보고하세요. 확인됨(코드 경로와 함께), 실패, 또는 세부 정보 부족(강한 `needs-info` 신호). 확인된 검증은 훨씬 더 강력한 에이전트 브리프를 만듭니다.

4. **집요한 검증 (필요하면).** 요청을 구체화해야 한다면 Skill 도구를 두 번 호출해 "grilling"과 "domain-modeling"을 쓰고, 한 라운드의 질문씩 형태를 갖추도록 집요하게 검증하세요. 결정이 내려질 때마다 도메인 용어를 다듬고 `GLOSSARY.md`/ADR을 인라인으로 갱신하세요.

5. **결과 적용:**
   - `ready-for-agent`: 에이전트 브리프 댓글을 게시합니다([AGENT-BRIEF.md](AGENT-BRIEF.md)).
   - `ready-for-human`: 에이전트 브리프와 같은 구조이지만, 왜 위임할 수 없는지(판단이 필요한 사안, 외부 접근, 설계 결정, 수동 테스트)를 적으세요.
   - `needs-info`: 트리아지 노트를 게시합니다(아래 템플릿).
   - `wontfix`의 경우 이슈를 닫되, 댓글은 *이유*에 따라 달라집니다.
     - **이미 구현됨**: 변경이 이미 코드베이스에 존재합니다. 어디에 있는지 가리키세요. `.out-of-scope/`에는 쓰지 **마세요**(그 지식 베이스는 만들어진 것이 아니라 *기각된* 요청을 위한 것입니다).
     - **기각됨 (버그)**: 정중하게 설명한 뒤 닫습니다.
     - **기각됨 (개선)**: `.out-of-scope/`에 쓰고, 댓글에서 링크한 뒤 닫습니다([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
   - `needs-triage`: 역할을 적용합니다. 부분적인 진전이 있으면 선택적으로 댓글을 남깁니다.

## 빠른 상태 재정의

메인테이너가 "#42를 ready-for-agent로 옮겨"라고 하면 그를 믿고 역할을 바로 적용하세요. 하려는 일(역할 변경, 댓글, 닫기)을 확인한 뒤 실행하세요. 집요한 검증은 건너뜁니다. 집요한 검증 세션 없이 `ready-for-agent`로 옮기는 경우에는 에이전트 브리프를 작성하고 싶은지 물으세요.

## Needs-info 템플릿

```markdown
## Triage Notes

**지금까지 확인된 것:**

- 항목 1
- 항목 2

**여전히 필요한 것 (@reporter):**

- 질문 1
- 질문 2
```

집요한 검증 중에 해결된 모든 것을 "지금까지 확인된 것" 아래에 담아서 작업이 사라지지 않게 하세요. 질문은 "추가 정보를 제공해 주세요"가 아니라 구체적이고 실행 가능해야 합니다.

## 이전 세션 재개

이슈나 PR에 이전 트리아지 노트가 있으면 읽고, 제보자가 미해결 질문에 답했는지 확인한 뒤, 계속하기 전에 갱신된 그림을 제시하세요. 해결된 질문을 다시 묻지 마세요.
