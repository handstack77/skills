# 버그 진단

까다로운 버그를 위한 규율입니다. 명시적으로 정당화될 때만 단계를 건너뛰세요.

코드베이스를 탐색할 때 `GLOSSARY.md`가 있으면 읽어서 관련 모듈에 대한 명확한 멘탈 모델을 갖고, 건드리는 영역의 ADR을 확인하세요.

## 가리기

이 스킬은 명령, 출력, 캡처한 산출물을 보여 주게 합니다. **보여 주기 전에 모든 비밀을 먼저 가리세요**: 그 자리에 `<REDACTED>`를 쓰세요. 자격 증명이 보여 주는 내용 속이 아니라 환경에 머물도록, 루프는 환경 변수를 기준으로 만드세요. 캡처한 산출물에는 인증 헤더가 들어 있습니다. 신호를 담은 줄만 인용하세요.

가린 출력만으로 버그를 진단할 수 없다면 그렇게 말하고 사용자에게 물으세요.

## 1단계: 피드백 루프 만들기

**이것이 이 스킬의 핵심입니다.** 나머지는 기계적입니다. 버그에 대한 **빡빡한** 통과/실패 신호(_이_ 버그에서 빨갛게 되는 것)가 있다면 원인을 찾게 됩니다. 이분 탐색, 가설 검증, 계측은 모두 그 신호를 소비할 뿐입니다. 없다면 코드를 아무리 들여다봐도 구해 주지 못합니다.

여기에 불균형할 만큼 노력을 쏟으세요. **공격적으로 하세요. 창의적으로 하세요. 포기를 거부하세요.**

### 루프를 만드는 방법, 대략 이 순서로

1. 버그에 닿는 어떤 이음매에서든 **실패하는 테스트**: 단위, 통합, e2e.
2. 실행 중인 개발 서버에 대한 **curl / HTTP 스크립트**.
3. 픽스처 입력으로 **CLI 호출**을 하고, stdout을 알려진 정상 스냅샷과 diff.
4. UI를 구동하며 DOM/콘솔/네트워크를 단언하는 **헤드리스 브라우저 스크립트**(Playwright / Puppeteer).
5. **캡처한 트레이스 재생.** 실제 네트워크 요청 / 페이로드 / 이벤트 로그를 디스크에 저장하고, 코드 경로를 격리해서 재생합니다.
6. **일회용 하네스.** 시스템의 최소 부분집합(서비스 하나, 의존성 모킹)을 띄워 함수 호출 한 번으로 버그 코드 경로를 실행합니다.
7. **속성 / 퍼즈 루프.** 버그가 "가끔 출력이 틀림"이라면 무작위 입력 1000개를 돌려 실패 양상을 찾으세요.
8. **이분 탐색 하네스.** 버그가 알려진 두 상태(커밋, 데이터셋, 버전) 사이에서 나타났다면, "상태 X에서 부팅하고 확인하고 반복"을 자동화해서 `git bisect run`으로 돌릴 수 있게 하세요.
9. **차분 루프.** 같은 입력을 이전 버전과 새 버전(또는 두 설정)에 통과시키고 출력을 diff하세요.
10. **HITL bash 스크립트.** 최후의 수단입니다. 사람이 클릭해야 한다면, `scripts/hitl-loop.template.sh`로 _그들을_ 안내해서 루프가 여전히 구조화되게 하세요. 캡처한 출력이 당신에게 돌아옵니다.

올바른 피드백 루프를 만들면 버그의 90%는 고쳐진 것입니다.

### 루프 조이기

루프를 제품처럼 다루세요. _하나의_ 루프가 생기면 **조이세요**.

- 더 빠르게 만들 수 있는가? (설정을 캐시하고, 무관한 초기화를 건너뛰고, 테스트 범위를 좁힌다.)
- 신호를 더 날카롭게 만들 수 있는가? ("크래시하지 않음"이 아니라 구체적인 증상을 단언한다.)
- 더 결정적으로 만들 수 있는가? (시간을 고정하고, RNG에 시드를 주고, 파일 시스템을 격리하고, 네트워크를 동결한다.)

30초 걸리는 불안정한 루프는 루프가 없는 것보다 거의 나을 게 없습니다. 2초짜리 결정적 루프는 빡빡한, 디버깅의 초능력입니다.

### 비결정적 버그

목표는 깨끗한 재현이 아니라 **더 높은 재현율**입니다. 트리거를 100번 반복하고, 병렬화하고, 스트레스를 주고, 타이밍 창을 좁히고, sleep을 주입하세요. 50% 확률로 불안정한 버그는 디버깅할 수 있지만 1%는 그럴 수 없으므로, 디버깅할 수 있을 때까지 재현율을 계속 높이세요.

### 정말로 루프를 만들 수 없을 때

멈추고 명시적으로 그렇게 말하세요. 시도한 것을 나열하세요. 사용자에게 다음을 요청하세요. (a) 재현되는 환경에 대한 접근, (b) 가린 캡처 산출물(HAR 파일, 로그 덤프, 코어 덤프, 타임스탬프가 있는 화면 녹화), 또는 (c) 임시 프로덕션 계측을 추가할 허락. 루프 없이 가설 세우기로 넘어가지 **마세요**.

### 완료 기준: 빨갛게 되는 빡빡한 루프

1단계는 루프가 **빡빡하고** **빨강이 가능**할 때 끝납니다. **명령 하나**(스크립트 경로, 테스트 호출, curl)를 말할 수 있고, 그것을 **이미 최소 한 번 실행**했으며(호출과 그 출력을, 가려서 보여 주세요), 다음을 만족해야 합니다.

- [ ] **빨강 가능**: 실제 버그 코드 경로를 구동하고 **사용자의 정확한 증상**을 단언하므로, 이 버그에서 빨갛게 되고 고치면 초록이 될 수 있습니다. "에러 없이 실행됨"이 아닙니다. _이 특정 버그를 잡아낼_ 수 있어야 합니다.
- [ ] **결정적**: 실행할 때마다 같은 판정(불안정한 버그는 위에서 말한 고정된 높은 재현율).
- [ ] **빠름**: 분이 아니라 초.
- [ ] **에이전트가 실행 가능**: 무인으로 실행할 수 있어야 합니다. 사람이 루프에 들어가는 것은 `scripts/hitl-loop.template.sh`를 통해서만 가능합니다.

이 명령이 존재하기 전에 이론을 세우려고 코드를 읽고 있는 자신을 발견하면 **멈추세요. 곧바로 가설로 건너뛰는 것이 이 스킬이 막으려는 바로 그 실패입니다.** 빨강 가능한 명령이 없으면 2단계도 없습니다.

## 2단계: 재현 + 최소화

루프를 실행하세요. 버그가 나타나면서 빨갛게 되는 것을 지켜보세요.

확인하세요.

- [ ] 루프가 근처에 있을 뿐인 다른 실패가 아니라 **사용자**가 설명한 실패 양상을 만들어 냅니다. 잘못된 버그 = 잘못된 수정.
- [ ] 여러 번 실행해도 실패가 재현됩니다(또는 비결정적 버그라면, 디버깅할 만큼 충분히 높은 비율로 재현됩니다).
- [ ] 이후 단계가 수정이 정말로 그것을 해결하는지 검증할 수 있도록 정확한 증상(에러 메시지, 잘못된 출력, 느린 시간)을 캡처했습니다.

### 최소화

빨갛게 되면 재현을 **여전히 빨강인 가장 작은 시나리오**로 줄이세요. 입력, 호출자, 설정, 데이터, 단계를 **하나씩** 잘라 내고 매번 루프를 다시 실행하세요. 실패에 하중을 받는 것만 남기세요.

왜 신경 쓰는가: 최소 재현은 3단계의 가설 공간을 줄이고(의심할 움직이는 부품이 줄어듭니다) 5단계의 깔끔한 회귀 테스트가 됩니다.

**남은 모든 요소가 하중을 받을 때** 끝납니다. 어느 하나를 제거해도 루프가 초록이 됩니다.

재현**하고** 최소화하기 전에는 넘어가지 마세요.

## 3단계: 가설 세우기

어느 것도 테스트하기 전에 **순위가 매겨진 가설 3~5개**를 만드세요. 가설을 하나만 만들면 처음 떠오른 그럴듯한 생각에 닻이 내려집니다.

각 가설은 **반증 가능**해야 합니다. 그 가설이 하는 예측을 서술하세요.

> 형식: "<X>가 원인이라면, <Y>를 바꾸면 버그가 사라지고 / <Z>를 바꾸면 더 나빠질 것이다."

예측을 서술할 수 없다면 그 가설은 느낌일 뿐입니다. 버리거나 다듬으세요.

**테스트하기 전에 순위가 매겨진 목록을 사용자에게 보여 주세요.** 사용자는 순위를 즉시 바꿀 도메인 지식("방금 #3에 변경을 배포했어요")이 있거나 이미 배제한 가설을 알고 있는 경우가 많습니다. 싼 체크포인트로 시간을 크게 아낍니다. 이를 기다리며 막히지는 마세요. 사용자가 자리를 비웠다면 당신의 순위대로 진행하세요.

## 4단계: 계측

각 프로브는 3단계의 특정 예측에 대응해야 합니다. **한 번에 한 변수만 바꾸세요.**

도구 선호도:

1. 환경이 지원한다면 **디버거 / REPL 점검**. 중단점 하나가 로그 열 개보다 낫습니다.
2. 가설들을 구별하는 경계에 **표적 로그**.
3. "전부 로그로 찍고 grep"은 절대 안 됩니다.

**모든 디버그 로그에** `[DEBUG-a4f2]` 같은 고유한 접두사를 **태그**로 붙이세요. 마지막 정리가 grep 한 번으로 끝납니다. 태그 없는 로그는 살아남고, 태그 붙은 로그는 죽습니다.

**성능 갈래.** 성능 회귀에서는 로그가 대개 틀립니다. 대신 기준선 측정(타이밍 하네스, `performance.now()`, 프로파일러, 쿼리 플랜)을 확립한 뒤 이분 탐색을 하세요. 먼저 측정하고, 그다음 고치세요.

## 5단계: 수정 + 회귀 테스트

수정 **전에** 회귀 테스트를 쓰세요. 단, 그것을 위한 **올바른 이음매**가 있을 때만입니다.

올바른 이음매란 테스트가 호출 지점에서 발생하는 대로 **실제 버그 패턴**을 실행하는 곳입니다. 쓸 수 있는 유일한 이음매가 너무 얕다면(버그가 여러 호출자를 필요로 하는데 호출자 하나짜리 테스트, 버그를 일으킨 연쇄를 재현할 수 없는 단위 테스트) 거기서의 회귀 테스트는 거짓된 확신을 줍니다.

**올바른 이음매가 없다면, 그 자체가 발견 사항입니다.** 기록하세요. 코드베이스 아키텍처가 버그를 고정하지 못하게 막고 있는 것입니다. 이를 다음 단계에 표시하세요.

올바른 이음매가 있다면:

1. 최소화한 재현을 그 이음매에서 실패하는 테스트로 바꿉니다.
2. 실패하는 것을 지켜봅니다. 코드나 픽스처를 변형해서 빨강을 강제했다면, 믿기 전에 원본 사본과 `diff`해서 변형이 적용되었음을 증명하세요.
3. 수정을 적용합니다.
4. 통과하는 것을 지켜봅니다.
5. 1단계의 피드백 루프를 원래의(최소화하지 않은) 시나리오에 다시 실행합니다.

## 6단계: 정리

완료를 선언하기 전에 필수입니다.

- [ ] 원래 재현이 더 이상 재현되지 않음 (1단계 루프를 다시 실행)
- [ ] 회귀 테스트가 통과함 (또는 이음매가 없다는 사실이 문서화됨)
- [ ] 모든 `[DEBUG-...]` 계측이 제거됨 (접두사를 `grep`)
- [ ] 일회용 프로토타입이 삭제됨 (또는 분명히 표시된 디버그 위치로 이동됨)
- [ ] 맞는 것으로 판명된 가설이 커밋 / PR 메시지에 서술되어, 다음 디버거가 배울 수 있음
