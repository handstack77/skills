# 코드베이스 아키텍처 개선

아키텍처의 마찰을 드러내고 **깊게 만들 기회**를 제안하세요. 얕은 모듈을 깊은 모듈로 바꾸는 리팩터링입니다. 목표는 테스트 용이성과 AI가 탐색하기 쉬운 구조입니다.

이 명령은 프로젝트의 도메인 모델에서 _정보를 얻고_, 공용 설계 어휘 위에 만들어졌습니다.

- Skill 도구로 "codebase-design"을 호출해 아키텍처 어휘(**모듈**, **인터페이스**, **깊이**, **이음매**, **어댑터**, **레버리지**, **지역성**)와 원칙(삭제 테스트, "인터페이스가 곧 테스트 표면", "어댑터 하나 = 가상의 이음매, 둘 = 진짜")을 확인하세요. 모든 제안에서 이 용어를 정확히 쓰고 "컴포넌트", "서비스", "API", "경계"로 흘러가지 마세요.
- `GLOSSARY.md`의 도메인 언어는 좋은 이음매에 이름을 붙여 줍니다. `docs/adr/`의 ADR은 이 명령이 다시 따지지 말아야 할 결정을 기록합니다.

## 절차

### 1. 탐색

**스캔하기 전에 범위를 정하세요: YAGNI.** 모듈을 깊게 만드는 것은 앞으로 그 모듈을 바꾸기 쉬워지게 해서 값을 합니다. 그러니 최근에 바뀐 코드베이스 부분에 더 큰 비중을 두세요. 살펴보기 전에 *어디를* 볼지 정하세요.

- 사용자가 방향(모듈, 서브시스템, 불편한 지점)을 지정했다면 그것을 따르고, 아래 추론은 건너뛰세요.
- 그렇지 않다면 커밋 이력(`git log --oneline`)을 한참 거슬러 올라가 코드베이스의 핫스팟, 즉 계속 등장하는 파일과 영역을 찾고, 그 경로들이 먼저 주의를 끌게 하세요. 변경이 흩어져 있고 뚜렷한 핫스팟이 없다면 그물을 넓히세요.

먼저 프로젝트의 도메인 용어집(`GLOSSARY.md`)과 건드리는 영역의 ADR을 읽으세요.

그다음 서브에이전트를 띄워 코드베이스를 훑게 하세요. 경직된 휴리스틱을 따르지 말고 유기적으로 탐색하며 마찰을 느끼는 곳을 기록하세요.

- 개념 하나를 이해하려면 작은 모듈 여러 개를 오가야 하는 곳은 어디인가?
- 인터페이스가 구현만큼 복잡한 **얕은** 모듈은 어디인가?
- 테스트 용이성만을 위해 순수 함수를 추출했지만 진짜 버그는 그것을 호출하는 방식에 숨어 있는 곳은 어디인가(**지역성** 없음)?
- 강하게 결합된 모듈이 이음매를 넘어 새는 곳은 어디인가?
- 코드베이스의 어느 부분이 테스트되지 않았거나 현재 인터페이스로는 테스트하기 어려운가?

얕다고 의심되는 것에 **삭제 테스트**를 적용하세요. 삭제하면 복잡성이 모일까, 아니면 그냥 옮겨질까? "모인다"가 원하는 신호입니다.

### 2. 후보를 HTML 보고서로 제시

저장소에 아무것도 남지 않도록 OS 임시 디렉터리에 독립적인 HTML 파일을 쓰세요. 임시 디렉터리는 `$TMPDIR`에서 찾고, 없으면 `/tmp`(Windows에서는 `%TEMP%`)로 폴백하세요. 매 실행마다 새 파일이 되도록 `<tmpdir>/architecture-review-<timestamp>.html`에 쓰세요. 사용자를 위해 열고(Linux는 `xdg-open <path>`, macOS는 `open <path>`, Windows는 `start <path>`) 절대 경로를 알려 주세요.

보고서는 레이아웃과 스타일링에 **CDN의 Tailwind**를, 그래프/흐름/시퀀스가 구조를 확실히 전달하는 곳의 다이어그램에 **CDN의 Mermaid**를 사용합니다. Mermaid를 손으로 만든 CSS/SVG 시각 자료와 섞으세요. 관계가 그래프 모양일 때(호출 그래프, 의존성, 시퀀스)는 Mermaid를 쓰고, 더 에디토리얼한 것(질량 다이어그램, 단면도, 붕괴 애니메이션)을 원할 때는 직접 만든 div/SVG를 쓰세요. 각 후보에는 **이전/이후 시각화**가 있어야 합니다. 시각적으로 만드세요.

후보마다 다음을 담은 카드를 렌더링하세요.

- **Files**: 관련된 파일/모듈
- **Problem**: 현재 아키텍처가 왜 마찰을 일으키는가
- **Solution**: 무엇이 바뀔지에 대한 쉬운 영어 설명
- **Benefits**: 지역성과 레버리지의 관점에서, 그리고 테스트가 어떻게 나아질지 설명
- **Before / After diagram**: 나란히 직접 그린, 얕음과 깊게 만들기를 보여 주는 그림
- **Recommendation strength**: `Strong`, `Worth exploring`, `Speculative` 중 하나, 배지로 렌더링

보고서는 **Top recommendation** 섹션으로 끝냅니다. 어떤 후보를 먼저 처리할지와 그 이유입니다.

**도메인에는 GLOSSARY.md 어휘를, 아키텍처에는 `/codebase-design` 어휘를 사용하세요.** `GLOSSARY.md`가 "Order"를 정의한다면 "FooBarHandler"나 "Order 서비스"가 아니라 "Order intake 모듈"이라고 말하세요.

**ADR 충돌**: 후보가 기존 ADR과 모순되면, 마찰이 ADR을 다시 검토할 만큼 실질적일 때만 드러내세요. 카드에 분명히 표시하세요(예: 경고 콜아웃, _"ADR-0007과 모순되지만 다시 열 가치가 있음. 왜냐하면…"_). ADR이 금지하는 이론상의 모든 리팩터링을 나열하지 마세요.

전체 HTML 뼈대, 다이어그램 패턴, 스타일 지침은 [HTML-REPORT.md](HTML-REPORT.md)를 보세요.

아직 인터페이스는 제안하지 마세요. 파일을 쓴 뒤 사용자에게 물으세요. "이 중 어떤 것을 탐색해 보시겠어요?"

### 3. 집요한 검증 루프

사용자가 후보를 고르면 Skill 도구로 "grilling"을 호출해 결정 트리를 함께 따라가세요. 제약, 의존성, 깊어진 모듈의 형태, 이음매 뒤에 있는 것, 어떤 테스트가 살아남는지를 다룹니다.

결정이 굳어지는 대로 부수 효과가 인라인으로 일어납니다. 진행하면서 도메인 모델을 최신으로 유지하도록 Skill 도구로 "domain-modeling"을 호출하세요.

- **깊어진 모듈을 `GLOSSARY.md`에 없는 개념으로 이름 짓는가?** `GLOSSARY.md`에 용어를 추가하세요. 파일이 없으면 그때 만드세요.
- **대화 중에 모호한 용어를 다듬었는가?** 바로 그 자리에서 `GLOSSARY.md`를 갱신하세요.
- **사용자가 결정적인 이유로 후보를 기각하는가?** ADR을 제안하세요. 이런 식으로 표현하세요. _"앞으로의 아키텍처 리뷰가 이것을 다시 제안하지 않도록 ADR로 기록할까요?"_ 같은 것을 다시 제안하지 않으려면 미래의 탐색자에게 그 이유가 실제로 필요할 때만 제안하세요. 일시적인 이유("지금은 그럴 가치가 없음")나 자명한 이유는 건너뛰세요.
- **깊어진 모듈의 대안 인터페이스를 탐색하고 싶은가?** Skill 도구로 "codebase-design"을 호출하고 그 두 번 설계하기 병렬 서브에이전트 패턴을 쓰세요.
