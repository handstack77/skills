# 코드베이스 설계

**깊은 모듈**을 설계하세요. 작은 인터페이스 뒤에 많은 동작이 있고, 깔끔한 이음매에 놓이며, 그 인터페이스를 통해 테스트할 수 있는 모듈입니다. 코드를 설계하거나 재구성하는 곳이라면 어디서든 이 언어와 원칙을 사용하세요. 목표는 호출자에게는 레버리지, 유지보수자에게는 지역성, 모두에게는 테스트 용이성입니다.

## 용어집

이 용어를 정확히 그대로 쓰세요. "컴포넌트", "서비스", "API", "경계"로 바꿔 쓰지 마세요. 일관된 언어가 핵심입니다.

**모듈(Module)**: 인터페이스와 구현을 가진 모든 것. 일부러 규모에 구애받지 않게 정의했습니다. 함수, 클래스, 패키지, 여러 계층에 걸친 슬라이스가 될 수 있습니다. _Avoid_: unit, component, service.

**인터페이스(Interface)**: 호출자가 모듈을 올바르게 쓰기 위해 알아야 하는 모든 것. 타입 시그니처뿐 아니라 불변식, 순서 제약, 에러 모드, 필수 설정, 성능 특성도 포함합니다. _Avoid_: API, signature (너무 좁아서 타입 수준의 표면만 가리킴).

**구현(Implementation)**: 모듈 안에 있는 것, 즉 코드 본체. **어댑터(Adapter)**와는 구별됩니다. 작은 어댑터에 큰 구현이 있을 수도 있고(Postgres 리포지터리), 큰 어댑터에 작은 구현이 있을 수도 있습니다(인메모리 페이크). 이음매가 주제일 때는 "어댑터"를, 그 외에는 "구현"을 쓰세요.

**깊이(Depth)**: 인터페이스에서의 레버리지. 호출자(또는 테스트)가 익혀야 하는 인터페이스 단위당 실행할 수 있는 동작의 양. 작은 인터페이스 뒤에 많은 동작이 있으면 모듈이 **깊고**, 인터페이스가 구현만큼 복잡하면 **얕습니다**.

**이음매(Seam)** _(Michael Feathers)_: 그 자리를 수정하지 않고도 동작을 바꿀 수 있는 곳. 모듈의 인터페이스가 놓이는 *위치*입니다. 이음매를 어디에 둘지는 그 뒤에 무엇을 둘지와는 별개의 설계 결정입니다. _Avoid_: boundary (DDD의 바운디드 컨텍스트와 의미가 겹침).

**어댑터(Adapter)**: 이음매에서 인터페이스를 충족하는 구체적인 것. 내용물(안에 무엇이 있는지)이 아니라 *역할*(어떤 자리를 채우는지)을 기술합니다.

**레버리지(Leverage)**: 깊이로 호출자가 얻는 것. 익히는 인터페이스 단위당 더 많은 능력. 구현 하나가 N개의 호출 지점과 M개의 테스트에서 값을 합니다.

**지역성(Locality)**: 깊이로 유지보수자가 얻는 것. 변경, 버그, 지식, 검증이 호출자들 사이로 퍼지지 않고 한곳에 모입니다. 한 번 고치면 어디서나 고쳐집니다.

## 깊음 대 얕음

**깊은 모듈** = 작은 인터페이스 + 많은 구현:

```
┌─────────────────────┐
│   작은 인터페이스    │  ← 메서드가 적고 파라미터가 단순
├─────────────────────┤
│                     │
│     깊은 구현        │  ← 복잡한 로직이 숨겨짐
│                     │
└─────────────────────┘
```

**얕은 모듈** = 큰 인터페이스 + 적은 구현 (피하세요):

```
┌─────────────────────────────────┐
│          큰 인터페이스           │  ← 메서드가 많고 파라미터가 복잡
├─────────────────────────────────┤
│  얇은 구현                      │  ← 그냥 통과시킬 뿐
└─────────────────────────────────┘
```

인터페이스를 설계할 때 물어보세요.

- 메서드 수를 줄일 수 있는가?
- 파라미터를 단순화할 수 있는가?
- 더 많은 복잡성을 안쪽에 숨길 수 있는가?

## 원칙

- **깊이는 구현이 아니라 인터페이스의 속성입니다.** 깊은 모듈도 내부적으로는 작고, 모킹할 수 있고, 교체할 수 있는 부품으로 구성될 수 있습니다. 그 부품이 인터페이스의 일부가 아닐 뿐입니다. 모듈은 인터페이스에 있는 **외부 이음매**뿐 아니라 **내부 이음매**(구현에 비공개이며 자체 테스트가 사용)도 가질 수 있습니다.
- **삭제 테스트.** 모듈을 삭제한다고 상상해 보세요. 복잡성이 사라지면 그것은 단순 통과였습니다. 복잡성이 N개의 호출자에 다시 나타나면 제 몫을 하고 있던 것입니다.
- **인터페이스가 곧 테스트 표면입니다.** 호출자와 테스트는 같은 이음매를 건넙니다. 인터페이스를 *넘어서* 테스트하고 싶다면 모듈의 형태가 잘못되었을 가능성이 큽니다.
- **어댑터가 하나면 가상의 이음매이고, 둘이면 진짜 이음매입니다.** 실제로 무언가가 그 이음매를 사이에 두고 달라지지 않는다면 이음매를 도입하지 마세요.

## 테스트 용이성을 위한 설계

좋은 인터페이스는 테스트를 자연스럽게 만듭니다.

1. **의존성은 만들지 말고 받으세요.**

   ```typescript
   // 테스트하기 쉬움
   function processOrder(order, paymentGateway) {}

   // 테스트하기 어려움
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **부수 효과를 만들지 말고 결과를 반환하세요.**

   ```typescript
   // 테스트하기 쉬움
   function calculateDiscount(cart): Discount {}

   // 테스트하기 어려움
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **표면적을 작게.** 메서드가 적으면 필요한 테스트도 적습니다. 파라미터가 적으면 테스트 설정이 단순해집니다.

## 관계

- **모듈**은 정확히 하나의 **인터페이스**(호출자와 테스트에 내미는 표면)를 가집니다.
- **깊이**는 **모듈**의 속성이며, **인터페이스**를 기준으로 측정합니다.
- **이음매**는 **모듈**의 **인터페이스**가 놓이는 곳입니다.
- **어댑터**는 **이음매**에 앉아 **인터페이스**를 충족합니다.
- **깊이**는 호출자에게 **레버리지**를, 유지보수자에게 **지역성**을 낳습니다.

## 기각한 관점

- **깊이를 구현 줄 수 대 인터페이스 줄 수의 비율로 보는 것** (Ousterhout): 구현을 부풀리는 것에 보상을 줍니다. 우리는 대신 깊이를 레버리지로 봅니다.
- **"인터페이스"를 TypeScript의 `interface` 키워드나 클래스의 public 메서드로 보는 것**: 너무 좁습니다. 여기서 인터페이스는 호출자가 알아야 하는 모든 사실을 포함합니다.
- **"경계"**: DDD의 바운디드 컨텍스트와 의미가 겹칩니다. **이음매**나 **인터페이스**라고 말하세요.
