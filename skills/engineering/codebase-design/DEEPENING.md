# 깊게 만들기

의존성을 고려해 얕은 모듈의 군집을 안전하게 깊게 만드는 방법입니다. [SKILL.md](SKILL.md)의 어휘를 전제로 합니다: **모듈**, **인터페이스**, **이음매**, **어댑터**.

## 의존성 범주

깊게 만들 후보를 평가할 때 그 의존성을 분류하세요. 범주에 따라 깊어진 모듈을 이음매 너머에서 어떻게 테스트할지가 정해집니다.

### 1. 프로세스 내부

순수 계산, 인메모리 상태, I/O 없음. 언제나 깊게 만들 수 있습니다. 모듈을 합치고 새 인터페이스를 통해 직접 테스트하세요. 어댑터는 필요 없습니다.

### 2. 로컬 대체 가능

로컬 테스트 대역이 있는 의존성(Postgres의 PGLite, 인메모리 파일 시스템). 대역이 있으면 깊게 만들 수 있습니다. 깊어진 모듈은 테스트 스위트에서 대역을 실행하며 테스트합니다. 이음매는 내부에 있으며, 모듈의 외부 인터페이스에는 포트가 없습니다.

### 3. 원격이지만 직접 소유 (포트와 어댑터)

네트워크 경계를 넘는 직접 만든 서비스(마이크로서비스, 내부 API). 이음매에 **포트**(인터페이스)를 정의하세요. 깊은 모듈이 로직을 소유하고, 전송 수단은 **어댑터**로 주입합니다. 테스트에서는 인메모리 어댑터를, 프로덕션에서는 HTTP/gRPC/큐 어댑터를 씁니다.

권고의 형태: *"이음매에 포트를 정의하고, 프로덕션용 HTTP 어댑터와 테스트용 인메모리 어댑터를 구현하세요. 그러면 네트워크 너머에 배포되더라도 로직은 하나의 깊은 모듈에 있게 됩니다."*

### 4. 진짜 외부 (목)

통제할 수 없는 서드파티 서비스(Stripe, Twilio 등). 깊어진 모듈이 외부 의존성을 주입된 포트로 받고, 테스트에서는 목 어댑터를 제공합니다.

## 이음매 규율

- **어댑터가 하나면 가상의 이음매이고, 둘이면 진짜 이음매입니다.** 어댑터가 최소 둘(보통 프로덕션 + 테스트)이 정당화되지 않으면 포트를 도입하지 마세요. 어댑터가 하나인 이음매는 간접 참조일 뿐입니다.
- **내부 이음매 대 외부 이음매.** 깊은 모듈은 인터페이스에 있는 외부 이음매뿐 아니라 내부 이음매(구현에 비공개이며 자체 테스트가 사용)도 가질 수 있습니다. 테스트가 쓴다는 이유만으로 내부 이음매를 인터페이스로 노출하지 마세요.

## 테스트 전략: 교체하세요, 쌓지 마세요

- 깊어진 모듈의 인터페이스에 테스트가 생기면, 얕은 모듈에 있던 기존 단위 테스트는 낭비가 됩니다. 삭제하세요.
- 새 테스트는 깊어진 모듈의 인터페이스에 작성하세요. **인터페이스가 테스트 표면입니다.**
- 테스트는 내부 상태가 아니라 인터페이스를 통해 관찰 가능한 결과를 단언합니다.
- 테스트는 구현이 아니라 동작을 기술하므로 내부 리팩터링에도 살아남아야 합니다. 구현이 바뀔 때 테스트도 바뀌어야 한다면, 인터페이스 너머를 테스트하고 있는 것입니다.
