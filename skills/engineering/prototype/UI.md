# UI 프로토타입

하나의 라우트에 **근본적으로 다른 UI 변형 여러 개**를 만들고, 화면 아래에 떠 있는 바로 전환할 수 있게 하세요. 사용자는 브라우저에서 변형들을 넘겨 보다가 하나를 고르거나(또는 각각에서 조각을 가져오고), 나머지는 버립니다.

질문이 어떻게 생겼는가가 아니라 로직/상태에 대한 것이라면 이 갈래가 아닙니다. [LOGIC.md](LOGIC.md)를 쓰세요.

## 이 형태가 맞는 경우

- "이 페이지는 어떻게 생겨야 할까?"
- "확정하기 전에 이 대시보드의 몇 가지 선택지를 보고 싶다."
- "설정 화면의 레이아웃을 다르게 시도해 보라."
- 사용자가 아니면 머릿속의 모호한 목업 셋 중에서 하루를 고르며 보낼 때는 언제든.

## 두 가지 하위 형태: A를 강하게 선호

UI 프로토타입은 **앱의 나머지와 맞닿아 있을 때** 훨씬 판단하기 쉽습니다. 실제 헤더, 실제 사이드바, 실제 데이터, 실제 밀도가 있기 때문입니다. 단독으로 떠 있는 일회용 라우트는 진공 상태입니다. 모든 변형이 따로 보면 다 괜찮아 보입니다. 변형들을 담을 만한 기존 페이지가 있다면 항상 하위 형태 A를 기본으로 하세요. 근처에 둘 곳이 정말 없을 때만 하위 형태 B를 쓰세요.

### 하위 형태 A: 기존 페이지에 대한 조정 (선호)

라우트가 이미 존재합니다. 변형은 `?variant=` URL 검색 파라미터로 조건을 걸어 **같은 라우트에서** 렌더링합니다. 기존의 데이터 가져오기, 파라미터, 인증은 모두 그대로 두고 렌더링만 교체합니다. 이것이 기본이며, 특별한 이유가 없다면 이것을 고르세요.

프로토타입 대상이 아직 페이지가 없지만 *자연스럽게 어떤 페이지 안에 들어갈* 것이라면(대시보드의 새 섹션, 설정 화면의 새 카드, 기존 흐름의 새 단계), 여전히 하위 형태 A입니다. 호스트 페이지 안에 변형을 마운트하세요.

### 하위 형태 B: 새 페이지 (최후의 수단)

프로토타입 대상이 들어갈 기존 페이지가 정말 없을 때만 쓰세요(예: 완전히 새로운 최상위 화면, 어디에도 합리적으로 끼워 넣을 수 없는 흐름).

프로젝트가 이미 쓰는 라우팅 관례를 따라 **일회용 라우트**를 만드세요. 새로운 최상위 구조를 만들지 마세요. 프로토타입임이 분명하도록 이름을 지으세요(예: 경로나 파일명에 `prototype`을 넣기). `?variant=` 패턴은 같습니다.

하위 형태 B를 확정하기 전에 점검하세요. 이것을 끼워 넣을 기존 페이지가 정말 없는가? 빈 라우트는 채워진 라우트라면 드러냈을 설계 문제를 가립니다.

두 하위 형태 모두에서 아래에 떠 있는 바는 동일합니다.

## 절차

### 1. 질문을 밝히고 N을 고르기

기본은 **변형 3개**입니다. 5개를 넘으면 근본적으로 다르지 않고 잡음이 되기 시작하므로 거기서 상한을 두세요.

계획을 한 줄로 프로토타입 위치나 파일 맨 위 주석에 적어 두세요.

> "기존 `/settings` 라우트에서 `?variant=`로 전환하는 설정 페이지 변형 3개."

사용자가 곁에서 반박하든 아니든 이렇게 하면 됩니다.

### 2. 근본적으로 다른 변형 만들기

각 변형의 초안을 만드세요. 각각에 다음을 지키게 하세요.

- 페이지의 목적과 접근할 수 있는 데이터.
- 프로젝트의 컴포넌트 라이브러리 / 스타일링 시스템(TailwindCSS, shadcn, MUI, 순수 CSS 등 무엇이든).
- 명확한 export 컴포넌트 이름. 예: `VariantA`, `VariantB`, `VariantC`.

변형은 **구조적으로 달라야** 합니다. 레이아웃, 정보 위계, 주된 어포던스가 달라야 하고 색만 다르면 안 됩니다. 살짝 손본 카드 그리드 셋은 UI 프로토타입이 아니라 벽지입니다. 두 초안이 너무 비슷하게 나오면, 명시적으로 "카드 그리드를 쓰지 말 것"이라는 지침을 주고 하나를 다시 만드세요.

### 3. 연결하기

라우트에 전환 컴포넌트 하나를 만드세요.

```tsx
// 의사코드, 프로젝트의 프레임워크에 맞게 조정
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

하위 형태 A(기존 페이지)는 기존의 데이터 가져오기를 모두 전환기 위에 그대로 두고, 변형마다 렌더링되는 서브트리만 바뀝니다.

하위 형태 B(새 페이지)는 `/prototype/<name>` 아래의 일회용 라우트가 같은 전환기를 마운트합니다.

### 4. 떠 있는 전환기 만들기

화면 아래 중앙에 고정 위치로 놓는 작은 바이며 세 부분이 있습니다.

- **왼쪽 화살표**: 이전 변형으로 순환합니다(처음에서 끝으로 이어짐).
- **변형 레이블**: 현재 변형 키를 보여 주고, 변형이 이름을 export하면 그 이름도 보여 줍니다. 예: `B (Sidebar layout)`.
- **오른쪽 화살표**: 앞으로 순환합니다(끝에서 처음으로 이어짐).

동작:

- 화살표를 클릭하면 URL 검색 파라미터를 갱신합니다(프레임워크의 라우터를 사용: Next의 `router.replace`, React Router의 `navigate` 등). 그래서 변형을 공유할 수 있고 새로고침에도 유지됩니다.
- 키보드: `←`와 `→` 화살표 키로도 순환합니다. `<input>`, `<textarea>`, `[contenteditable]`에 포커스가 있을 때는 화살표 키를 가로채지 마세요.
- 페이지와 시각적으로 구별되게 합니다(예: 대비가 높은 알약 모양, 은은한 그림자). 평가 중인 디자인의 일부가 아님이 분명해야 합니다.
- 프로덕션 빌드에서는 숨깁니다. `process.env.NODE_ENV !== 'production'` 또는 동등한 검사로 조건을 걸어, 프로토타입이 실수로 병합되어도 바가 사용자에게 배포되지 않게 하세요.

전환기는 두 하위 형태가 재사용할 수 있도록 하나의 공유 컴포넌트에 두세요. 프로젝트에서 공유 UI가 있는 곳에 두세요.

### 5. 넘겨주기

URL(그리고 `?variant=` 키)을 알려 주세요. 사용자는 시간이 날 때 넘겨 볼 것입니다. 흥미로운 피드백은 대개 **"B의 헤더에 C의 사이드바를 쓰고 싶어요"** 같은 것이고, 그것이 사용자가 실제로 원하는 디자인입니다.

### 6. 답을 기록하고 정리하기

변형 하나가 이기면 답(어느 변형이고 왜인지)을 기록한 뒤, [SKILL](SKILL.md)이 설명하는 방식으로 프로토타입을 기록하세요. 승자는 실제 코드에 녹이고 나머지는 main이 아니라 일회용 브랜치로 옮기세요.

- **하위 형태 A**: 승자를 기존 페이지에 녹이고, 진 변형들과 전환기는 main에서 지웁니다.
- **하위 형태 B**: 승리한 변형을 실제 라우트로 승격하고, 일회용 라우트와 전환기는 main에서 지웁니다.

변형 전체가 1차 자료이므로 쓰레기통이 아니라 일회용 브랜치에 남깁니다. 변형 컴포넌트와 전환기가 main 브랜치에 남으면 금세 썩어서 다음 독자를 혼란스럽게 하기 때문입니다.

## 안티패턴

- **색이나 카피만 다른 변형.** 그건 미세 조정이지 프로토타입이 아닙니다. 진짜 변형은 구조에 대해 의견이 다릅니다.
- **변형끼리 코드를 너무 많이 공유하기.** 공유 `<Header>`는 괜찮지만 공유 `<Layout>`은 취지를 무너뜨립니다. 각 변형은 레이아웃을 자유롭게 버릴 수 있어야 합니다.
- **변형을 실제 변이(mutation)에 연결하기.** 읽기 전용 프로토타입은 괜찮습니다. 변형이 변이해야 한다면 스텁을 가리키게 하세요. 질문은 "이것은 어떻게 생겨야 하는가"이지 "백엔드가 동작하는가"가 아닙니다.
- **프로토타입을 곧바로 프로덕션으로 승격하기.** 변형 코드는 프로토타입 제약(테스트 없음, 최소한의 에러 처리) 아래서 작성되었습니다. 녹여 넣을 때 제대로 다시 쓰세요.
