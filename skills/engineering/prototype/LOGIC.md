# 로직 프로토타입

누구나 버튼을 눌러 상태 모델을 조작해 볼 수 있는, 독립적인 HTML 파일 하나(**공유 가능한 데모**)입니다. 질문이 **비즈니스 로직, 상태 전이, 데이터 형태**에 관한 것일 때 쓰세요. 종이 위에서는 그럴듯해 보이지만 실제 사례를 통과시켜 봐야 이상하다는 걸 느끼게 되는 종류의 것입니다.

설치할 것 없는 파일 하나이므로 비개발자(디자이너, PM, 도메인 전문가)에게 건네서 직접 모델을 느껴 보게 할 수 있습니다. 그래서 코드의 언어가 아니라 그들의 언어로 말해야 합니다.

## 이 형태가 맞는 경우

- "이 상태 머신이 X 다음에 Y가 오는 엣지 케이스를 처리하는지 모르겠다."
- "이 데이터 모델로 ...인 경우를 실제로 표현할 수 있는가?"
- "API를 작성하기 전에 어떤 모양이어야 할지 감을 잡고 싶다."
- 누군가 **버튼을 누르며 상태가 바뀌는 걸 보고 싶은** 모든 경우.

질문이 "이것은 어떻게 생겨야 하는가"라면 이 갈래가 아닙니다. [UI.md](UI.md)를 쓰세요.

## 절차

### 1. 질문 밝히기

코드를 쓰기 전에 어떤 상태 모델과 어떤 질문을 프로토타이핑하는지 적으세요. 한 문단으로, 데모 맨 위에(주석만이 아니라 눈에 보이는 소개로) 둡니다. 엉뚱한 질문에 답하는 로직 프로토타입은 순전한 낭비이므로, 사용자가 지금 보고 있든 나중에 자리를 비운 채 돌아오든 나중에 확인할 수 있도록 질문을 명시하세요.

### 2. 로직을 이식 가능한 모듈로 분리하기

실제 로직(질문에 답하는 부분)을 단일 `<script>` 블록에, 나중에 떼어 내서 실제 코드베이스에 넣을 수 있는 작고 순수한 모듈로 쓰세요. 그 주변의 페이지는 일회용이지만 이 모듈은 아닙니다.

적절한 형태는 질문에 따라 다릅니다.

- **순수 리듀서**: `(state, action) => state`. 동작이 개별 이벤트이고 상태가 단일 값일 때 좋습니다.
- **상태 머신**: 명시적인 상태와 전이. "지금 어떤 동작이 합법적인가"가 질문의 일부일 때 좋습니다.
- 일반 데이터 타입에 대한 **작은 순수 함수 모음**. 암묵적인 현재 상태 없이 변환만 있을 때 좋습니다.
- 로직이 진짜로 지속적인 내부 상태를 소유할 때는 **메서드 표면이 분명한 클래스나 모듈**.

페이지에 연결하기 가장 쉬운 형태가 아니라, 던지는 질문에 가장 잘 맞는 형태를 고르세요. 순수하게 유지하세요. DOM도, `document`도, 그 안으로 손을 뻗는 버튼 핸들러도 없어야 합니다. 페이지가 모듈을 호출하고, 반대 방향으로는 아무것도 흐르지 않습니다. 이것이 프로토타입을 자기 수명 너머에서도 유용하게 만듭니다. 질문에 답이 나오면 검증된 리듀서 / 머신 / 함수 모음이 그대로 실제 모듈로 옮겨집니다.

### 3. 공유 가능한 HTML 파일 만들기

파일 하나, 순수 HTML/CSS/JS로 만듭니다. 프레임워크도, 번들러도, 서버도 없고 모두 인라인이라 더블클릭으로 열리며 이메일로 돌려도 살아남습니다. 누구나 열기만 하면 실행할 수 있어야 합니다.

비개발자를 위해 쓰세요. 모든 레이블은 코드가 아니라 **도메인 언어**로 씁니다. 버튼과 상태는 리듀서가 아니라 비즈니스처럼 읽혀야 합니다. 무슨 일이 일어나는지 쉬운 말로 설명하세요.

위에서 아래로 깔끔한 위계로 배치하세요.

1. **제목과 한 줄 설명**: 이 데모로 무엇을 탐색할 수 있는지(1단계의 질문).
2. **현재 상태**: 관련 상태 전체를 읽기 쉬운 패널로 렌더링합니다(원본 JSON 덤프가 아니라 레이블이 붙은 필드). 클릭할 때마다 다시 렌더링해서 변화가 보이게 합니다. 비개발자가 따라가는 데 도움이 되면 방금 무엇이 바뀌었는지 짚어 주세요.
3. **자유 조작 버튼**: 동작마다 버튼 하나, 항상 사용할 수 있어 누구나 아무 순서로나 모델을 찔러볼 수 있습니다. 클릭할 때마다 해당 동작을 디스패치하고 상태를 다시 렌더링합니다.
4. **안내형 워크스루**: 탭마다 **시나리오** 하나씩의 모음. 각 탭에는 시나리오(설정되는 상황과 주목할 점)에 대한 짧은 쉬운 말 설명이 있고, 그 아래에 해당 시나리오에서 누를 **버튼들**이 순서대로 있습니다. 각 단계는 진짜 버튼입니다. 누르면 그 동작을 수행하고 다음 단계로 넘어갑니다. 워크스루를 시작하면 알려진 초기 상태로 리셋해서 시나리오가 매번 똑같이 실행되게 합니다.

종이 위에서 추론하기 어려운 까다로운 경우를 보여 주는 시나리오를 고르세요. 정상 경로, 까다로운 엣지 케이스, 불법이어야 하는 일을 시도하는 경우입니다.

아름답지만 절제되게 하세요. 깔끔한 타이포그래피, 넉넉한 간격, 강조색 하나. 애니메이션도, 잔재주도 없고 상태와 버튼과 경쟁하는 것은 없어야 합니다.

### 4. 넘겨주기

파일을 보내거나 대신 열어 주세요. 그들은 시간이 날 때 워크스루를 따라 클릭하고 자유롭게 눌러 볼 것입니다. 흥미로운 순간은 "잠깐, 이건 불가능해야 하는데"나 "어, 난 X가 다를 거라고 생각했는데"라고 말할 때입니다. 그것들이 _아이디어_의 버그이고, 그게 바로 핵심입니다. 새 동작이나 새 시나리오를 원하면 추가하세요. 프로토타입은 진화합니다.

### 5. 답과 프로토타입 기록하기

프로토타입이 질문에 답했으면 답을 기록한 뒤 [SKILL](SKILL.md)이 설명하는 방식으로 프로토타입을 기록하세요. 로직 갈래의 대응은 이렇습니다. 검증된 리듀서 / 머신 / 함수 모음은 실제 모듈로 옮겨지고(결정이 흡수됨), HTML 껍데기는 프로토타입을 1차 자료로 보관하는 일회용 브랜치로 따라갑니다. 독립적인 파일 하나이므로 거기서도 쉽게 다시 실행할 수 있습니다.

## 안티패턴

- **테스트를 추가하지 마세요.** 테스트가 필요한 프로토타입은 더 이상 프로토타입이 아닙니다.
- **실제 데이터베이스에 연결하지 마세요.** 질문이 구체적으로 영속성에 관한 것이 아니라면 인메모리 상태를 쓰세요.
- **일반화하지 마세요.** "나중에 X를 지원하고 싶다면" 같은 건 없습니다. 프로토타입은 하나의 질문에 답합니다.
- **로직과 페이지를 뒤섞지 마세요.** 순수 모듈이 DOM, `document`, 버튼 핸들러를 참조하면 더 이상 옮길 수 없습니다. 페이지는 순수 모듈 위의 얇은 껍데기로 유지하세요.
- **프레임워크, 번들러, 서버에 손대지 마세요.** 받는 사람이 더블클릭하는 파일 하나여야 합니다. React 앱이나 개발 서버는 "공유 가능"의 취지를 무너뜨립니다.
- **HTML 껍데기를 프로덕션에 내보내지 마세요.** 페이지는 손으로 클릭하며 훑어보도록 최적화되어 있습니다. 그 뒤의 로직 모듈이 남길 가치가 있는 부분입니다.
