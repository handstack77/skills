# 프로토타입

프로토타입은 **질문에 답하는 일회용 코드**입니다. 질문이 형태를 결정합니다.

## 갈래 고르기

사용자의 프롬프트, 주변 코드를 보고 어떤 질문에 답하는 중인지 파악하세요. 사용자가 곁에 있다면 물어봐도 됩니다.

- **"이 로직 / 상태 모델이 맞게 느껴지는가?"** → [LOGIC.md](LOGIC.md). 종이 위에서 추론하기 어려운 경우들을 상태 머신에 통과시켜 보는, 공유 가능한 HTML 파일 하나를 만드세요(자유 조작 버튼과 탭으로 나뉜 안내형 워크스루). 비개발자도 조작할 수 있어야 합니다.
- **"이것은 어떻게 생겨야 하는가?"** → [UI.md](UI.md). 하나의 라우트에서 근본적으로 다른 UI 변형 여러 개를 만들고, URL 검색 파라미터와 화면 아래 떠 있는 바로 전환하게 하세요.

두 갈래는 매우 다른 산출물을 만들기 때문에, 잘못 고르면 프로토타입 전체가 낭비됩니다. 질문이 정말 모호하고 사용자에게 연락할 수 없다면, 주변 코드에 더 잘 맞는 갈래를 기본으로 하고(백엔드 모듈이면 로직, 페이지나 컴포넌트면 UI) 그 가정을 프로토타입 맨 위에 밝혀 두세요.

## 두 갈래 모두에 적용되는 규칙

1. **처음부터 일회용이고, 그렇다고 분명히 표시합니다.** 프로토타입 코드는 실제로 쓰일 곳 가까이(프로토타입 대상 모듈이나 페이지 옆)에 두어 맥락이 분명하게 하되, 가볍게 읽는 사람도 프로덕션이 아니라 프로토타입임을 알 수 있게 이름을 지으세요. 일회용 UI 라우트는 프로젝트가 이미 쓰는 라우팅 관례를 따르고, 새로운 최상위 구조를 만들지 마세요.
2. **실행하기 쉬워야 합니다.** UI 프로토타입은 프로젝트의 태스크 러너에서 명령 하나로 시작합니다. `pnpm <name>`, `python <path>`, `bun <path>` 등입니다. 로직 데모는 사용자가 더블클릭하는 HTML 파일 하나입니다. 어느 쪽이든 시작하는 데 생각이 필요하지 않아야 합니다.
3. **기본적으로 영속성은 없습니다.** 상태는 메모리에 둡니다. 영속성은 프로토타입이 _확인하는_ 대상이지, 의존해야 할 대상이 아닙니다. 질문이 데이터베이스를 명시적으로 포함한다면, "PROTOTYPE, wipe me"처럼 분명한 이름을 가진 임시 DB나 로컬 파일을 쓰세요.
4. **다듬기는 건너뜁니다.** 테스트도, 프로토타입을 _실행 가능하게_ 만드는 것 이상의 에러 처리도, 추상화도 없습니다. 빠르게 무언가를 배우는 것이 핵심입니다.
5. **상태를 드러냅니다.** 모든 동작(로직) 뒤 또는 모든 변형 전환(UI)마다 관련 상태 전체를 출력하거나 렌더링해서 사용자가 무엇이 바뀌었는지 볼 수 있게 하세요.
6. **끝나면 기록으로 남깁니다.** 검증된 결정은 실제 코드에 녹이고, 프로토타입 자체는 **1차 자료**로 남기세요. main이 아닌 일회용 브랜치에 커밋하고, 구현 이슈에 그 브랜치를 가리키는 컨텍스트 포인터를 남깁니다. 답(판결과 그것이 해소한 질문)도 이슈나 커밋에 남기세요. main 브랜치에는 검증된 결정만 남습니다.
