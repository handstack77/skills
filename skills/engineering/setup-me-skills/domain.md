# 도메인 문서

코드베이스를 탐색할 때 엔지니어링 스킬이 이 저장소의 도메인 문서를 어떻게 사용해야 하는지 설명합니다.

## 탐색하기 전에 이것들을 읽으세요

- 저장소 루트의 **`GLOSSARY.md`**, 또는
- 저장소 루트에 **`GLOSSARY-MAP.md`**가 있다면 그것: 컨텍스트마다 `GLOSSARY.md` 하나를 가리킵니다. 주제와 관련된 것들을 각각 읽으세요.
- **`docs/adr/`**: 작업하려는 영역을 건드리는 ADR을 읽으세요. 다중 컨텍스트 저장소에서는 컨텍스트 범위의 결정을 위해 `src/<context>/docs/adr/`도 확인하세요.

이 파일 중 없는 것이 있으면 **조용히 진행하세요**. 없다고 표시하지 말고, 미리 만들라고 제안하지도 마세요. `/domain-modeling` 스킬(`/grill-with-docs`와 `/improve-codebase-architecture`로 도달)이 용어나 결정이 실제로 정리될 때 필요한 만큼만 만듭니다.

## 파일 구조

단일 컨텍스트 저장소 (대부분의 저장소):

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

다중 컨텍스트 저장소 (루트에 `GLOSSARY-MAP.md`가 있음):

```
/
├── GLOSSARY-MAP.md
├── docs/adr/                          ← 시스템 전체 결정
└── src/
    ├── ordering/
    │   ├── GLOSSARY.md
    │   └── docs/adr/                  ← 컨텍스트별 결정
    └── billing/
        ├── GLOSSARY.md
        └── docs/adr/
```

## 용어집의 어휘를 사용하세요

출력이 도메인 개념(이슈 제목, 리팩터링 제안, 가설, 테스트 이름)을 명명할 때는 `GLOSSARY.md`에 정의된 용어를 쓰세요. 용어집이 명시적으로 피하는 동의어로 흘러가지 마세요.

필요한 개념이 용어집에 아직 없다면 그것이 신호입니다. 프로젝트가 쓰지 않는 언어를 지어내고 있거나(재고하세요) 실제 공백이 있는 것입니다(`/domain-modeling`을 위해 기록하세요).
